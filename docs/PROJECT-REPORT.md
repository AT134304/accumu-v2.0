## 1. 왜 만들었나

### 문제 인식

고등학생의 비교과 활동(동아리·대회·봉사·진로 체험)은 세 가지 문제를 갖고 있다.

1. **기록이 흩어진다.** 활동은 학교 공지, 개인 메모, 카카오톡 단톡방, 종이 확인서에 나뉘어 남는다. 정작 진학 준비를 시작할 때 "내가 뭘 했더라"를 다시 모아야 한다.
2. **참여를 확인할 방법이 약하다.** 이름만 올리고 오지 않거나, 왔다가 바로 가는 경우를 걸러낼 수단이 사실상 없다.
3. **참여 자체에 보상이 없다.** 봉사시간처럼 제도화된 일부를 빼면, 참여의 결과가 학생에게 즉시 돌아오지 않는다.

### 해결 방향

세 문제를 **하나의 흐름**으로 묶었다.

```
활동 참여  →  QR 입·퇴장 2회 인증  →  포인트 적립  →  월말 지역화폐 전환
                     ↓
             디지털 아카이브에 자동 기록  →  PDF 포트폴리오
```

**QR을 두 번 찍게 한 것이 이 설계의 핵심이다.** 입장만 인증하면 "얼굴만 비추고 가는" 참여를 막을 수 없고, 퇴장만 인증하면 늦게 와서 끝에만 나타나는 참여를 막을 수 없다. 두 번을 다 받아야 "처음부터 끝까지 있었다"가 성립한다.

포인트를 지역화폐로 전환한다는 아이디어는 실제 제도(경기도 기후행동 기회소득, 지자체 독서포인트)에서 가져왔다. 다만 이 프로젝트에서 **실제 결제·계좌 연동은 하지 않는다** — 시뮬레이션까지가 범위다.

## 2. 무엇을 만들었나

### 2-1. 학생 기능

| 기능 | 설명 |
|---|---|
| 회원가입 | 학교 계정(학교·학번·이름·비밀번호 + 관리자 초대코드) / 개인 계정(이메일 또는 네이버·구글 소셜) |
| 프로그램 탐색 | 유형 4종 × 진로 계열 7종 필터, 검색, 3가지 정렬 |
| 참여 신청 | 정원이 차면 자동으로 **대기열** 등록, 앞사람이 취소하면 순번대로 자동 승격 |
| QR 인증 | 입장·퇴장 각각 1회용 토큰, 30분 만료. 기간제 프로그램은 진행일마다 따로 인증 |
| 포인트 | 퇴장 인증이 끝나야 지급. 150~3,000P |
| 지역화폐 | M월 적립분이 (M+1)월 말일에 전액 자동 전환 |
| 디지털 아카이브 | 완료 활동 자동 기록, 진로 계열 레이더 차트, **PDF 인쇄** |
| 만족도 평가 | 별점 + 한줄평 |
| 온보딩 튜토리얼 | 신규 학생용 12단계 가이드 + 연습용 프로그램(관리자 스캔 없이 자동 인증) |

### 2-2. 관리자 기능 (의도적으로 5가지로 한정)

1. 프로그램 올리기 / 내리기 / 수정 (대표 사진 업로드 포함)
2. 담당 학생 5명의 아카이브 조회 (PDF 확인, 포인트 열람)
3. QR 카메라 스캔 (실제 카메라 권한 사용)
4. 담당 학생 해제
5. 담당 학생 비밀번호 초기화

### 2-2-1. 관리자를 견제하는 장치 (2026-08-20 추가)

관리자 기능을 5가지로 좁혀 놓아도, **그 5가지 안에서 아무거나 할 수 있다**는 문제가 남는다.
프로그램을 아무렇게나 올려도 막을 사람이 없었다. 실제 유사 시스템은 전부 승인자를 두지만
(꿈길의 학교운영자 승인, 청소년수련활동 인증제의 사전 심사), 1인 시연이라 승인자를 둘 수 없다.

**사람 대신 세 가지 장치를 뒀다.**

| 장치 | 무엇을 막나 |
|---|---|
| **끝난 프로그램 수정 잠금** | 이미 참여자와 지급된 포인트가 붙은 활동의 기록을 사후에 고치는 것 |
| **게시 전 세 관문** | 버튼 한 번에 학생 전체에게 공개되는 것 (미리보기 → 체크리스트 → 서버 검사) |
| **학생 신고 → 자동 게시중단** | 서로 다른 학생 3명이 신고하면 서버가 내린다. 사람이 처리하지 않는다 |
| **감사 로그** | 관리자의 모든 쓰기를 남긴다. 막지는 않지만 전부 추적된다 |

**가장 마음에 드는 부분은 두 목록이 같다는 것이다.** 관리자가 게시 전에 체크하는 3문장과, 참여하지
않은 학생이 신고할 수 있는 3가지가 정확히 같은 항목이다(학업 아님 / 무료 / 부적절하지 않음).
*"네가 올리며 확인한 것이 곧 학생이 신고할 수 있는 것"* 이라서, 신고가 취향 차이가 아니라
**약속 위반**을 가리킨다.

**신고는 두 종류로 갈린다.** 공고만 봐도 아는 것(유료·학업·부적절)은 누구나, 겪어야 아는 것
(시간 미준수·설명 불일치)은 QR 입장 인증을 마친 학생만 신고할 수 있다. 그리고 **이유 서술의 최소
길이가 다르다** — 공개 150자, 참여자 80자. 신고의 비용은 *진입장벽 + 글자 수*인데 두 신고의
장벽이 다르기 때문이다. 같은 하한을 걸면 실제로 피해를 겪은 학생이 오히려 더 손해를 본다.

**셋 다 관리자가 새로 할 수 있게 된 일은 0개다.** 신고는 학생 기능, 자동 게시중단은 서버 동작,
감사 로그는 읽는 화면이 없다. 원칙 6("관리자 기능 5가지")을 늘리지 않고 견제만 추가한 것이다.

**신고 설계에서 가장 신경 쓴 것은 "관리자가 신고자를 알 수 없게" 하는 것이었다.** 이 앱의 관리자는
담당 학생의 비밀번호를 초기화할 수 있다(ADR 0019). 신고자를 특정할 수 있으면 보복 경로가 생기고,
그 순간 학생은 신고하지 않는다. 그래서 관리자는 자기 프로그램에 대한 신고조차 **읽을 수 있는 정책이
아예 없고**, 받는 알림에도 신고자·건수·사유가 들어가지 않는다 — "내려갔다"는 사실 하나만 간다.

### 2-3. 안 만든 것 (범위 밖으로 명시)

실제 결제·계좌 연동, 법정대리인 동의 절차, GPS 인증, 백그라운드 푸시 알림, 다중 관리자, 학교 단위 대시보드, 외부 봉사 API 연동.

> **"안 만든 것"을 문서에 적어 둔 이유**: 범위를 적어 두지 않으면 기능은 계속 늘어난다. 무엇을 만들지보다 **무엇을 만들지 않을지**를 먼저 정해 두는 편이 프로젝트를 끝낼 수 있게 한다.

## 3. 어떻게 만들었나 (아키텍처)

### 3-1. 전체 구조

```
[학생 브라우저]  [관리자 브라우저]
       │                │
       └────── React (Vite) ──────┐
                                  │  supabase-js (anon key)
                                  ▼
                       ┌──────────────────────┐
                       │      Supabase        │
                       │  ┌────────────────┐  │
                       │  │  PostgreSQL    │  │ ← RLS 정책 28개가 권한의 실제 경계
                       │  │  + 서버 함수 37 │  │
                       │  └────────────────┘  │
                       │  Auth / Storage      │
                       │  Edge Functions ×3   │ ← 네이버·구글 OAuth, 비밀번호 초기화
                       └──────────────────────┘
```

**별도의 백엔드 서버가 없다.** 권한 판정과 비즈니스 규칙을 전부 데이터베이스 안에 두었다.

### 3-2. 왜 별도 서버를 두지 않았나

서버를 하나 더 두면 "권한을 검사하는 곳"이 두 군데(서버 + DB)가 된다. 두 곳이 시간이 지나며 어긋나면, 어긋난 쪽이 곧 보안 구멍이 된다. **경계를 한 곳에만 두는 편이 1인 프로젝트에서는 더 안전하다**고 판단했다.

### 3-3. RLS(Row Level Security)를 권한의 소유자로

이 프로젝트에서 가장 중요한 설계 원칙이다.

```sql
-- 예시: 학생은 자기 참여 기록만 읽을 수 있다
create policy "participations_select_own"
  on public.participations for select to authenticated
  using (student_id = auth.uid());
```

프런트엔드 코드에는 `if (내 것이 아니면 숨긴다)` 같은 판단이 **거의 없다.** 화면에서 숨기는 것은 UX일 뿐이고, 개발자도구로 우회할 수 있기 때문이다. 진짜 경계는 DB가 갖는다.

이 원칙을 지키니 부수 효과가 생겼다. 예를 들어 관리자가 담당 학생의 아카이브를 보는 화면에서 **"이 학생이 내 담당인가"를 코드로 검사하지 않는다.** `mentor_students` 테이블에 매핑이 있는 학생만 조회 결과에 나오기 때문이다. 즉 **테이블 자체가 권한 경계**다.

### 3-4. 설계 결정을 기록으로 남겼다 (ADR 23건)

`docs/adr/`에 결정 하나마다 문서를 하나씩 남겼다. 각 문서는 이 형식을 따른다.

```
배경 (무엇이 문제였나)
  → 결정 (무엇을 골랐나)
  → 대안으로 고려했던 것 (왜 그것들은 안 골랐나)
  → 원칙 체크 (프로젝트 원칙을 어기지 않는가)
  → 재검토 시점 (언제 이 결정을 다시 봐야 하나)
```

2주짜리 프로젝트에 이런 문서가 필요했던 이유는, **과거의 내가 왜 그렇게 했는지 일주일만 지나도 기억나지 않기 때문**이다. 실제로 결정을 뒤집을 때마다 이 기록이 "그때 무엇을 막으려 했는지"를 알려줘서, 같은 함정을 다시 밟지 않을 수 있었다.

## 4. 지킨 원칙 6가지

프로젝트 시작 시점에 원칙을 먼저 정하고, 새 기능마다 위반 여부를 검토했다.

| # | 원칙 | 이유 |
|---|---|---|
| 1 | **게임적·사행적 요소 배제** | 랜덤박스·뽑기·경쟁 랭킹·아바타 성장 없음. 학생을 경쟁시키는 순간 "활동 기록"이 아니라 "점수 경쟁"이 된다 |
| 2 | **학업이 아닌 진로·커리어 활동** | 자습·문제풀이는 대상이 아니다 |
| 3 | **지역화폐 전환은 시뮬레이션만** | 실제 결제 연동은 미성년자 대상 서비스에서 별도의 법적 절차가 필요하다 |
| 4 | **포트폴리오가 포인트보다 먼저 보인다** | 포인트가 주인공이 되면 "돈 벌려고 하는 활동"이 된다. 그래서 포인트 색(amber)은 화면당 한 곳으로 제한 |
| 5 | **QR은 입장·퇴장 2회 인증** | 부정 참여 방지 장치라 단순화하지 않는다 |
| 6 | **관리자 기능은 5가지로 한정** | 학교 단위 대시보드·통계를 넣지 않는다 |

### 원칙이 실제로 코드를 막은 사례

- **"기타" 카테고리를 만들지 않았다.** 애매한 활동이 갈 곳이 생기면 전부 그리로 몰려 분류가 무너진다.
- **방과후 활동을 뺐다.** 참여에 돈이 드는 활동을 포인트로 보상하면 "돈 내고 포인트 사는" 구조가 된다.
- **관리자에게 신청자 명단을 주지 않았다.** 화면에서 숨긴 게 아니라, 애초에 그 데이터를 읽을 수 있는 RLS 정책을 만들지 않았다.
- **정산 화면에 진행바·달성률을 넣지 않았다.** 원칙 1(게임화 배제)에 걸린다. 그런 CSS 클래스 자체를 만들지 않았다.

## 5. 기억할 만한 기술적 결정 8가지

> 면접에서 가장 많이 쓰일 부분. 각 항목은 **문제 → 선택지 → 왜 이걸 골랐나** 순서다.

### 5-1. QR 코드에 토큰 하나만 담았다

**문제** — 처음에는 QR에 `{참여ID, 종류(입장/퇴장), 만료시각, 토큰}` 4개를 JSON으로 담았다.

**깨달은 것** — 서버가 검증에 쓰는 값은 **토큰 하나뿐**이었다. 참여ID와 종류는 위조할 수 있어서 신뢰할 수 없고, 만료시각은 학생 화면의 카운트다운 표시용이라 발급 응답에서 읽으면 된다.

**결과**

| | 담는 내용 | 크기 | QR 버전 |
|---|---|---|---|
| 이전 | JSON 4필드 | 약 136바이트 | 버전 7 (45×45 격자) |
| 이후 | 토큰 10자 | 10바이트 | **버전 1 (21×21 격자)** |

격자가 성글어지니 오류 정정 수준을 15%에서 25%로 올리고도 크기가 그대로였다. **카메라 인식 속도가 빨라지고, 화면 반사나 기울임에도 강해졌다.**

**이 사례의 요점** — 보안(위조 가능한 값을 신뢰하지 않는다)과 성능(QR이 성글어진다)이 **같은 방향**을 가리켰다. 서버가 읽지 않는 값을 담는 것은 그 자체로 설계 오류였다.

### 5-2. 지역화폐 전환을 "학생이 누르는 버튼"에서 "월 단위 자동 정산"으로 바꿨다

**문제** — 처음에는 학생이 금액을 골라 전환 버튼을 누르는 방식이었다. 그런데 실제 제도(기후행동 기회소득 등)는 그렇게 동작하지 않는다. 적립 기간이 끝나면 **전액이 일괄 지급**된다.

**결정** — M월 적립분 전액을 (M+1)월 말일에 자동 전환. 학생은 시점도 금액도 고르지 않는다. 서버 함수 `settle_my_points()`는 **인자가 0개**다.

**구현에서 흥미로웠던 점** — 정산을 스케줄러(`pg_cron`)로 돌리지 않았다. 대신 **학생이 화면에 들어올 때 계산**한다.

> 정산 결과가 *시각*이 아니라 *날짜*의 함수이기 때문이다. 8월 적립분은 9월 30일이 지났으면 언제 계산해도 답이 같다. 그러면 "정해진 시각에 도는 작업"이 필요 없다.

중복 정산은 `unique (student_id, settled_month)` 제약이 막는다. 즉 **멱등성을 코드가 아니라 DB 제약이 보장한다.**

### 5-3. 소셜 로그인을 Supabase 기본 경로 대신 직접 구현했다

**배경** — Supabase는 구글 로그인을 기본 지원한다. 네이버는 지원하지 않는다.

**처음 결정** — 구글은 Supabase 경로로, 네이버는 Edge Function으로 (각자 쉬운 방법으로).

**뒤집은 이유** — 두 제공자의 **설정하는 곳**과 **고장났을 때 볼 곳**이 갈렸다.

| | 설정 위치 | 로그 위치 |
|---|---|---|
| 구글(Supabase 경로) | Supabase 대시보드 Providers | Supabase Auth 로그 |
| 네이버(Edge Function) | Edge Function 환경변수 | Edge Function 로그 |

시연 중에 로그인이 안 되면 **어디를 봐야 할지부터 갈린다.** 그래서 구글도 Edge Function으로 옮겨 둘을 같은 모양으로 맞췄다(ADR 0011).

**요점** — 각자 최적인 방법을 쓰는 것보다, **둘이 같은 모양인 것**이 유지보수에서 더 가치 있을 때가 있다.

### 5-4. 정원이 차면 "거부"가 아니라 "대기열"

**문제** — 처음에는 정원이 차면 신청을 거부했다. 그러면 학생은 계속 새로고침하며 자리가 나기를 기다려야 한다.

**결정** — 정원이 차도 신청을 받되 `waitlisted` 상태로 등록한다. 앞사람이 취소하면 **가장 먼저 신청한 대기자가 자동으로 승격**된다.

**왜 서버 함수(RPC)로 만들었나** — 취소는 "내 행을 지운다"에서 끝나지 않는다. 자리가 하나 비고, 그 자리를 대기자에게 넘겨야 한다. **두 행에 걸친 원자적 연산**이라 RLS 정책 하나로는 표현할 수 없다. `security definer` 함수 안에서 `for update` 잠금으로 처리했다.

### 5-5. 공개 버킷의 SELECT 정책을 지웠다 (보안)

**상황** — 프로그램 대표 사진을 Supabase Storage 공개 버킷에 저장하면서 `insert` 정책과 `select` 정책을 함께 만들었다.

**발견** — 공개 버킷의 이미지 읽기는 `/storage/v1/object/public/` 경로가 처리하고, **그 경로는 RLS를 타지 않는다.** 즉 select 정책은 이미지 표시에 필요 없었다.

그런데 `to public` select 정책이 있으면 anon 키로 `list('')`가 통과한다. 그러면 이런 것들이 전부 열거된다.

- 아직 게시하지 않은 **초안 프로그램의 사진**
- 등록에 실패해 버려진 사진
- 관리자의 UUID (폴더 이름이 곧 `auth.uid()`였다)
- 업로드 시각 등 메타데이터

"파일명이 UUID라 추측할 수 없다"는 전제가 **열거 앞에서는 무의미**했다. 정책을 지우는 것만으로 닫혔고, 이미지 표시는 그대로 동작했다.

### 5-6. 비밀번호 변경에 현재 비밀번호를 요구하도록 바꿨다

**처음 결정** — 로그인된 세션 자체가 본인 확인이므로 현재 비밀번호를 묻지 않는다. (Supabase Auth의 기본 신뢰 모델과 같다.)

**뒤집은 이유** — 논리는 틀리지 않았지만 **막으려는 위협을 잘못 골랐다.** 이 확인이 실제로 막는 것은 "계정 주인인가"가 아니라, **로그인된 화면을 잠깐 만진 사람이 계정을 영구히 가져가는 것**이다.

| 상황 | 안 물으면 | 물으면 |
|---|---|---|
| 학교 공용 PC에 로그아웃 안 하고 감 | 다음 사람이 비밀번호를 바꿔 계정 탈취 | 못 바꿈 |
| 폰을 잠깐 빌려줌 | 같음 | 못 바꿈 |

이 서비스는 **학번이 곧 로그인 아이디**라 아이디가 이미 반쯤 공개돼 있고, 학교 공용 PC 사용이 전제된 환경이다. 표준 관행이기도 하다(OWASP ASVS가 명시적으로 요구).

**구현에서의 문제** — Supabase의 재인증 API는 확인 코드를 **메일로 보낸다.** 그런데 학번 계정은 `20250001@accumu.local` 같은 가상 주소라 메일을 받을 수 없다. 그래서 **세션의 이메일로 로그인을 한 번 더 시도**하는 방식으로 검증했다.

### 5-7. 카테고리 8종을 4종으로 재편했다

**문제** — 처음 카테고리는 `교내 동아리 / 교내 대회 / 교내 기타 / 교외 봉사 / 교외 대회 / 교외 기타 / ...` 였다.

**진단** — 하나의 분류 안에 **두 개의 축**이 눌려 있었다. "어디서 하는가(교내/교외)"와 "무엇을 하는가(동아리/대회/봉사)". 그래서 "대회"가 두 곳에, "기타"가 두 곳에 나뉘었다.

**결정** — 두 축을 완전히 분리했다.

- `category`(4종): 교내 활동 / 대회·공모전 / 봉사활동 / 진로 체험 — **무엇을 하는가**
- `career_track`(7종): 인문·어학 / 사회·교육 / 상경·경영 / 자연과학 / 공학·IT / 의약·보건 / 예술·체육 — **어느 진로 계열인가**

"어디서"는 카테고리가 아니라 주최 기관 이름(`org`)이 화면에 찍어 주면 되는 정보였다.

### 5-8. 휴대폰 가로 모드를 "고치지 않고 지원 범위에서 뺐다"

**문제** — 가로 모드에서 튜토리얼 안내 배너가 안내 대상을 덮는 문제가 있었다.

**진단** — 반응형 기준(980/768/600/430px)이 전부 **폭** 기준이었다. 폰을 눕히면 폭은 오히려 넉넉해지고(800px+) **높이가 400px 안팎**으로 줄어든다. 그 구간은 설계된 적이 없었다.

**결정** — 고치는 대신 **지원하지 않는다고 명시**했다. 가로 + 높이 500px 미만 + 터치 기기이면 안내 화면이 덮는다.

> 그냥 두면 리뷰어가 폰을 돌렸을 때 **"버그"**로 보이지만, 말해 주면 **"의도"**가 된다. 둘의 차이는 코드량이 아니라 신뢰다.

조건을 세 개로 좁힌 이유: 태블릿 가로(높이 768px)는 멀쩡하므로 제외하고, 데스크톱 창을 세로로 짧게 줄인 경우에 "폰을 돌리세요"가 뜨지 않도록 터치 기기로 한정했다.

### 5-9. 각각은 옳은 결정 두 개가 겹치는 자리에서 구멍이 났다

> **이 프로젝트에서 찾은 가장 심각한 보안 문제이자, 가장 설명할 가치가 있는 사례다.**

**결정 A (초대코드)** — 관리자마다 고정된 학교 초대코드를 준다. 값은 `SCH-` + `md5(관리자 uuid)`
앞 4자로 만든다. 결정론적이라 마이그레이션을 다시 돌려도 같은 코드가 나온다. 합리적이었다.

**결정 B (대표 사진)** — 프로그램 사진을 Supabase Storage에 올린다. 관리자마다 자기 폴더에만
올릴 수 있게 경로를 `{관리자 uuid}/{파일}.webp`로 잡는다. 폴더 이름이 곧 소유자라 정책이 한 줄로
끝난다. 이것도 합리적이었다.

**겹치는 자리** — 사진의 공개 URL은 이렇게 생겼다.

```
https://<프로젝트>.supabase.co/storage/v1/object/public/program-images/<관리자 uuid>/사진.webp
                                                                       ^^^^^^^^^^^^^^
```

그리고 이 URL은 **학생 화면의 카드가 실제로 읽는 필드**다. 그러면 이렇게 된다.

```
사진이 붙은 프로그램을 하나라도 본 학생
   → 카드 데이터에서 관리자 uuid를 읽는다
   → md5(uuid) 앞 4자를 계산한다          ← 브라우저 콘솔 한 줄
   → 그게 그 관리자의 학교 초대코드다
```

**무차별 대입이 아니다. 계산이다.** 더 뼈아픈 건, 이 코드를 지키려고 앞서 만들어 둔 방어
(연속 5회 실패 시 15분 잠금)가 **이 경로를 전혀 막지 못한다**는 점이었다. 첫 시도가 맞으니까.
막으려는 위협을 잘못 골랐던 것이다.

**해결** — 코드를 난수로 바꿨다. salt를 섞는 방법도 검토했지만 기각했다. **salt가 저장소에 남으면
같은 문제가 그대로 돌아온다.** 입력이 공개값 하나뿐인 해시는 "비밀"이 아니라 그냥 **인코딩**이다.

그리고 규칙을 함수 하나(`new_school_invite_code()`)로 뽑아냈다. 원래 그 규칙은 마이그레이션 네 곳에
**리터럴로 복사돼 있었다** — 트리거를 재정의할 때마다 옛 규칙을 그대로 옮겨 적었기 때문이다.
값을 고치는 것과 별개로, 규칙의 주인이 없으면 같은 일이 다섯 번째로 반복된다.

**이 사례의 요점** — 코드 리뷰로는 못 찾는 종류의 문제다. 두 파일 다 각각 보면 잘못된 곳이 없다.
문제는 파일이 아니라 **결정 사이의 공백**에 있었다: "관리자 uuid는 비밀인가?"를 물어본 문서가
어디에도 없었다. 설계 결정을 문서로 남겨왔는데도 그 문서들 **사이**는 비어 있었던 셈이다.

### 5-10. 검증을 "설명"에서 "실행"으로 옮겼다

권한 경계를 전부 DB에 두고 문서로 꼼꼼히 설명해 뒀지만, **그것이 실제로 막히는지 실행해 본 적은
없었다.** 그리고 정책은 한 줄만 어긋나도 조용히 열리는데, **조용히 열린 것은 화면을 봐서는 절대
발견되지 않는다** — 화면은 원래 그 데이터를 안 그리기 때문이다.

그래서 회귀 테스트를 만들었다(`npm run test:rls`). anon / 학생 2명 / 관리자 2명의 세션으로 금지된
요청 약 50건을 실제 HTTP로 쏜다.

```
anon    → programs insert                     기대: 42501
학생    → 남의 학생 프로필 select              기대: 0행
학생    → 자기 포인트 잔액 직접 update         기대: 0행 영향
관리자A → 관리자B 프로그램 update              기대: 0행 영향
관리자A → 소유권을 B에게 이전                  기대: 0행 영향
관리자A → 공백만 있는 제목으로 등록            기대: 23514
관리자B → 관리자A 프로그램의 QR 인증           기대: not_authorized
같은 QR 토큰 두 번 스캔                        기대: used
```

**통과가 아니라 거부를 기대하는 테스트가 대부분이다.** 그리고 검증 요청에는 `service_role` 키를
쓰지 않는다 — 그 키는 RLS를 통째로 우회해서, 그걸로 테스트하면 **전부 통과하고 아무것도 검증하지
않는다.**

위 5-9의 회귀를 잡는 케이스도 넣었다: 저장된 초대코드가 `md5(관리자 uuid)`와 같지 않은지 확인한다.
마이그레이션을 안 돌린 환경에서 즉시 빨간불이 뜬다.

## 6. 결정을 뒤집은 기록

> 면접에서 **"실패하거나 바꾼 경험"**을 물으면 쓸 소재. 뒤집었다는 사실 자체보다 **왜 처음 판단이 틀렸는지 설명할 수 있는가**가 중요하다.

| 무엇을 | 처음 | 나중 | 왜 바꿨나 |
|---|---|---|---|
| 구글 로그인 | Supabase 기본 경로 | Edge Function 직접 구현 | 제공자마다 디버깅할 곳이 갈리면 시연 중 원인을 못 찾는다 |
| 지역화폐 전환 | 학생이 버튼으로 실행 | 월 단위 자동 정산 | 실제 제도가 그렇게 동작하지 않는다 |
| 정원 초과 | 신청 거부 | 대기열 자동 등록 | 거부는 학생에게 아무 다음 행동도 주지 않는다 |
| 관리자의 포인트 열람 | 금지(원칙 4) | 상세 화면 1줄 허용 | 원칙 4의 목적은 "비교표 방지"인데, 학생 1명 상세는 비교표가 아니다 |
| 관리자 기능 개수 | 3종 → 4종 → **5종** | | 담당 해제·비밀번호 초기화는 실제로 필요했다. 원칙을 어긴 게 아니라 **원칙을 개정하고 근거를 남겼다** |
| 비밀번호 변경 | 현재 비밀번호 안 물음 | 물음 | 막으려는 위협을 잘못 골랐다 (5-6 참고) |
| 학교 정보 | 관리자가 소유, 학생은 상속 | 학생이 직접 입력·대조 | 관리자가 없는 학교도 성립해야 한다 |
| 가로 모드 | 고치려 함 | 지원 범위에서 제외 | 시연에서 아무도 안 볼 경로에 복잡도를 붙이는 일 |

**공통점** — 대부분 "기능을 더 넣어서" 해결한 게 아니라 **범위를 좁히거나 중복을 없애서** 해결했다.

## 7. 어려웠던 문제와 해결

> 면접에서 **"가장 어려웠던 문제"**를 물으면 쓸 소재. 셋 다 **증상과 원인이 다른 곳에 있던** 사례다.

### 7-1. 사진을 올렸더니 카드 전체가 사진에 덮였다

**증상** — 프로그램 카드의 아이콘 자리에 사진을 넣었더니, 사진이 카드 전체를 덮어 제목·날짜가 보이지 않았다.

**첫 가설(틀림)** — "사진을 안 잘라서 그렇다."

**진짜 원인** — CSS Grid의 크기 계산 순환이었다.

```
.thumb 는 display:grid, 행 크기가 auto (높이 108px 지정)
   ↓
auto 행의 높이를 재는 시점에는 행 높이가 아직 정해지지 않았다
   ↓
그래서 자식 이미지의 height:100% 가 auto 로 해석된다
   ↓
행이 이미지 원본 높이(폰 사진이면 3000px)로 잡힌다
   ↓
108px 컨테이너를 넘어 본문 위를 덮는다
```

`place-items:center` 때문에 stretch도 걸리지 않아 이미지가 스스로 줄어들지도 않았다.

**해결** — 이미지를 `position: absolute; inset: 0`으로 흐름에서 빼냈다. 그러면 행 크기 계산에 아예 참여하지 않고 `inset:0`이 108px 컨테이너에 직접 걸린다.

**배운 것** — 증상("사진이 크다")과 원인("행 높이 계산")이 다른 층에 있었다. 자르기 기능은 결국 별도로 만들었지만, 그것만으로는 이 버그가 고쳐지지 않았다.

### 7-2. 모바일에서 튜토리얼이 아무것도 없는 곳을 가리켰다

**증상** — 데스크톱에서는 잘 동작하는 튜토리얼 하이라이트가, 모바일에서는 화면 왼쪽 위 구석의 작은 점으로 나타났다.

**원인** — 하이라이트할 요소를 `querySelector`로 찾는데, 이 앱은 같은 메뉴가 **두 벌** 있다. 데스크톱 상단 메뉴와 모바일 하단 탭바다. `querySelector`는 항상 DOM에서 먼저 나오는 **데스크톱 메뉴**를 반환했고, 그 요소는 모바일에서 `display:none`이라 좌표가 전부 0이었다.

혼란스러웠던 점은 **클릭은 정상 동작했다**는 것이다. 클릭 판정은 `closest()`로 하기 때문에 실제로 누른 요소를 기준으로 했다. 그래서 "안내만 안 보이는" 것처럼 보였다.

**해결** — 크기가 0인 요소를 건너뛰고 실제로 보이는 요소를 고르는 함수를 만들어 교체했다.

### 7-3. 모바일에서 로고가 잘렸다 — 그런데 원인은 로고가 아니었다

**증상** — 휴대폰에서 상단바의 "Accumu" 로고가 `Ac…`로 잘렸다.

**원인** — 상단바 전체의 폭 예산이 이미 넘쳐 있었다.

```
좌우 패딩 32 + 요소 간격 40 + 로고 아이콘 39
  + 캘린더 36 + 알림 36 + 포인트칩·아바타 120 + 로그아웃 36  =  약 339px
```

360px 화면에서 로고 글자에 남는 자리가 **21px**이었다. 코드 주석에는 "320px 같은 초소형 화면에서만 줄어든다"고 적혀 있었는데, 그 주석을 쓴 뒤에 캘린더 아이콘이 추가되면서 예산이 40px 늘어난 상태였다.

**해결** — 픽셀을 더 깎는 대신 **중복을 없앴다.** 아바타는 마이페이지로 가는 지름길인데, 그 화면 폭에서는 하단 탭바에 "마이" 탭이 이미 떠 있었다. 같은 목적지 버튼이 한 화면에 두 개였던 것이다. 포인트 잔액도 마이페이지가 본진이다. 그래서 그 칩을 상단바에서 빼니 **사라지는 정보가 0개인 채로** 로고 자리가 100px 넘게 남았다.

**배운 것** — "자리가 모자라다"는 문제는 대부분 **줄여야 할 것**이 아니라 **빼야 할 중복**을 알려주는 신호였다.

## 8. 한계와 앞으로

### 지금의 한계

- **실사용자 검증이 없다.** 1인 시연용으로 만들어 실제 학생·교사가 써 본 적이 없다.
- **학교가 여러 개일 때의 설계가 얕다.** 학번이 전역 고유값이라 두 학교에 같은 학번이 있으면 충돌한다.
- **테스트가 권한 경계에만 있다.** RLS 회귀 테스트 약 50건(`npm run test:rls`)은 있지만, 화면·상태·계산 로직에 대한 단위 테스트는 없다.
- **접근성이 부분적이다.** 키보드 포커스 트랩과 스크린리더 라벨은 넣었지만 전체 점검은 못 했다.

### 더 만든다면

1. 학교를 별도 테이블로 분리하고 학번을 학교 단위 고유값으로 (다중 학교 지원)
2. 참여 이력 기반 추천 고도화 (지금은 관심 계열 일치 + 최신순)
3. 프로그램 `status`를 자유 입력에서 **파생값**으로 (지금은 진행 전인데 날짜와 status가 어긋날 수 있다 — 표시와 사실이 갈린다)
4. 신고 임계치를 학교 규모에 비례하게 (지금은 3명 고정 — 학생 5명짜리 데모에 맞춘 값이다)
5. 실제 학생 대상 사용성 테스트

## 9. 예상 면접 질문과 답변 방향

> **아래 답변을 외우지 말 것.** 면접관은 준비된 문장인지 이해한 내용인지 금방 구분한다.
> 각 항목의 **핵심 아이디어만 잡고 자기 말로 설명**하는 연습을 할 것.
> 그리고 이 문서에 있는 내용은 전부 실제로 설명할 수 있어야 한다 — 설명할 수 없는 항목은 말하지 않는 편이 낫다.

### Q1. 이 프로젝트에서 가장 어려웠던 점은?

→ **7장의 세 사례 중 하나**를 고르되, "증상과 원인이 달랐다"는 구조로 말하기.
→ 추천: 7-1(CSS Grid)은 기술적 깊이가, 7-3(로고)은 문제 해결 방식이 잘 드러난다.

### Q2. QR 인증은 어떻게 구현했나요?

→ 흐름: 학생이 발급 요청 → 서버가 1회용 토큰 생성(30분 만료) → 학생 화면에 QR 표시 → 관리자가 카메라로 스캔 → 서버가 만료·재사용 검증 → 통과 시 시각 기록 + 토큰 즉시 무효화
→ 덧붙일 것: **왜 두 번 찍는가**(1장), **왜 토큰만 담는가**(5-1)

### Q3. 보안은 어떻게 신경 썼나요?

→ 네 층으로 나눠 설명:
1. **권한 경계를 DB에 두었다** (RLS 28개). 프런트에서 숨기는 것은 UX일 뿐 경계가 아니다
2. **실제로 구멍을 찾아 막았다** (5-5 Storage 열거, 5-6 비밀번호, **5-9 초대코드 — 이게 제일 세다**)
3. **1회용 토큰 + 만료** (QR)
4. **막혔다는 것을 실행해서 증명한다** (5-10 RLS 회귀 테스트 약 50건)

→ 하나만 고른다면 **5-9**. "취약점을 찾았다"가 아니라 **"각각 옳은 결정 두 개가 겹치는 자리에서
   생긴 문제"**라는 구조로 말할 것. 코드 리뷰로는 안 잡히는 종류라는 점이 핵심이다.
→ 자주 나오는 후속 질문: *"그럼 앞으로 어떻게 예방하나요?"*
   → 답: 값을 고치는 것과 **규칙의 주인을 하나로 만드는 것**은 다른 일이다. 그 규칙이 마이그레이션
     네 곳에 복사돼 있었기 때문에 계속 되살아났고, 함수로 뽑아낸 뒤에야 다시 새어나갈 자리가 없어졌다.

### Q4. React를 왜 골랐나요?

→ 솔직하게: 화면 간 상태 공유(로그인 정보, 알림 개수)를 다루기에 컴포넌트 구조가 맞았고, 자료가 많아 혼자 배우기 좋았다.
→ 덧붙일 것: 그 전에 순수 HTML/CSS/JS로 프로토타입을 먼저 만들었고(`Accumu_prototype.html`), **거기서 "새로고침하면 데이터가 사라진다"는 한계를 겪은 뒤** 백엔드가 필요하다고 판단했다.

### Q5. Supabase를 쓰면 직접 만든 게 적은 것 아닌가요?

→ 방어적으로 답하지 말 것. 사실을 말하면 된다:
"서버 인프라를 직접 세우는 대신 **권한 설계와 데이터 모델링**에 시간을 썼습니다. RLS 정책 28개와 서버 함수 38개를 직접 설계했고, 특히 **어떤 데이터를 누가 읽을 수 있는가**를 테이블 구조 자체로 표현하려고 했습니다. 예를 들어 관리자가 담당 학생만 볼 수 있는 것은 코드의 if 문이 아니라 `mentor_students` 테이블이 보장합니다."

### Q6. 왜 기능을 더 안 넣었나요? / 관리자 기능이 5개뿐인 이유는?

→ 원칙 6과 그 개정 이력(6장)을 설명.
→ 핵심: "기능을 늘리지 않은 게 아니라, **늘릴 때마다 근거를 남겼다.** 3종에서 5종이 됐는데 그때마다 왜 필요한지, 원칙의 어느 부분과 충돌하는지를 문서로 정리했습니다."

### Q7. 혼자 만들었나요? / AI를 썼나요?

→ **사실대로 말할 것.** 어떤 도구를 썼는지보다 **네가 무엇을 결정했는지**가 평가 대상이다.
→ 강조할 것: 원칙 6가지를 정한 것, 결정을 뒤집은 판단들(6장), 무엇을 만들지 않을지 정한 것(2-3).
→ 준비할 것: 이 문서의 아무 항목이나 짚어서 "이건 왜 그렇게 했어요?"라고 물었을 때 답할 수 있어야 한다.

### Q8. 이 서비스가 실제로 쓰인다면 무엇이 문제일까요?

→ 8장의 한계를 먼저 말하기. **스스로 한계를 아는 것**이 좋은 신호다.
→ 특히: 다중 학교 설계, 실사용자 검증 부재, 개인정보(학번·이름) 처리에 대한 법적 절차.

### Q9. 한국디지털미디어고에 와서 뭘 더 하고 싶나요?

→ 8장 "더 만든다면"과 연결. 자동화 테스트, 다중 학교 설계, 실사용자 테스트.
→ 개인적 동기와 연결할 것: 이 프로젝트에서 **혼자서는 검증에 한계가 있었다**는 점 → 함께 만들고 리뷰받는 환경이 필요하다.

## 10. 용어 사전

> 면접에서 쓸 용어. **뜻을 모르면 쓰지 말 것.**

| 용어 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| **RLS** (Row Level Security) | DB가 행 단위로 "누가 이 행을 볼 수 있는가"를 판정하는 기능 | 권한의 실제 경계. 정책 28개 |
| **정책(Policy)** | RLS의 규칙 하나. `using`(읽기 조건) / `with check`(쓰기 조건) | `participations_select_own` 등 |
| **security definer 함수** | 함수를 만든 사람의 권한으로 실행되는 DB 함수. RLS를 우회할 수 있어 조심해서 써야 함 | 여러 행에 걸친 연산(대기열 승격)에 사용 |
| **멱등성(Idempotency)** | 같은 작업을 여러 번 해도 결과가 한 번 한 것과 같은 성질 | 월 정산이 중복 실행돼도 안전하도록 unique 제약으로 보장 |
| **트리거(Trigger)** | 특정 테이블에 변화가 생길 때 자동 실행되는 DB 함수 | 회원가입 시 프로필 자동 생성 |
| **Edge Function** | Supabase가 제공하는 서버리스 함수 (Deno) | 네이버·구글 OAuth 교환, 비밀번호 초기화 |
| **OAuth** | 다른 서비스 계정으로 로그인하게 해 주는 표준 | 네이버·구글 로그인 |
| **ADR** (Architecture Decision Record) | 설계 결정과 그 이유를 남기는 문서 | 23건 |
| **마이그레이션** | DB 스키마 변경을 순서대로 기록한 SQL 파일 | 35개 |
| **anon key** | 클라이언트에 노출되는 공개 키. 이것만으로는 아무 데이터도 못 읽는다(RLS가 막는다) | 프런트가 쓰는 유일한 키 |
| **service_role key** | 모든 권한을 가진 비밀 키. 절대 클라이언트에 두면 안 된다 | 시딩 스크립트·Edge Function에서만 |
