## 배경 / 왜 필요한가

ADR 0005 "추가 확정"이 구현을 2단계로 나눴다. **1단계(QR + 관리자 셸·홈·스캔) 완료, 2단계 전반부(프로그램 관리) 완료.** 남은 것이 이 화면이고, `/admin/students`는 지금 `AdminPlaceholderPage`로 연결돼 있다(`src/App.jsx` 68~78줄).

지금 앱의 상태를 정확히 말하면 이렇다. **QR 퇴장 인증이 `completed` 참여와 포인트 원장을 만들어내고 있는데, 그 결과를 사람이 읽는 화면이 앱 어디에도 없다.** 학생 본인 아카이브(`/student/archive`)도 placeholder이고, 학생 홈의 StackViz는 블록이 쌓이는 것만 보여준다(숫자·목록 없음). 즉 **"비교과 활동 참여 → 디지털 포트폴리오"라는 이 프로젝트의 한 문장짜리 정체성이 아직 화면으로 존재하지 않는다.**

이번 스펙이 채우는 것이 그 칸이다. 그리고 이 화면은 **앱 최초의 "남의 기록을 읽는 화면"**이다 — 지금까지 관리자가 본 것은 자기가 만든 `programs`와 스캔 RPC가 돌려준 한 줄뿐이었다. 그래서 이 스펙의 실질적 무게중심은 기능이 아니라 **"열려 있는 것 중 무엇을 보여주지 않을 것인가"**다.

### 구조 변경 — "담당 학생"을 **관리자 마이페이지**로 통합한다 (2026-07-30)

케빈의 최초 요청은 "관리자 마이페이지를 메뉴에 **추가**"였다. **그대로 하면 관리자 메뉴가 홈 + 3종 + 마이페이지 = 5개가 되고, 원칙 6(관리자 기능은 3가지로 한정)과 마찰이 생긴다.** 논의 결과 **기존 "담당 학생" 자리를 "마이페이지"로 바꾸고 그 안에 계정 정보를 얹는 것**으로 정리됐다.

**이것이 원칙 6과 충돌하지 않는 이유 — 기능이 아니라 배치가 바뀐다:**

| 관점 | 판단 |
|---|---|
| 메뉴 개수 | **변하지 않는다.** 홈 + 3종 = 4개 그대로. 새 항목이 추가되지 않는다 |
| 관리자가 할 수 있는 일 | **변하지 않는다.** 프로그램 관리 / QR 스캔 / 담당 학생 아카이브 조회 3종 그대로. **새로 생긴 동작이 0개**다 |
| DB 권한 표면 | **변하지 않는다.** 계정 정보는 `profiles_select_own`(본인 1행)으로 이미 읽고 있다 — `AdminShell`이 지금도 우측에 이름·코드를 그리고 있다(`AdminShell.jsx` 67~73줄) |
| 원칙 6이 금지하는 것 | "학교 단위 대시보드"와 "다중 관리자 관리". 본인 계정 정보 표시는 **어느 쪽도 아니다** |
| 학생 화면과의 대칭 | 학생 셸에도 `/student/mypage`가 있다(`ic-user`). 관리자만 자기 계정 화면이 없는 편이 오히려 비대칭이었다 |

**즉 "관리자 기능 3종"의 카운트는 관리자가 수행하는 **업무**의 개수이고, 본인 계정 정보 조회는 업무가 아니라 셸의 일부다.** 그것을 셸 구석의 텍스트에서 화면 상단으로 옮긴 것이 이번 변경의 전부다.

**[이 통합으로 원칙 1 가드의 중요도가 올라간다 — 반드시 인지할 것]**
계정 정보와 담당 학생 5명이 **한 화면에** 놓이면서, "관리자 본인 정보 옆에 학생 5명이 나란히 있는" 구조가 된다. 이런 배치는 심리적으로 **"내 담당 학생들 현황판"**으로 읽히기 쉽고, 그 순간 건수·포인트를 얹고 싶은 압력이 생긴다.
→ **결정 B(담당 학생 목록에 숫자 0개)는 이 구조에서 타협 대상이 아니라 이 화면이 성립하기 위한 전제다.** 아래 A절·B절·"절대 원칙 체크"에서 반복해 명시한다.

### A. 왜 2단계 라우트인가 (마스터-디테일 2단 레이아웃 기각)

원칙 1 가드는 "학생 1명 단위 화면"을 **요구**한다. 이걸 지키는 방법은 두 가지다.

| 안 | 판단 |
|---|---|
| **A-1 (채택) 목록 라우트 → 상세 라우트** | **한 화면에 학생이 1명만 존재한다.** 비교 UI를 만들려야 만들 수 없다 — 가드가 규율이 아니라 구조가 된다. 인쇄 대상도 "지금 이 페이지"로 자명해진다. 모바일에서 그대로 성립 |
| A-2 (기각) 좌측 5명 목록 + 우측 상세 | 옆에 5명이 계속 떠 있어 "여기에 건수만 살짝" 유혹이 상시 존재한다. 인쇄하면 좌측 목록까지 따라 들어간다. 430px에서 무너져 어차피 2단계로 접어야 한다 |
| A-3 (기각) 목록 + 상세 모달 | 인쇄 시 모달 오버레이/스크롤 컨테이너가 그대로 잘린다. PDF가 목적인 화면에서 모달은 최악의 컨테이너다 |

- 상세는 **URL 직접 진입·새로고침으로도 살아나야 한다**(목록을 거치지 않고 조회 가능해야 한다). 담당이 아닌 id를 URL에 넣으면 RLS가 0행을 내려주고 화면은 안내 문구를 띄운다(에러 표 참고).
- **마이페이지 통합 후 이 결정의 값어치가 더 커졌다.** 계정 정보 + 학생 5명이 한 화면에 오면서 A-2(마스터-디테일)를 골랐다면 **계정 + 5명 목록 + 1명 상세가 동시에 떠 있는 화면**이 됐을 것이고, 그건 정확히 "현황판"이다. A-1은 상세로 들어가는 순간 계정 정보와 나머지 4명이 **화면에서 사라진다.**

### M. 라우트 — `/admin/mypage` + 상세를 **그 하위에** 둔다

| 안 | 판단 |
|---|---|
| M-1 (기각) `/admin/students` 경로 유지, 라벨만 "마이페이지" | URL과 화면 이름이 어긋난다. 그리고 이제 이 화면의 주제는 학생이 아니라 **관리자 본인**이다 |
| **M-2 (채택) `/admin/mypage` + `/admin/mypage/students/:studentId`** | 아래 근거 |
| M-3 (기각) `/admin/mypage` + 상세는 `/admin/students/:studentId` | **상세에서 활성 메뉴가 사라진다** — 아래 근거의 정반대 결과 |

**채택 근거 (특히 M-3을 기각하는 이유가 실질적이다):**
- `AdminShell`의 메뉴는 `NavLink`로 활성 판정을 한다. `/admin` 항목만 `end: true`이고 나머지는 **하위 경로에서도 활성**이다. 상세를 `/admin/mypage/students/:id`에 두면 **학생 아카이브를 보는 동안에도 "마이페이지" 메뉴가 켜져 있다.** M-3처럼 형제 경로로 쪼개면 상세 화면에서 **어떤 메뉴도 활성이 아니게 되어** 관리자가 "내가 어디 있는지" 신호를 잃는다.
- 뒤로 가기 목적지가 경로에서 자명해진다(`/admin/mypage`).
- 데모에 외부 링크·북마크 개념이 없으므로 `/admin/students`를 남겨둘 이유가 없다. **리다이렉트를 만들지 않는다** — 죽은 경로를 유지하는 비용이 이득보다 크다.
- 메뉴 아이콘은 `ic-folder` → **`ic-user`**. 학생 셸의 마이페이지가 이미 `ic-user`라 대칭이 맞고, `ic-folder`는 학생 셸에서 "디지털 아카이브"가 쓰는 아이콘이므로 **마이페이지 안의 "담당 학생 아카이브" 섹션 헤더**로 내려 보내면 의미가 그대로 이어진다. **신규 아이콘 추가 0개.**

### N. 로그아웃 — **셸과 마이페이지 양쪽에 둔다** (중복 허용)

현재 상태를 먼저 확인했다:
- 관리자: 셸 우측 상단 아이콘 버튼(`AdminShell.jsx` 75줄, `.bell.logoutbtn`). **`.bell`에는 반응형 숨김 규칙이 없어 모바일에서도 남는다.** 768px 이하에서 사라지는 건 옆의 이름·코드 텍스트(`.nav .me .adminname`)뿐이다(`AdminShell.css` 322줄).
- 학생: 셸에는 없고 **마이페이지 안에만** 있다(`StudentMyPage.jsx` 48~50줄, `.ph-logout`).

| 안 | 판단 |
|---|---|
| N-1 (기각) 셸에서 빼고 마이페이지로 옮긴다 (학생과 동일) | **이 앱에서 로그아웃은 최다 사용 경로다** — 1인 시연의 핵심 동작이 학생↔관리자 계정 전환이다. 스캔 화면이나 프로그램 관리 도중 로그아웃하려면 매번 마이페이지로 이동해야 한다 |
| **N-2 (채택) 셸 유지 + 마이페이지에도 텍스트 버튼 추가** | 아래 근거 |
| N-3 (기각) 셸만 유지, 마이페이지에는 없음 | 계정 정보를 다루는 화면에 계정 종료 동작이 없는 건 어색하고, 학생 마이페이지와의 대칭도 깨진다 |

**채택 근거:**
- **발견성 보완.** 셸의 것은 라벨 없는 아이콘 버튼이고, **768px 이하에서 옆의 이름·코드가 사라지면 그 자리가 무엇인지 더 모호해진다.** 마이페이지의 텍스트 버튼("로그아웃")이 그 모호함을 메운다.
- **속도 유지.** 셸의 것을 남기면 어느 화면에서든 1클릭이다. 시연 리듬을 해치지 않는다.
- **중복 진입점의 위험이 낮다.** 로그아웃은 파괴적이지도, 되돌리기 어렵지도 않다(다시 로그인하면 끝). 중복을 피해야 하는 종류의 동작이 아니다.
- **학생 화면과 시각 대칭.** 양쪽 마이페이지가 같은 위치·같은 스타일(`.ph-logout` 계열)의 텍스트 버튼을 갖는다.
- 구현: **`signOut()`을 두 곳에서 각자 호출하지 말고** 학생 마이페이지의 `handleSignOut` 패턴(진행 중 `busy` 잠금)을 그대로 따른다. 셸 버튼은 **수정하지 않는다.**

### O. 관리자 본인 운영 요약 — **넣되, 지표가 아니라 링크로 만든다**

계정 카드가 이름·코드 두 줄뿐이면 화면 상단이 빈약하다. 그렇다고 요약을 얹으면 마이페이지가 대시보드처럼 보일 위험이 있다. **두 위험을 다 피하는 형태로 결정한다.**

**넣는 것:** 계정 카드 안 **한 줄 메타** — `내가 올린 프로그램 · 게시중 12 · 미게시 1` **(그 줄 전체가 `/admin/programs`로 가는 링크)**

| 검토 항목 | 결과 |
|---|---|
| 새 권한이 필요한가 | **아니다.** `programs_select_own_as_admin`으로 이미 조회된다. `fetchAdminPrograms(adminId)`가 이미 존재하므로 **새 서비스 함수 0개** |
| 원칙 1(게임화)과 충돌하는가 | **아니다.** 학생 데이터가 아니라 **본인이 만든 객체의 개수**다. 경쟁 상대도, 순위도, 희소성도 없다 |
| 원칙 6(3종 한정)과 충돌하는가 | **아니다.** ADR 0005 결정 7-5가 금지한 것은 "참여자 수·신청자 명단·출석률·학생 랭킹·학교 단위 통계"이고, 여기 해당하는 항목이 하나도 없다 |
| 대시보드화 위험 | **아래 가드로 막는다** |

**대시보드화를 막는 가드 (frontend 필수):**
- [ ] **별도 카드·타일·큰 숫자로 만들지 않는다.** 계정 카드 안의 **작은 메타 한 줄**이다
- [ ] 그 줄이 **클릭 시 `/admin/programs`로 이동**한다 → 읽는 계기판이 아니라 **가는 길**이 된다
- [ ] **그래프·추세·전월 대비·목표 대비·증감 화살표 금지**
- [ ] **"오늘 진행 프로그램" 수를 여기에 넣지 않는다** — 관리자 홈이 이미 담당한다(결정 7-5). 두 화면이 같은 숫자를 각자 계산하면 어긋난다
- [ ] **학생·참여 관련 숫자를 절대 넣지 않는다** (참여자 수·출석률·담당 학생 활동 건수). 데이터도 얻을 수 없다(결정 7-2(d))
- [ ] 조회 실패 시 그 줄만 조용히 생략한다 — **계정 정보와 담당 학생 목록이 이것 때문에 죽지 않는다**

### G. PDF는 왜 인쇄 CSS인가 (라이브러리 기각)

`package.json` 의존성은 현재 6개다. **라이브러리 추가는 근거가 필요하고, 여기서는 근거가 오히려 반대 방향이다.**

| 안 | 판단 |
|---|---|
| **G-1 (채택) `window.print()` + `@media print`** | 의존성 0. 텍스트가 **벡터로** 들어가 PDF에서 검색·복사된다(입시 제출 문서에서 이게 크다). 브라우저 인쇄 대화상자의 "대상: PDF로 저장"이 곧 PDF 생성이고, 기획서의 표현도 "PDF **확인**"이다. 페이지 나눔(`break-inside`)을 브라우저가 처리한다 |
| G-2 (기각) `jspdf` | **한글이 기본 폰트에 없다.** 폰트 파일(수 MB)을 base64로 임베딩해야 하고, 그 순간 번들과 라이선스 관리가 따라온다. 레이아웃을 좌표로 다시 짜야 해서 화면과 문서가 갈라진다 |
| G-3 (기각) `html2canvas` + `jspdf` | 화면을 **래스터 이미지로** 떠서 PDF에 붙이는 방식 — 글자가 이미지가 되고, 여러 장 넘어가면 잘림 처리를 직접 해야 한다. CSS 변수·`box-shadow` 재현 실패가 잦다 |

**구현 요구:**
- 전역 `@media print` 스타일을 새 파일 `src/styles/print.css`에 둔다(Vite에서 CSS import는 전역이므로, 규칙 전체를 `@media print` 안에 넣고 `.no-print` 클래스로 제어한다).
- 인쇄에서 숨긴다: `.nav`, `.bottomnav`, 화면 전용 버튼(`.no-print`), StackViz(이슈 5).
- 인쇄 시 배경색이 빠지는 브라우저 대비: 배지·카테고리 아이콘 배경에 `print-color-adjust: exact;`(+`-webkit-`).
- 활동 행에 `break-inside: avoid;` — 한 활동이 페이지 경계에서 반으로 잘리지 않게.
- 인쇄 직전 `document.title`을 `Accumu_활동아카이브_{이름}_{학번}_{todayISO()}`로 바꾸고 `onafterprint`에서 되돌린다 → 브라우저 기본 파일명이 그대로 쓸 만해진다.
- 문서 머리글(**인쇄에서만 보이는 블록**): "Accumu 활동 아카이브" / 학생 이름·학번 / **출력일 = `todayISO()`** / "QR 입·퇴장 인증이 완료된 활동만 기록됩니다" 한 줄.
- **`window.print()` 외의 경로를 만들지 않는다.** 서버 렌더·`service_role`·엣지 함수는 금지(결정 7-3).

## 사용자 시나리오

### 시나리오 1 — 마이페이지를 열고 담당 학생 아카이브로 들어간다
1. 관리자가 좌측 네비 **"마이페이지"**를 눌러 `/admin/mypage`로 들어온다.
2. 최상단에 **계정 카드** — 이름(정하윤), 관리자 코드(ADM-0001), 역할 배지(관리자). 그 아래 작은 한 줄: "내가 올린 프로그램 · 게시중 12 · 미게시 1"(누르면 프로그램 관리로 이동).
3. 그 아래 **"담당 학생 아카이브"** 섹션에 5명(신지훈·김도윤·이서연·박민준·최하은)이 이름·학번·진로 계열과 함께 뜬다. **점수·건수·순위는 어디에도 없다.**
4. 아직 활동 기록이 없는 학생에게는 회색 **"활동 기록 없음"** 배지가 붙어 있다(헛클릭 방지).
5. "신지훈(10718)"을 누른다 → `/admin/mypage/students/{id}`. **좌측 네비의 "마이페이지"는 계속 활성 상태다.**
6. 상단에 이름·학번·진로 계열, 그 옆에 **활동 기간(첫 활동 ~ 최근 활동)**과 **교내/교외 분포**가 뜬다. 어두운 패널 안에 최근 5개월 마일스톤 블록이 쌓여 있다. **계정 정보와 나머지 4명은 화면에서 사라진다**(결정 A).
7. 아래에 완료 활동이 최근순으로 나열된다 — 유형 아이콘, 제목, 주최, 날짜·시간, 진로 계열, 그리고 **참여 확인 일시**(퇴장 인증 시각).

### 시나리오 2 — PDF로 확인한다
1. 상세 우측 상단 "PDF로 확인"을 누른다 → 브라우저 인쇄 미리보기가 열린다.
2. 미리보기에는 좌측 네비·하단 탭바·버튼이 사라지고, 상단에 **"Accumu 활동 아카이브 / 신지훈 · 10718 / 출력일 2026-07-30"** 머리글이 붙어 있다.
3. "대상"을 **PDF로 저장**으로 바꾸고 저장하면 `Accumu_활동아카이브_신지훈_10718_2026-07-30.pdf`가 만들어진다.
4. 그 PDF 안의 글자는 **이미지가 아니라 텍스트**라 복사·검색이 된다.

### 시나리오 3 — 기록이 아직 없는 학생 (지금 DB의 실제 상태)
1. "최하은(10722)"을 누른다.
2. 화면이 죽거나 비어 있지 않고 **안내가 뜬다**: "아직 완료한 활동이 없습니다. 활동은 **QR 퇴장 인증이 끝난 뒤** 이곳에 자동으로 기록됩니다."
3. 진로 계열이 미설정(`career_interest = null`)이라 계열 자리에는 "계열 미설정"이 뜬다. **화면이 깨지지 않는다.**

### 시나리오 4 — 게시중단된 프로그램의 완료 기록
1. 관리자가 프로그램 관리에서 어떤 프로그램을 "내리기" 한다.
2. 담당 학생 아카이브를 다시 연다 → **그 활동 행이 사라지지 않는다.**
3. 데모에서는 전 프로그램이 `created_by = ADM-0001`이라 제목·날짜가 **정상 표시**된다(이슈 2 — 관리자는 학생보다 유리하다).
4. 만약 다른 관리자의 미게시 프로그램이라면 제목 자리에 **"게시가 중단된 프로그램"**이 뜨고, 날짜는 `exit_at` 기준으로 대체 표시된다. 그래도 행은 남는다.

### 시나리오 5 — 담당이 아닌 학생을 URL로 직접 열어본다
1. 주소창에 담당이 아닌 학생의 uuid를 넣는다.
2. RLS가 `profiles` 0행을 내려주고, 화면은 **"담당 학생이 아니거나 존재하지 않는 학생입니다"** + "마이페이지로 돌아가기" 버튼을 띄운다.
3. 활동 목록도 당연히 0건이다 — 프런트 필터가 아니라 **DB가 안 내려준 결과**다.

### 시나리오 6 — 계정을 바꿔 시연을 이어간다 (결정 N)
1. 관리자가 마이페이지 하단의 **"로그아웃"** 텍스트 버튼을 누른다 → 로그인 화면.
2. 학생 계정으로 로그인해 QR 왕복을 돌리고, 다시 관리자로 돌아온다.
3. 급할 때는 **어느 화면에서든 셸 우측 상단의 로그아웃 아이콘**을 눌러도 된다(같은 동작).

## 화면 구성 요소

### A. 관리자 마이페이지 (`/admin/mypage`)

**한 화면 = 계정 정보 + 담당 학생 목록. 위에서 아래로 2블록이다.**

#### A-1. 섹션 헤더
- eyebrow `My page` / 제목 **"마이페이지"** / 서브 "내 계정과 담당 학생 아카이브를 확인합니다"
- 학생 마이페이지의 `eyebrow="My page" title="마이페이지"`와 **문자열 단위로 대칭**을 맞춘다.

#### A-2. 계정 카드 (최상단)
- **아바타** — 이름 첫 글자(셸의 `.av`와 같은 표현)
- **이름**(크게) / **관리자 코드**(`ADM-0001`) / **역할 배지 "관리자"**(셸의 `.adminbadge` 재사용 — 새 배지 스타일을 만들지 않는다)
- **운영 요약 한 줄 (결정 O)** — `내가 올린 프로그램 · 게시중 N · 미게시 N`. **줄 전체가 `/admin/programs`로 가는 링크**다. 조회 실패 시 이 줄만 생략한다.
- **로그아웃 버튼 (결정 N)** — 카드 하단 또는 화면 최하단. 학생 마이페이지의 `.ph-logout` 계열 스타일. 진행 중에는 "로그아웃 중…"으로 잠근다.
- **표시하지 않는 것** — 포인트/지역화폐(관리자에게 개념이 없다), 비밀번호 변경·프로필 수정(`profiles` update 정책 0개 — 만들어도 동작하지 않는다), 계정 삭제, 알림 설정.

#### A-3. 담당 학생 아카이브 섹션
1. **섹션 소제목** — `ic-folder` + "담당 학생 아카이브" + 서브 "학생을 선택하면 활동 기록을 볼 수 있습니다"
2. **안내 한 줄**(목록 상단, 담백하게) — "**QR 입·퇴장 인증이 완료된 활동만** 아카이브에 기록됩니다."
   → 시연 첫 화면이 빈 상태일 수 있다는 사실을 화면이 스스로 설명한다(이슈 3).
3. **행 = `.adm-row` 확장** — 아바타(이름 첫 글자, `.av` 계열) + 이름 + 학번(`code`) + 진로 계열 칩(`TRACK[].name`) + 우측 `.chev`
4. **"활동 기록 없음" 배지** — 완료 활동이 0건인 학생에게만 회색 배지. **있는 쪽에는 아무 배지도 붙이지 않는다**(붙이는 순간 훈장이 된다).
5. **표시하지 않는 것 (원칙 1 가드 — 필수. 마이페이지 통합으로 중요도가 올라갔다)**
   - 완료 활동 **건수** / 포인트(`points_balance`·`points_total`) / 지역화폐(`currency_balance`)
   - 학생 간 정렬 옵션·랭킹·진척도 막대·"이번 달 최다 참여" 류 라벨
   - 목록 정렬은 **학번 오름차순 고정**(성취와 무관한 축). 정렬 UI를 만들지 않는다.
   - **[통합 구조 특유의 위험]** 바로 위 계정 카드에는 숫자 한 줄(결정 O)이 있다. **그 형식을 학생 행에 복사하지 말 것** — 관리자 본인의 개수는 자기 물건 세기이고, 학생 5명의 개수는 **비교표**다. 두 블록의 시각 언어를 의도적으로 다르게 유지한다(계정=한 줄 메타 링크 / 학생=이름·계열 중심 행).
6. **빈 상태** — 담당 매핑 자체가 0건일 때: "담당 학생이 아직 배정되지 않았습니다."
7. **"관리 = 조회다"** — 이 섹션에 **담당 학생 추가/삭제 버튼을 만들지 않는다.** 아래 "스코프 아님" 참고.

### 이슈 1 — `point_transactions`는 정책이 0개다 (**이 스펙의 핵심 쟁점**)

ADR 0005 결정 3-6은 못박았다: **아카이브의 포인트는 `programs.points`가 아니라 `point_transactions.amount`(지급 시점 스냅샷)를 읽어야 한다.** 프로그램 관리에서 `points`가 사후 수정될 수 있기 때문이다.

그런데 결정 2-1이 **`point_transactions`의 정책을 0개(select 포함)로 두었다.** 관리자도 학생도 이 테이블을 읽을 수 없다. 즉 **"올바른 포인트 값을 아카이브에 표시할 방법이 현재 존재하지 않는다."** 선택지는 셋뿐이다.

| 안 | 결과 | 판단 |
|---|---|---|
| **D-1 (채택) 포인트를 아카이브에 표시하지 않는다** | backend 0건 유지. 원칙 4에 정면으로 부합 | **채택** |
| D-2 `programs.points`를 대신 읽는다 | 조회는 되지만 **결정 3-6이 금지한 값**이다. 관리자가 포인트를 수정한 뒤에는 **틀린 숫자**가 된다 | **기각** |
| D-3 `point_transactions`에 관리자용 select 정책을 연다 | 올바른 값을 얻지만 **새 정책 = backend 작업**이고, ADR 0005가 의도적으로 닫아둔 원장 테이블을 **관리자에게 처음 여는** 결정이 된다 | **기각(질문 K)** |

**D-1을 채택하는 적극적 근거 (backend 0건은 결과이지 이유가 아니다):**

1. **원칙 4가 이 화면에서 가장 강하게 적용된다.** "포트폴리오가 포인트보다 먼저 보여야 한다"의 극단이 아카이브다. 아카이브는 **활동 기록 문서**이고, 멘토가 담당 학생과 상담하며 볼 정보는 "무엇을 얼마나 했는가"이지 "얼마를 벌었는가"가 아니다.
2. **포인트를 보여줄 화면이 따로 있다.** 학생 마이페이지(포인트 내역·지역화폐 전환)가 그 몫이고, 거기서 `point_transactions_select_own`을 여는 것이 ADR 0005가 예고한 자리다. **관리자 아카이브가 그 문을 대신 열 이유가 없다.**
3. **5명 목록에서 포인트는 곧 순위다.** 합계 포인트(`points_total`)는 **정책이 이미 열어준 값**이라 마음만 먹으면 5명을 나란히 세울 수 있다. 원칙 1 가드가 정확히 이걸 금지한다. **아예 select 하지 않는 것이 가장 확실한 준수 방법이다.**
4. **D-2는 "틀린 숫자를 보여주는 것"이다.** admin-programs 스펙 F-3이 같은 상황에서 내린 판단("틀린 숫자를 보여주는 것은 안 보여주는 것보다 나쁘다")을 그대로 적용한다.

→ **`archiveService`의 select 목록에서 `points` 계열 컬럼을 전부 뺀다.** 화면 규율이 아니라 **쿼리로** 표현한다.

### 이슈 2 — 관리자 쪽 게시중단 열화는 학생 쪽보다 **약하다** (확인 결과)

결정 7-4는 학생 화면 기준으로 "프로그램 정보 표시가 깨진다"고 적었다. **관리자 쪽을 확인한 결과는 다르다.**

| 프로그램 | 관리자가 `programs` 행을 읽을 수 있는가 |
|---|---|
| 게시중(`is_published = true`) | **읽는다** (`programs_select_published`) |
| **본인이 만든 미게시** | **읽는다** (`programs_select_own_as_admin`, 게시 여부 무관 — 결정 7-1) |
| 다른 관리자의 미게시 | 못 읽는다 |
| `created_by IS NULL`인 미게시 | 못 읽는다 |

- **데모에서는 프로그램 20건 + 앱에서 등록한 것 전부가 `created_by = ADM-0001`이다.** 따라서 **관리자 아카이브에서는 게시중단 열화가 사실상 발생하지 않는다** — 관리자는 자기가 내린 프로그램의 제목·날짜를 계속 본다.
- **그래도 방어를 뺄 수 없다.** 다중 관리자 상황(설계상 성립하게 만들어 둔 축)과 `created_by IS NULL` 행에서 실제로 발생하고, 무엇보다 **"못 찾으면 화면이 죽는다"가 가장 나쁜 실패**다. 위 "방어적 렌더" 체크리스트는 전부 필수다.
- 검증 방법: SQL로 어떤 프로그램의 `created_by`를 다른 uuid로 바꾼 뒤 `is_published = false`로 내리고 아카이브를 연다 → 그 활동 행이 **대체 문구로 남아 있어야** 한다.

### 이슈 3 — 빈 상태가 **지금 DB의 실제 상태다** (시연 첫 화면 리스크)

`participations`/`point_transactions`는 시드하지 않는다(결정 8-3, 케빈 확정). 즉 **QR 왕복을 돌린 계정에만 기록이 있고 나머지 학생은 빈 화면이다.** 시연 당일 새 프로젝트에 시드만 돌린 상태라면 **5명 전원이 빈 화면**이다.

**가짜 데이터를 넣지 않는다는 확정은 유지한다.** 대신 화면과 절차로 흡수한다:

1. **목록의 "활동 기록 없음" 배지** — 관리자가 빈 학생을 눌러보는 헛클릭을 없앤다. (담당 5명 전원의 `completed` 참여를 **한 번의 쿼리로** 가져오면 알 수 있다 — 아래 조회 설계)
2. **목록 상단 안내 한 줄** — "QR 입·퇴장 인증이 완료된 활동만 기록됩니다." 빈 화면이 **버그가 아니라 설계**임을 화면이 스스로 말한다.
3. **상세 빈 상태 문구** — "아직 완료한 활동이 없습니다. 활동은 QR 퇴장 인증이 끝난 뒤 이곳에 자동으로 기록됩니다."
4. **README/시연 메모에 순서를 명시한다** (frontend-agent 작업 항목):
   > 아카이브를 시연하기 전에 **학생 계정(10718 권장)으로 QR 왕복을 2~3건 완료**해 둘 것. 아카이브는 `completed` 참여만 표시하며, 그 데이터는 QR 퇴장 인증이 처음 만든다.
   > 서로 다른 **월·교내/교외**의 프로그램을 섞으면 마일스톤과 분포 요약이 함께 살아난다.
5. **10718(신지훈)을 목록 첫 행에 두는 인위적 조작을 하지 않는다** — 학번 오름차순이면 자연스럽게 첫 행이다(10718 < 10719 < …). 운이 좋은 게 아니라 확인한 사실이다.

### 이슈 4 — 정책이 컬럼을 다 열지만, **select 목록으로 좁힌다**

결정 7-2(c)가 수용한 대로 정책은 담당 학생 행의 모든 컬럼을 연다. **열려 있다는 것과 보여준다는 것은 다르다.**

| 컬럼 | 이번 화면 |
|---|---|
| `id`, `code`, `name` | 조회·표시 |
| `career_interest` | 조회·표시 (진로 축은 이 앱의 핵심 정보이고 민감 정보가 아니다) |
| `points_balance`, `points_total`, `currency_balance` | **조회하지 않는다** (이슈 1) |
| `role`, `created_at` | 조회하지 않는다 (쓸 곳이 없다) |

- 이 규율은 admin-programs 스펙이 `popularity`를 페이로드에서 뺀 것과 같은 계열이다: **화면에 쓰지 않는 값을 네트워크에 싣지 않는다.**
- 다만 **이것이 보안 경계가 아니라는 점을 분명히 한다.** 관리자가 개발자도구로 `select *`를 쏘면 값은 온다. 경계는 여전히 RLS의 행 경계(담당 5명)이고, **컬럼 선택은 "화면이 무엇을 정보로 취급하는가"의 선언**이다.

### 이슈 5 — StackViz는 **어두운 배경 전용**이고 인쇄·모바일에서 사라진다 (재사용 시 함정)

`src/styles/StudentHome.css` 26~39줄을 확인한 결과:

- 빈 블록 배경이 `rgba(255,255,255,.14)`, 캡션 색이 `#9FB0C9` → **흰 카드 위에 그대로 놓으면 빈 블록과 캡션이 보이지 않는다.**
- `@media (max-width: 600px) { .stackviz { display: none } }` → **모바일에서 자동으로 사라진다.**
- `animation: grow ... both` → `both`라서 지연 시작 전 상태가 유지된다. **인쇄 렌더에서 블록이 `opacity: 0`으로 굳을 수 있다.**

→ 요구사항:
- 상세 상단에 **`.arc-hero`(학생 홈 `.hero`와 같은 어두운 계열 패널)**를 두고 그 안에 StackViz를 넣는다. `StackViz.jsx`와 `StudentHome.css`의 `.stackviz` 규칙은 **수정하지 않는다**(학생 홈과 공유하는 자산이라 건드리면 양쪽이 어긋난다).
- **인쇄에서는 `.arc-hero`를 통째로 숨긴다.** 어두운 대형 배경은 인쇄에 부적합하고, 애니메이션 문제도 함께 사라진다. 인쇄에서는 요약 블록(활동 기간·분포)이 같은 정보를 텍스트로 전달한다.
- 600px 이하에서 StackViz가 사라져도 **요약 블록이 남아 화면이 비지 않는다**(요약을 StackViz 안에 넣지 말 것).

### 조회 설계 (`src/lib/archiveService.js`)

```js
// 목록: mentor_students / profiles / participations 를 병렬 3쿼리로 읽고 클라이언트에서 결합한다.
//   - embed·뷰 금지 (정의자 권한 함정 — ADR 0003 6번 / ADR 0004 5번)
//   - participations 는 RLS 가 "담당 5명 + completed" 만 내려주므로, 조건 없이 읽어도
//     정확히 필요한 집합이 온다. 여기에 클라이언트 필터를 덧붙이지 않는다(경계의 소유자를 흐린다).
//   - points_* / currency_balance 는 select 목록에 없다 (이슈 1·4)
const STUDENT_FIELDS  = 'id, code, name, career_interest';
const PART_FIELDS     = 'id, student_id, program_id, exit_at';
const ARCHIVE_PROGRAM_FIELDS = 'id, category, title, org, date, time, career_track';
```

- `fetchMentoredStudents()` → `{ students: [...], hasActivity: Set<student_id> }`
  `hasActivity`는 위 `participations` 조회 결과의 `student_id` 집합이다. **건수를 세지 않고 집합만 만든다** — 숫자를 만들지 않으면 화면에 새어나갈 수도 없다(결정 B).
- `fetchStudentArchive(studentId)` → `{ student, activities: [{ participation, program|null }] }`
  상세 직접 진입을 지원해야 하므로 목록 상태에 의존하지 않고 자체 조회한다.
- 모든 쿼리에 `.limit(200)` 안전 상한(기존 관례).
- **어떤 쿼리도 `point_transactions`를 참조하지 않는다.**

**계정 카드가 추가하는 조회 (결정 O)**
- **`archiveService`에 넣지 않는다.** 프로그램 개수는 아카이브와 무관한 축이므로 기존 `programService.fetchAdminPrograms(adminId)`를 그대로 호출한다 — **새 서비스 함수 0개, 새 필드 0개.**
- 계정 정보(이름·코드·역할)는 `AuthContext`의 `profile`에 이미 있다. **`profiles`를 다시 조회하지 않는다.**
- 이 조회는 **담당 학생 목록과 독립적으로 실패할 수 있어야 한다.** 하나의 `Promise.all`로 묶어 전부 실패시키지 말 것 — 운영 요약 한 줄 때문에 아카이브가 안 뜨면 주객이 전도된다.

## 스코프 아님 (Out of scope)

- **포인트 표시(건별·합계)** — 이슈 1 / 결정 D. 표시하려면 `point_transactions` 정책이 필요하고 그건 backend 작업이다.
- **`point_transactions_select_own`(학생 포인트 내역)** — ADR 0005가 **마이페이지 스펙**의 자리로 예약했다. 이 스펙이 먼저 열지 않는다.
- **학생 간 비교·정렬·랭킹·진척도** — 원칙 1 가드(결정 7-2(c), frontend 필수). 구조(결정 A)로도 차단된다.
- **완료 건수를 목록에 표시** — 결정 B. 5명이 나란히 놓이는 유일한 화면이다.
- **신청만 하고 안 간 활동(`applied`/`entered`) 표시** — 결정 7-2(d). **DB가 안 내려준다.** 프런트 필터로 되살릴 수 없다.
- **관리자의 아카이브 쓰기(코멘트·평가·확인 도장·활동 추가)** — `participations`/`profiles`에 관리자 update 정책 0개(결정 2-1). 만들어도 동작하지 않는다.
- **담당 학생 매핑 추가·삭제·이동 (중요 — 명시)** — **"관리"는 조회·열람이지 매핑 편집이 아니다.**
  - `mentor_students`에 **insert/update/delete 정책이 0개**이고, ADR 0005 결정 7-2가 이를 **의도적으로** 열지 않았다("매핑 변경 UI 없음. 시딩이 유일한 입력 경로" — 마이그레이션 795줄 주석).
  - CLAUDE.md 10장의 표현도 **"담당 학생 5명 아카이브 조회 + PDF 확인"**이지 배정 관리가 아니다.
  - **이 매핑은 이제 권한 경계 자체다**(결정 7-2(f)). 앱에서 편집 가능하게 만든다는 것은 **관리자가 자기가 볼 수 있는 학생을 스스로 늘릴 수 있게 만든다**는 뜻이다 — 담당 5명 경계가 무의미해진다.
  - **화면에 추가/삭제/검색 버튼을 만들지 않는다.** 만들어도 403으로 실패한다. 매핑 변경이 필요하면 `seed-accounts.mjs`(service_role) 또는 SQL 콘솔에서 한다.
  - **마이페이지 통합으로 이 항목의 유혹이 커졌다** — "내 페이지에 내 담당 학생 목록이 있으니 편집도 되어야 할 것 같은" 인상이 생긴다. 되지 않는다.
- **관리자 프로필 수정 (이름·코드·비밀번호 변경)** — `profiles` update 정책 0개(결정 2-1). 계정 카드는 **읽기 전용**이다. 계열 선택 UI는 학생 전용이며 그조차 definer RPC가 필요하다(ADR 0005 "향후 변경").
- **담당 5명 일괄 PDF / 학년·학교 단위 출력** — 결정 H + CLAUDE.md 2장 6번(학교 단위 대시보드 금지).
- **PDF 라이브러리 도입, 서버 렌더, 워터마크·전자서명·QR 검증코드 삽입** — 결정 G / 결정 7-3. **`service_role` 금지.**
- **별점·한줄평 표시** — `reviews` 테이블이 아직 없다. 아카이브 확장 스펙 몫.
- **학생 본인 아카이브 화면(`/student/archive`)** — 별도 스펙. `participations_select_own`이 이미 권한을 주므로 backend 0건이고, **이번에 만드는 요약·활동 목록 표현을 재사용할 수 있게** 컴포넌트를 학생 id 비의존으로 짜두면 좋다(의무 아님).
- **1365 등 외부 봉사 실적 연동** — CLAUDE.md 11장.
- **아카이브 검색·필터·기간 선택·페이징** — 데모 규모(학생 5명 × 활동 수 건). ADR 0003 6번 판단 유지.

## 절대 원칙 체크

- **게임화/사행성: 영향 없음.** 랜덤·뽑기·베팅·아바타·레벨 없음.
  - **가드 (frontend 필수 준수):**
    - [ ] **담당 학생 목록에 건수·포인트·순위·진척도 숫자가 하나도 없다** (결정 B)
    - [ ] 학생 간 정렬·비교·"이번 달 최다" 류 라벨 없음. 정렬은 **학번 고정**
    - [ ] StackViz에 숫자·레벨·게이지·"N개 달성" 라벨을 붙이지 않는다 (결정 5 가드 그대로)
    - [ ] 요약 블록에 **퍼센트·달성률·목표 대비·등급**을 쓰지 않는다 — 사실 기술(`교내 3 · 교외 2`)만
    - [ ] **계정 카드의 숫자 표현(결정 O)이 학생 목록으로 번지지 않는다** — 아래 통합 구조 항목
  - **[단일 학생 상세의 건수가 원칙 1을 위반하지 않는 이유 — 케빈 확정 L-1]** 원칙 1이 금지하는 것은 **경쟁·서열·희소성 연출**이다. 한 화면에 학생이 1명뿐이라 비교 대상이 존재하지 않고, 활동 건수는 생활기록부에 준하는 **사실 기술**이다. 비교가 발생할 수 있는 유일한 자리(5명 목록)에서는 숫자를 전부 뺐다.
  - **[마이페이지 통합이 만든 새 위험 — 이번 갱신의 핵심 가드]**
    계정 정보와 담당 학생 5명이 한 화면에 놓이면서 이 화면은 시각적으로 **"내 담당 현황판"**처럼 읽힐 여지가 생겼다. 게다가 바로 위 계정 카드에는 **숫자 한 줄이 실제로 존재한다**(결정 O: 게시중 N · 미게시 N). 그 형식을 아래 학생 행으로 복사하면 **한 번의 복붙으로 원칙 1 가드가 무너진다.**
    - **관리자 본인의 개수** = 자기가 만든 물건 세기. 비교 대상 없음. 허용.
    - **학생 5명의 개수** = 나란히 놓인 순간 **비교표**. 금지.
    - → 두 블록의 시각 언어를 **의도적으로 다르게** 유지한다(계정 = 작은 메타 링크 한 줄 / 학생 = 이름·계열 중심의 행). "일관성"을 이유로 통일하지 말 것.
    - → 데이터 층에서도 막혀 있다: `fetchMentoredStudents()`는 **건수를 세지 않고 `Set`만 만든다**(조회 설계). 숫자를 만들지 않으면 새어나갈 수도 없다.
- **관리자 기능 범위: 3종 내 (확장 없음).** 이 화면은 3종 중 **3번(담당 학생 5명 아카이브 조회 + PDF 확인)** 그 자체이며, 계정 정보는 셸에 이미 있던 것을 옮긴 것이다.
  - [ ] **메뉴가 4개(홈 + 3종) 그대로다** — 마이페이지는 추가 항목이 아니라 "담당 학생" 자리의 개명이다(위 "구조 변경")
  - [ ] **관리자가 할 수 있는 동작이 하나도 늘지 않았다** — 새로 생긴 것은 로그아웃 진입점 1개(기존 동작)와 읽기 전용 표시뿐
  - [ ] 학교 단위 대시보드·전교생 통계 없음 — **데이터도 얻을 수 없다**(결정 7-2(d))
  - [ ] 다중 관리자 관리 UI 없음
  - [ ] **담당 매핑 추가/삭제 UI 없음** — "관리 = 조회"이며 정책이 0개다("스코프 아님" 참고)
  - [ ] 담당이 아닌 학생이 목록에 뜨지 않는다 (RLS 행 경계)
  - [ ] **이 화면이 관리자에게 새 조회 권한을 하나도 주지 않는다** (새 정책 0건). 계정 정보는 `profiles_select_own`, 운영 요약은 `programs_select_own_as_admin` — **둘 다 이미 쓰고 있던 권한이다**
- **포인트/지역화폐 시뮬레이션 원칙: 유지.**
  - [ ] 이 화면에 `profiles.points_*` / `currency_balance` / `point_transactions`를 **조회하는 코드조차 없다**
  - [ ] 포인트를 지급·차감·전환하는 경로 없음. 지급은 여전히 `verify_participation_qr()`뿐
  - 실제 결제·계좌 연동 없음.
- **포인트 < 포트폴리오 (원칙 4): 이 화면에서 가장 강하게 준수된다.**
  - [ ] 아카이브에 **amber가 한 곳도 등장하지 않는다**(포인트를 표시하지 않으므로)
  - [ ] 시각 위계 = 성장/활동(brand blue·indigo) 100%
  - [ ] PDF에도 포인트가 없다 — 입시 제출 문서에 남는 것은 **활동 기록**이다
- **진로 중심 (원칙 2): 유지.** 표시 축은 활동 유형 8종 + 진로 계열 5종. 자습·성적·문제풀이 지표 없음.
- **QR 2회 인증 (원칙 5): 훼손 없음.** 이 화면에 참여 상태를 바꾸는 경로가 0개다.
  - [ ] "관리자가 수동으로 참여 완료 처리" 같은 우회 버튼을 만들지 않는다 — 정책상 동작하지도 않는다
  - **오히려 이 화면이 2회 인증의 결과물이다**: 아카이브에 뜨는 활동은 **전부 퇴장 인증을 통과한 것**이고, 그래서 "빈 화면"이 정직한 상태다(이슈 3).
- **GPS: 스코프 제외 유지.** 위치 정보 표시·수집 없음.
- **디자인: 초록 계열 금지 / 이모지 금지 / duotone SVG.** 신규 아이콘 2종(`ic-print`, `ic-arrow-left`)도 이 규칙을 따른다.
- **개인정보 관점 (이 스펙에서 새로 짚는 것)**
  - [ ] 학생의 **미완료 신청 내역이 관리자에게 보이지 않는다** — DB 경계(7-2(d))이자 의도된 사생활 보호
  - [ ] 학생의 **잔액 정보를 화면에도 페이로드에도 싣지 않는다** (이슈 4)
  - [ ] PDF에 학번 이상의 식별정보(연락처·주소 등)를 넣지 않는다 — 애초에 DB에 없다

## 열린 질문 원문 (결정 근거 — **2026-07-30 전부 해소**)

> ~~"추천안대로"라고 답하면 K-1 / L-1로 확정합니다.~~ → **케빈이 둘 다 추천안대로 확정.** 아래는 결정 근거 원문이며 다시 고를 선택지가 아니다.

### K. 아카이브에 포인트를 표시할까 → **K-1 확정 (표시하지 않는다)**

- **K-1 (채택): 표시하지 않는다.**
  backend 0건 유지, 원칙 4에 정면 부합, 5명 비교 위험 원천 차단. 포인트는 학생 마이페이지가 담당한다.
- K-2: `profiles.points_total`(누적)만 상세 헤더에 1줄.
  정책이 이미 열어준 값이라 backend 0건은 유지되지만, **활동별 금액과 합계가 어긋날 수 있고**(전환이 생기면 더) 5명 목록으로 새어나가기 쉽다. **비추천.**
- K-3: 활동별 지급 포인트까지 표시.
  올바른 값(`point_transactions.amount`)을 읽으려면 **새 RLS 정책 = backend 작업**이 발생하고, ADR 0005가 닫아둔 원장 테이블을 관리자에게 처음 여는 결정이 된다. `programs.points`로 대신하는 것은 결정 3-6이 금지한다. **비추천.**

### L. 상세 화면의 활동 건수·분포 숫자를 노출할까 → **L-1 확정 (노출한다)**

- **L-1 (채택): 단일 학생 상세에서만 `교내 3 · 교외 2` / `방과후 2 · 봉사활동 2` 형태로 표시.**
  한 화면에 학생이 1명뿐이라 비교 대상이 없고, 포트폴리오 문서에 요약이 없으면 PDF가 활동 나열뿐이 된다. 게이지·퍼센트·달성률은 금지.
- L-2 (미채택): 숫자 없이 활동 목록만.
  원칙 1에 가장 안전하지만 **PDF가 요약 없는 나열**이 되고, 인쇄에서 StackViz를 숨기므로(이슈 5) 문서에 한눈에 보이는 요약이 사라진다.
- ※ **담당 학생 목록(5명)에 숫자를 넣지 않는 것은 질문이 아니라 결정이다** — 원칙 1 가드가 명시적으로 금지한 자리다. L-1 확정 후에도 목록은 그대로이며, **마이페이지 통합으로 이 구분이 더 중요해졌다**(절대 원칙 체크 참고).

### 2. qa-agent
- **"권한 점검" 9항목**을 anon 키로 직접 뚫어볼 것. 특히 **`point_transactions` 0행**(이슈 1이 실재함)과 **`participations`에 `applied`/`entered`가 안 나오는 것**(7-2(d))이 핵심이다.
