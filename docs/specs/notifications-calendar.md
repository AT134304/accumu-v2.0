# 인앱 알림 + 활동 캘린더

## 영향 범위
**학생 공통 셸의 상단 아이콘 2개.** 다른 화면은 손대지 않는다.
`docs/specs/student-home.md` **확정 C(아이콘 + 빈 상태 팝업 껍데기)를 이 문서가 대체한다.**

> **갱신 이력**
> - 2026-08-06 구현. 마이그레이션 `20260806120000_add_notifications.sql`.

---

## 배경

CLAUDE.md 5장 데이터 모델에서 **유일하게 구현되지 않은 테이블이 `notifications`** 였다.
종·캘린더 아이콘은 눌리지만 열리는 것은 빈 상태 문구뿐이었고, 그 상태가 스펙 3개를 거쳐 남아 있었다
(`student-programs.md` E-1 → `qr-dual-auth.md` → 지금).

미뤄진 이유도 기록돼 있다: 신청만 있던 시점에는 알릴 사건이 없었고(E-1), 근거 없는 dot 을 띄우지
않으려고 조회조차 하지 않았다(확정 C). **지금은 신청·입장·퇴장·게시가 전부 동작하므로 알릴 사건이 있다.**

## 결정

| # | 항목 | 결정 |
|---|---|---|
| **A** | 알림 저장 | **실제 테이블**(`notifications`). 파생 조회로 대신하지 않는다 — `is_read` 는 파생할 수 없다 |
| **B** | 누가 만드는가 | **DB 트리거만.** insert 정책 0개. 알림은 서버가 관측한 사실이지 사용자가 쓰는 데이터가 아니다 |
| **C** | 읽음 처리 | **RPC `mark_notifications_read()` 로만.** update 정책도 0개(`profiles` 와 같은 규율) |
| **D** | 관리자 알림 | **없다.** `student_id` 축뿐. 알림함을 주면 관리자 기능이 4번째가 된다(원칙 6) |
| **E** | 캘린더 저장 | **새 테이블 없음.** `participations` + `programs` 를 날짜축으로 다시 그린 것뿐이다 |
| **F** | 기준일 | **언제나 실제 오늘.** 프로토타입의 `TODAY_ISO='2026-07-02'` 하드코딩을 재현하지 않는다 |

### 알림 종류 4가지

프로토타입 `NOTIF_IC`(1139줄) 4종을 이 앱의 실제 사건에 맞췄다.

| type | 사건 | 문구 | 부가 줄 |
|---|---|---|---|
| `new` | 프로그램 게시(올리기) | 새 프로그램이 등록되었어요 | 제목 · 주최 |
| `apply` | 학생이 신청 | 참석 신청이 완료되었어요 | 제목 · 날짜 |
| `enter` | QR 입장 인증 | 입장 인증이 완료되었어요 | 제목 |
| `exit` | QR 퇴장 인증 | 참여가 완료되었어요 | 제목 · +N P 적립 |

프로토타입의 `qr`("참여 QR이 발급되었습니다")은 대응이 없다 — 이 앱은 신청 시점이 아니라 학생이
필요할 때 QR 을 발급하므로, 그 자리를 `apply` 가 대신한다.

**`exit` 문구에서 포인트를 앞세우지 않는다**(절대 원칙 4). "참여가 완료되었어요"가 제목이고
적립액은 부가 줄이다.

### CLAUDE.md 5장과의 차이 — 의도된 확장 2개

문서의 필드는 `(id, student_id, type, message, is_read, created_at)` 이다. 여기에 둘을 더했다.

- `detail` — 두 번째 줄. 프로토타입 알림도 title + body 2줄이다(1147줄).
- `program_id` — 어떤 프로그램의 알림인지. 문구를 파싱하지 않고 화면이 맥락을 안다.

한 줄에 욱여넣으면 화면이 `message` 를 잘라 쓰게 된다 — 그게 더 나쁜 결합이다.

## 화면

### A. 알림 팝업
- 종 아이콘에 **안 읽은 개수 배지**(`.ndot`, 9 초과는 `9+`)
- 목록: 종류별 아이콘 + 문구 + 부가 줄 + 상대 시각(`방금 전`/`N분 전`/`어제`/`M월 D일`)
- **"모두 읽음"** 버튼. 안 읽은 것이 없으면 비활성
- **자동 읽음 처리를 하지 않는다.** 프로토타입은 팝업을 열고 1초 뒤 전부 읽음 처리했지만(1156줄),
  열자마자 사라지는 표시는 "내가 뭘 놓쳤는지" 확인할 기회를 빼앗는다

### B. 활동 캘린더 팝업
- 월 그리드(일~토) + 활동 있는 날에 **계열 색 점**(최대 3개) + 오늘 강조
- 헤더에 이전/다음 달 이동. **기본값은 실제 오늘의 달**
- 아래에 그 달의 활동 목록: 계열 아이콘 + 제목 + 날짜·시간 + 상태 배지
- 상태 3종: `참여 예정`(amber) / `참석 중`(indigo) / `참여 완료`(brand)

## 절대 원칙 체크

- **게임화/사행성**: 연속 참여일·달성률·월간 목표·순위를 **그리지 않는다.** 캘린더의 점은 계열 색이지
  성취 표시가 아니고, 배지는 사실 3종이다. 그런 스타일 규칙이 CSS 에도 없다.
- **진로·커리어 중심**: 알림·캘린더 모두 프로그램 참여 축이다. 학업 기록이 들어갈 자리가 없다.
- **포인트 시뮬레이션**: 알림은 `points_*` 를 **읽지도 쓰지도 않는다.** `exit` 문구의 금액은
  `programs.points` 를 옮긴 것이고, 지급은 여전히 `verify_participation_qr()` 안에서만 일어난다.
- **포트폴리오 우선**: `exit` 알림의 제목이 "참여가 완료되었어요"다. 적립액은 부가 줄.
- **QR 2회 인증**: 입장·퇴장이 **각각** 알림을 만든다. 단계를 합치지 않는다.
- **관리자 기능 3종 한정**: 관리자에게 알림이 없다. 동작 0개 추가.

## 스코프 아님

- **푸시 알림(백그라운드)** — CLAUDE.md 11장.
- **알림 개별 읽음/삭제** — "모두 읽음" 하나면 데모에서 충분하고, 행마다 쓰기 경로를 여는 값이 없다.
- **실시간 구독(Realtime)** — 팝업을 열 때 조회한다. 셸이 상시 구독하면 모든 학생 화면이 소켓에 묶인다.
- **캘린더에서 신청/취소** — 캘린더는 읽기 전용이다. 쓰기는 프로그램 화면이 소유한다.
- **관리자 캘린더** — 관리자 홈의 "오늘 진행 프로그램"이 이미 그 역할이다.

## 알려진 열화

- **`new` 알림은 게시 1회당 학생 수만큼 행이 생긴다.** 데모 규모(5~6명)에서는 무시할 수 있고,
  "관리자가 올리면 학생 화면에 뜬다"가 시연에서 가장 잘 보이는 연결이라 감수한다.
  **학생이 수천 명이면 이 구조는 성립하지 않는다** — 그때는 "게시 이벤트 1행 + 읽음 상태 분리"로 바꿔야 한다.
- **게시중단된 프로그램의 캘린더 항목은 제목이 `게시가 중단된 프로그램` 으로 뜬다**
  (학생이 select 할 수 없다 — ADR 0005 결정 7-4의 알려진 틈).

## 인수 조건

- [ ] 관리자가 프로그램을 **올리면** 학생 종 아이콘에 배지가 생긴다 (내리기는 알림을 만들지 않는다)
- [ ] 학생이 신청하면 `apply` 알림이 생긴다
- [ ] QR 입장 인증 후 `enter`, 퇴장 인증 후 `exit`(+N P 적립) 알림이 각각 생긴다
- [ ] "모두 읽음"을 누르면 배지가 사라지고, 팝업을 다시 열어도 읽음 상태가 유지된다
- [ ] **다른 학생의 알림이 조회되지 않는다** (RLS `notifications_select_own`)
- [ ] **개발자도구로 `notifications` insert/update 를 시도하면 거부된다** (정책 0개)
- [ ] 캘린더 기본 표시 달이 **실제 오늘의 달**이고 오늘 칸이 강조된다
- [ ] 활동이 있는 날에 계열 색 점이 뜨고, 그 달 목록에 상태 배지가 맞게 표시된다
- [ ] 활동이 없는 달로 이동하면 빈 상태 문구가 뜬다
- [ ] 관리자 화면에는 종·캘린더 아이콘이 **없다**
