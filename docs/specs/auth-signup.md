# 회원가입 — 학생(학교/개인) + 관리자(초대코드)

## 영향 범위
**로그인 화면 + 신규 가입 화면 + 양쪽 마이페이지 1블록씩.** 기존 로그인 흐름(ADR 0002)은 **변경 0건**이다.
※ **backend 작업이 확실히 있다.** 이 앱에서 `profiles` 행을 **앱이 직접 만드는 최초의 경로**이고, 지금까지 계정 생성은 `service_role` 시딩뿐이었다(`scripts/seed-accounts.mjs`).
※ 자매 문서: `docs/adr/0008-signup-invite-codes-and-role-provisioning.md`(권한 경계 설계).

> **갱신 이력**
> - 2026-07-31 초안 + **케빈 확정** — 가입 대상(학생+관리자), 초대코드 형태(관리자별 고정), 개인→학교 전환(허용) 확정.
> - 2026-07-31 **개정(케빈 요청)** — **개인 계정은 학번을 받지 않는다**(아이디 = 이메일 또는 소셜 계정, `profiles.code`는 서버가 `P-XXXXXX` 발급). **소셜 로그인 3종(Google · Kakao · Facebook) 추가.** 아래 "결정 E·F" 신설. 마이그레이션 `20260731140000`.

---

## 배경 / 왜 필요한가

지금까지 모든 시연은 **시딩된 6개 계정**(학생 5 + 관리자 1)으로만 진행했다. 그래서 심사자가 "직접 가입해서 써볼 수 있나요?"라고 물으면 보여줄 화면이 없다. 회원가입은 기능 하나가 아니라 **"이 앱이 계정을 스스로 만들 수 있는가"**라는 질문이고, 그 답이 지금은 "아니오"다.

동시에 이 기능은 **이 프로젝트에서 가장 위험한 쓰기 경로**다. 앱의 모든 권한 경계가 `profiles.role` 한 컬럼에 걸려 있기 때문이다:

- `role = 'admin'` 이면 → 프로그램 등록/게시, QR 스캔으로 포인트 지급, 담당 학생 아카이브 조회가 전부 열린다.
- 즉 **가입 폼이 role 을 정할 수 있으면 누구나 관리자가 된다.** 이것이 이 스펙의 무게중심이며, 화면보다 먼저 결정해야 하는 부분이다.

## 케빈 확정 (2026-07-31)

| # | 질문 | 확정 |
|---|---|---|
| **A** | 가입 대상 | **학생 + 관리자.** 단 관리자는 **사전 발급된 관리자 초대코드**가 있어야 한다 |
| **B** | 학생 계정 종류 | **학교 계정 / 개인 계정 2가지.** 학교 = 관리자의 초대코드로 가입해 그 관리자와 연동, 개인 = 어디에도 소속되지 않음 |
| **C** | 학교 초대코드 형태 | **관리자별 고정 코드 1개.** 관리자 마이페이지에 **표시만** 한다(생성·만료·회수 버튼 없음) |
| **D** | 개인 → 학교 전환 | **허용.** 학생 마이페이지에서 코드를 입력하면 연동된다. **되돌리는 경로(소속 해제)는 만들지 않는다** |

| **E** | 개인 계정 아이디 | **학번을 받지 않는다.** 이메일 + 비밀번호 또는 소셜 계정으로 가입·로그인하고, `profiles.code`는 서버가 `P-XXXXXX`로 발급한다 |
| **F** | 소셜 로그인 | ~~Google · Kakao · Facebook 3종~~ → ~~네이버만~~ → **2026-08-06 케빈 결정: 네이버 + 구글 2종** (ADR 0010). 카카오·페이스북은 계속 없다. 소셜 계정은 제공자와 무관하게 **언제나 학생 · 개인 계정**이며 관리자가 될 수 없다 |

### E. 개인 계정에서 학번을 뺀 이유

학번은 **학교가 부여하는 식별자**다. 소속이 없는 계정에 요구할 근거가 없고, 요구하면 "아무 숫자나 학번처럼 입력된 값"이 `profiles.code`의 unique 공간을 차지해 나중에 진짜 그 학번을 쓰는 학생이 가입할 수 없게 된다.

- 그렇다고 `code`를 NULL 허용으로 바꾸지 않는다. 그러면 "로그인 아이디이자 표시용 식별자"라는 컬럼의 성격이 계정 종류마다 갈라지고 unique 도 함께 흔들린다. **값은 유지하되 생성 주체만 서버로 옮긴다**(`generate_personal_code()`).
- 개인 계정의 로그인 아이디는 **이메일**이다. 화면에서도 학번 자리에 이메일을 보여준다 — `P-XXXXXX`는 외우거나 불러줄 값이 아니라 내부 식별자다.

### F. 소셜 로그인의 경계 — **네이버 + 구글 (2026-08-06 재개정)**

> 최초 결정은 "Google · Kakao · Facebook 3종, 네이버는 만들지 않는다"였고, 2026-07-31 에 **네이버만**으로 좁혔다(ADR 0009). 2026-08-06 에 네이버가 실제로 동작하는 것을 확인한 뒤 **케빈이 구글을 다시 추가하기로 했다**(ADR 0010). 네이버의 비용(Supabase 미지원 → Edge Function + `service_role`)은 **사라진 것이 아니라 계속 수용 중**이며, 그 비용을 묶는 가드는 ADR 0009 결정 3에 있다. 구글에는 그 비용이 없다 — Supabase 기본 경로라 서버 코드가 0줄이다.
>
> **되돌리기가 쌌던 이유**: ADR 0009 가 `handle_new_user()` 의 소셜 분기를 삭제하지 않고 남겨뒀다. 그래서 구글 복귀에 **마이그레이션이 0건**이다.

| 항목 | 결정 |
|---|---|
| 제공자 | **네이버 + 구글 2종.** 카카오·페이스북은 계속 없다 |
| 구글 구현 방식 | Supabase 기본 `signInWithOAuth({provider:'google'})`. Edge Function·콜백 라우트·`VITE_` 환경변수 **전부 불필요**. 활성 여부는 `/auth/v1/settings` 의 `external.google` 로 판정한다(ADR 0010 결정 4) |
| 구현 방식 | Supabase 의 소셜 경로를 쓰지 않는다. **Edge Function `naver-auth`** 가 `code → token → 프로필 → 계정 → 매직링크 토큰`을 잇고, 프런트가 `verifyOtp` 로 세션을 만든다 |
| **role** | 네이버 계정은 **언제나 `student` / `personal`** 이다. Edge Function 이 `createUser` 에 넘기는 metadata 가 `{ name }` 뿐이라 트리거의 "(c) 개인 이메일 가입" 분기를 탄다 → **네이버로 관리자가 되는 경로가 구조적으로 없다** |
| 배치 | 버튼은 **학생 탭 + 개인 계정**에만 둔다. 학교 계정은 학번·이름 대조가 로그인의 일부라 대체할 수 없고, 관리자 탭에 두면 되지 않는 경로를 약속하는 셈이다 |
| 이름 | `name` → `nickname` 순으로 쓰고 둘 다 없으면 `이름 미설정` |
| 이메일 | 검수 전에는 안 올 수 있다. 없으면 `naver_{id}@accumu.local` 를 쓴다(같은 사람 = 같은 값이라 계정이 하나로 유지된다) |
| 설정 전 상태 | `VITE_NAVER_CLIENT_ID` 가 없으면 **버튼이 비활성**이고 사유가 화면에 뜬다. 나머지 기능은 그대로 동작한다 |
| 학교 연동 | 네이버로 가입한 뒤에도 마이페이지에서 초대코드를 넣으면 학교 계정이 된다(확정 D 경로 그대로) |
| **폰 시연 제약** | 네이버는 Callback URL 로 **앱 주소**를 등록해야 하는데 사설 IP(`192.168.x.x`)는 거부될 수 있다 → **네이버는 PC 전용**, 폰에서는 이메일 가입/로그인을 쓴다 |

### C 를 "표시만"으로 정한 이유 (원칙 6 충돌 회피)

케빈의 최초 표현은 "관리자가 발송한 초대 코드"였다. **코드를 앱에서 발급·관리하게 만들면 관리자 기능이 4번째가 되어 CLAUDE.md 2장 6번(관리자 기능 3가지 한정)을 개정해야 한다.** 그리고 더 무거운 문제가 있다:

> ADR 0005 결정 7-2 / `admin-students.md`: **담당 매핑은 권한 경계 그 자체다.** 관리자가 앱에서 매핑을 늘릴 수 있게 만든다는 것은 "관리자가 자기가 볼 수 있는 학생을 스스로 늘릴 수 있게 만든다"는 뜻이다.

**고정 코드 + 표시만** 형태는 두 문제를 동시에 피한다.

| 관점 | 판단 |
|---|---|
| 관리자 기능 개수 | **3종 그대로.** 새로 생긴 관리자 **동작이 0개**다 — 계정 카드에 자기 코드가 한 줄 보이는 것뿐(`admin-students.md` 결정 O 와 같은 성격) |
| 매핑을 누가 늘리는가 | **학생의 가입 행위**다. 관리자가 특정 학생을 지목해 추가하는 경로는 여전히 없다. 서버가 코드→관리자 매핑을 판정한다 |
| 케빈의 요구 충족 | 코드를 화면에서 보고 학생에게 불러주면 그게 곧 "발송"이다. 시연 흐름이 동일하다 |
| CLAUDE.md 개정 | **불필요** |

## 사용자 시나리오

1. **학교 계정 가입** — 관리자가 마이페이지에서 자기 코드(`SCH-XXXX`)를 확인해 학생에게 알려준다 → 학생이 가입 화면에서 학번·이름·비밀번호 + 그 코드를 입력 → 가입 즉시 로그인되고 홈으로 진입 → **관리자 마이페이지 담당 학생 목록에 그 학생이 바로 나타난다.**
2. **개인 계정 가입** — 초대코드 없이 가입. 프로그램 신청·QR 인증·포인트·아카이브가 **전부 동일하게 동작**한다. 차이는 단 하나, 어떤 관리자도 그 학생의 아카이브를 볼 수 없다.
3. **개인 → 학교 전환** — 개인으로 쓰던 학생이 마이페이지에서 코드를 입력하면 그 시점부터 담당 학생이 된다. **이미 쌓인 활동 기록도 함께 보이게 된다**(참여 행은 그대로이고 조회 권한만 열리기 때문).
4. **관리자 가입** — 관리자 코드(`ADM-000N`)·이름·비밀번호 + **관리자 초대코드**를 입력해야 가입된다. 코드가 없으면 학생으로도 만들어지지 않고 **가입 자체가 거부**된다.
5. **중복 학번** — 이미 있는 학번으로 가입을 시도하면 폼 단계에서 막힌다("이미 등록된 학번입니다").

## 화면 구성 요소

### A. 가입 화면 (`/signup`) — 신규

1. **상단 탭 2개** — `학생` / `관리자`. 로그인 화면(`LoginPage`)의 탭과 **같은 시각 언어**를 쓴다(복제하지 않고 같은 클래스 재사용).
2. **학생 탭**
   - **계정 유형 선택(칩 2개)** — `학교 계정` / `개인 계정`. 기본값 **개인 계정**(코드 없이도 끝까지 갈 수 있는 쪽이 기본)
   - 입력: **학번 · 이름 · 비밀번호 · 비밀번호 확인** + (학교 선택 시) **초대코드**
   - 선택 입력: **관심 진로 계열**(`TRACK` 5종 칩, 건너뛸 수 있음) — 넣으면 첫 홈 화면부터 추천이 동작한다
3. **관리자 탭** — 입력: **관리자 코드 · 이름 · 비밀번호 · 비밀번호 확인 · 관리자 초대코드(필수)**
4. **계정 유형 안내 한 줄** — 학교: "선생님이 알려준 초대코드를 입력하면 담당 선생님과 연동됩니다." / 개인: "혼자 사용하는 계정입니다. 나중에 마이페이지에서 초대코드를 넣어 학교 계정으로 바꿀 수 있어요."
5. **가입 버튼** → 성공 시 **자동 로그인 + 역할별 홈으로 이동**
6. 하단 "이미 계정이 있나요? **로그인**" 링크
7. **표시하지 않는 것** — 이메일 입력(가상 이메일이라 받을 것이 없다), 법정대리인 동의(CLAUDE.md 11장 스코프 제외), 약관·개인정보 동의 체크박스(같은 이유), 소셜 로그인, 이메일 인증 메일

### B. 로그인 화면 (`LoginPage`) — 1줄 추가
- 폼 하단에 **"계정이 없으신가요? 회원가입"** 링크. 기존 로그인 로직·문구는 **손대지 않는다**.

### C. 학생 마이페이지 — 계정 연동 블록 (개인 계정일 때만)
- 프로필 카드 안, 관심 계열 아래: **"학교 계정 연동"** — 코드 입력 + 연동 버튼
- 학교 계정이면 대신 **"학교 계정 · 담당 선생님과 연동됨"** 배지 한 줄(입력창 없음, **해제 버튼 없음**)

### D. 관리자 마이페이지 — 초대코드 한 줄 (결정 C)
- 계정 카드 안, 운영 요약 줄 아래: **"내 학교 초대코드 `SCH-XXXX`"** + **복사** 버튼
- 안내: "학생이 회원가입 시 이 코드를 입력하면 담당 학생으로 연동됩니다."
- **생성·재발급·만료·회수 버튼을 만들지 않는다**(결정 C). 코드는 시딩/마이그레이션이 소유한다.

## 데이터/백엔드 영향

> 상세 설계·근거는 ADR 0008. 여기서는 "무엇이 성립해야 하는가"만 적는다.

1. **`profiles.account_type`** (`'school' | 'personal'`, 학생만. 관리자는 NULL)
   - 학생이 **자기 소속을 화면에 표시**하려면 필요하다. `mentor_students`로는 알 수 없다 — 그 테이블에 **학생 축 정책이 없고**(ADR 0005: "학생은 자기 멘토가 누구인지도 모른다") 그 경계를 이 스펙이 열지 않는다.
2. **`invite_codes` 테이블 신규** — `code / kind('school'|'admin') / admin_id / is_active`
   - `kind='school'` 이면 `admin_id` 필수(그 관리자에게 연동), `kind='admin'` 이면 NULL.
   - **insert/update/delete 정책 0개** — 코드 생성은 시딩/SQL 전용이다(결정 C).
   - select 정책은 **관리자 본인의 school 코드 1행**만.
3. **가입 시 `profiles` 행 생성** — 클라이언트가 `role`을 정할 수 없어야 한다.
   - `role='admin'`은 **유효한 관리자 초대코드가 있을 때만** 부여된다. 판정은 **DB 안에서** 일어난다.
   - 학교 코드로 가입하면 `mentor_students` 1행이 **같은 트랜잭션에서** 생성된다.
4. **개인 → 학교 전환 경로 1개** (`profiles.account_type` + `mentor_students` insert)
   - **`profiles`의 update 정책은 계속 0개**여야 한다(ADR 0007 결정 3-6 규율 유지).
5. **중복 학번/관리자코드** — `profiles.code`가 이미 unique 다. 폼 단계에서 미리 안내하되, 최종 판정은 DB 제약이다.

### Supabase 대시보드 설정 (코드로 못 하는 것)
- **Authentication → Email → "Confirm email" 을 꺼야 한다.** 가상 이메일(`{code}@accumu.local`)은 실제로 메일을 받을 수 없어, 켜져 있으면 가입은 되는데 로그인이 막힌다. (켜진 상태로 시도하면 무료 플랜 메일 한도에 걸려 `over_email_send_rate_limit`(429)로 실패한다 — 실제로 밟은 함정이다.)
- **구글 (ADR 0010)** — 이쪽은 Supabase Providers 설정이 **맞다.**
  1. Google Cloud Console → 사용자 인증 정보 → OAuth 클라이언트 ID(웹) 생성
  2. **승인된 리디렉션 URI = Supabase 콜백** `https://<project-ref>.supabase.co/auth/v1/callback` (앱 주소가 아니다 — 네이버와 반대)
  3. Supabase → Authentication → Providers → Google 켜고 Client ID / Secret 입력
  4. Supabase → Authentication → URL Configuration → Site URL + Additional Redirect URLs 에 `http://localhost:5173/**` 와 배포 주소 등록. **빠지면 구글 인증은 되는데 앱으로 못 돌아온다.**
  5. 프런트 환경변수 추가 없음
- **네이버 (ADR 0009)** — Supabase Providers 설정이 **아니다.**
  1. [developers.naver.com/apps](https://developers.naver.com/apps) 에서 애플리케이션 등록 → 사용 API `네이버 로그인`, 제공 정보 `이메일 · 이름`
  2. **Callback URL = 앱 주소** `http://localhost:5173/auth/naver` (Supabase 콜백이 아니다)
  3. 클라이언트 ID → `.env.local` 의 `VITE_NAVER_CLIENT_ID`
  4. 클라이언트 Secret → **Edge Function 환경변수로만**: `supabase secrets set NAVER_CLIENT_ID=... NAVER_CLIENT_SECRET=...`
  5. `supabase functions deploy naver-auth --no-verify-jwt`

## 절대 원칙 체크

- **게임화/사행성**: 영향 없음. 가입 보너스 포인트를 **주지 않는다**(원장에 행이 생기지 않는다).
- **진로·커리어 중심**: 가입 시 관심 계열을 선택 가능하게 해 첫 화면부터 진로 축이 살아 있게 한다.
- **포인트 시뮬레이션**: 가입 경로는 `points_*`를 **한 컬럼도 건드리지 않는다**(초기값 0은 테이블 기본값).
- **포트폴리오 우선**: 가입 직후 홈은 기존 화면 그대로다. 포인트 배너를 새로 만들지 않는다.
- **QR 2회 인증**: 개인 계정도 동일하게 적용된다. 가입 방식이 인증 단계를 줄이지 않는다.
- **관리자 기능 3종 한정**: **동작 0개 추가.** 초대코드는 "표시"이지 관리 기능이 아니다.

## 인수 조건

### 가입 — 개인 계정 / 소셜 (개정분)
- [ ] 개인 계정 가입 폼에 **학번 입력이 없다**(이메일을 받는다)
- [ ] 이메일로 가입한 계정이 **이메일 + 비밀번호로 재로그인**된다
- [ ] 소셜 버튼으로 가입하면 프로필이 자동 생성되고 학생 홈으로 들어간다
- [ ] 소셜/개인 계정의 `profiles.code`가 `P-XXXXXX` 형식으로 발급된다
- [ ] **소셜로 가입한 계정의 role 이 언제나 `student`, `account_type`이 `personal`이다**
- [ ] 마이페이지의 학번 자리에 **이메일**이 뜬다(학교 계정은 학번 그대로)
- [ ] 소셜 계정도 마이페이지에서 초대코드로 학교 계정이 된다
- [ ] 미설정 제공자 버튼을 누르면 **설정 문제임이 드러나는 문구**가 뜬다(입력을 고치라고 하지 않는다)

### 가입 — 학생
- [ ] 개인 계정으로 가입되고 즉시 로그인되어 학생 홈으로 이동한다
- [ ] 학교 코드로 가입하면 **관리자 마이페이지 담당 학생 목록에 즉시 나타난다**
- [ ] 잘못된 학교 코드는 가입이 진행되지 않는다
- [ ] 중복 학번이 폼 단계에서 막힌다
- [ ] 가입 시 고른 관심 계열이 홈 추천에 반영된다(안 골라도 가입된다)
- [ ] 가입한 계정으로 **로그아웃 후 재로그인**이 된다(학번·이름·비밀번호 3개 일치)

### 가입 — 관리자 (권한 경계, **반드시 확인**)
- [ ] 관리자 초대코드 없이는 관리자로 가입되지 않는다
- [ ] **가입 폼을 우회해 `role='admin'`을 넣어도 관리자가 되지 않는다**(개발자도구·직접 API 호출로 시도할 것)
- [ ] 관리자로 가입한 계정이 QR 스캔·프로그램 등록을 실제로 할 수 있다
- [ ] 관리자로 가입해도 **담당 학생이 0명**이다(매핑은 학생의 가입/연동으로만 생긴다)

### 연동 (개인 → 학교)
- [ ] 개인 계정 마이페이지에 연동 입력이 뜨고, 코드 입력 시 학교 계정이 된다
- [ ] 연동 후 **이전에 쌓은 활동 기록까지** 관리자 아카이브에서 보인다
- [ ] 학교 계정에는 입력창 대신 배지가 뜨고 **해제 버튼이 없다**
- [ ] 연동 경로로 `points_*` / `role` / `code` 가 바뀌지 않는다

### 관리자 초대코드 표시
- [ ] 관리자 마이페이지에 본인 코드 1개가 뜨고 복사된다
- [ ] **생성·재발급·만료·회수 버튼이 없다**
- [ ] 다른 관리자의 코드는 조회되지 않는다(정책이 본인 축뿐)

### 회귀
- [ ] 기존 시드 계정 6개의 로그인이 그대로 동작한다
- [ ] 시드 스크립트(`seed-accounts.mjs`)가 **신규 프로젝트에서 그대로 동작한다** — 트리거는 시딩 경로에 관여하지 않는다(`account_type` 한 필드만 스크립트에 추가됨, `profiles_account_type_rule` CHECK 때문)
- [ ] QR 발급→스캔→포인트 지급, 정원 차단, 게시중단 열화가 전부 그대로 동작한다
