# 학생 디지털 아카이브 + 마이페이지 (+ 만족도 평가)

## 영향 범위
**학생 화면 전용** (`/student/archive` 교체 + `/student/mypage` 교체 + `QrCenterModal` 퇴장 완료 화면 1곳). 관리자 화면 변경 0건.
※ CLAUDE.md 9장 학생 화면 10개 중 **마지막 남은 2개**(디지털 아카이브, 마이페이지) + **만족도 평가**(6장 3번, 지금까지 유일하게 미구현인 절대 원칙 조항).
※ **[자매 스펙과 결정적으로 다른 점] backend 작업이 확실히 있다.** `admin-programs.md`는 정원 차단 1건, `admin-students.md`는 0건이었지만 **이 스펙은 최소 4건**(정책 1 + 테이블 1 + RPC 2)이 발생한다. 아래 "데이터/백엔드 영향" 절 전체가 architect·backend 입력이다.
※ 자매 스펙 `docs/specs/admin-students.md`가 **아카이브 화면을 이미 한 번 설계했다.** 무엇을 공유하고 무엇을 다르게 하는지는 아래 **B절 대조표**에 전부 적었다. 표현·컴포넌트·인쇄 방식을 새로 발명하지 않는다.

## 배경 / 왜 필요한가

지금 `/student/archive`는 13줄 placeholder, `/student/mypage`는 로그아웃 + QR 진입점만 있는 placeholder다. 그래서 앱의 상태를 정확히 말하면 이렇다.

1. **QR 퇴장 인증이 포인트를 지급하고 있는데, 학생이 자기 포인트를 볼 화면이 없다.** `verify_participation_qr()`가 `profiles.points_balance`를 올리고 `point_transactions`에 원장을 쌓지만, 그 값을 읽는 화면이 앱에 0개다. 게다가 `point_transactions`는 **정책이 0개(select 포함)**라 학생 본인도 읽을 수 없다.
2. **"디지털 포트폴리오"라는 이 프로젝트의 한 문장짜리 정체성이 학생 화면에 없다.** 학생 홈의 StackViz는 블록만 보여주고(숫자·목록 없음), 아카이브는 빈 placeholder다. `admin-students.md`가 관리자 쪽 아카이브를 설계했지만 **그건 남의 기록을 읽는 화면**이고, 정작 본인이 자기 기록을 보는 화면이 없다.
3. **절대 원칙 3(포인트 → 지역화폐 전환은 시뮬레이션)이 아직 한 줄도 구현되지 않았다.** `point_transaction_type` enum에 `'전환'` 값이 정의만 되어 있고(ADR 0005 결정 3-2), `currency_balance`를 건드리는 코드가 앱에 0개다.
4. **절대 원칙 6장 3번("퇴장 인증 완료 시 만족도 평가 자동 노출")이 유일하게 미구현 상태로 남아 있다.** 훅 지점 주석이 `src/components/student/QrCenterModal.jsx:289`에 "미구현이지 삭제가 아니다"로 남아 있고, ADR 0005 결정 B-1이 `reviews` 테이블을 **이 스펙으로 명시적으로 미뤘다.**

이 스펙이 그 4칸을 한 번에 닫는다. 그리고 이 화면은 **앱 최초로 "학생이 자기 포인트를 소비(전환)하는" 화면**이다 — 지금까지 학생의 쓰기는 `participations` insert 2컬럼과 `issue_participation_qr()` 하나뿐이었다. 그래서 이 스펙의 실질적 무게중심은 화면이 아니라 **잔액을 줄이는 경로를 어떻게 열 것인가**다.

### 전제 — 이미 확정된 것 (재논의하지 않는다)

| 항목 | 확정 내용 | 출처 |
|---|---|---|
| `point_transactions` 정책 | **현재 0개(select 포함).** "마이페이지 스펙에서 `point_transactions_select_own`을 열 자리"로 **명시적 예약** | ADR 0005 결정 2-1 / "RLS 영향" 절 |
| 포인트 표시의 소스 | 아카이브·내역은 **`programs.points`가 아니라 `point_transactions.amount`**(지급 시점 스냅샷)를 읽는다 | 결정 3-6 |
| `profiles` update | **정책 0개.** 포인트를 늘리는 유일한 경로는 `verify_participation_qr()` | 결정 3-4 |
| 전환의 형태 | `type='전환'` 원장 1행 + `points_balance` 차감 + `currency_balance` 증가. **차감도 `profiles` update이므로 definer RPC가 필요**(update 정책을 열지 말 것) | 결정 3-4 / "향후 변경" |
| `points_total` | 누적. **전환이 생겨도 줄지 않는다** — "둘이 갈라지는 것은 전환이 생길 때" | 결정 3-4 |
| 계열 선택 | `career_interest`만 여는 컬럼 경계는 RLS로 불가능, 컬럼 grant도 역할 구분 불가 → **definer RPC가 될 가능성이 높다.** `for update using (id = auth.uid())`만 여는 것으로 끝내지 말 것(`points_*`가 함께 열린다) | 결정 "향후 변경" |
| `reviews` | 확정 B-1이 미뤘다. **아카이브 스펙에서 함께 만든다.** 훅 지점 주석 유지 | 결정 "향후 변경" |
| 월 버킷 기준 | **`programs.date`**(활동이 일어난 달), `exit_at` 아님. 날짜는 `src/lib/date.js` KST 유틸, **`toISOString()` 금지** | 결정 5 |
| StackViz 가드 | 블록에 **숫자·레벨·게이지·"N개 달성" 라벨 금지, amber 금지** | 결정 5 |
| 게시중단 열화 | 학생은 미게시 `programs` 행을 **읽을 수 없다.** 프로그램 정보 표시만 열화되고 참여·포인트는 정상 | 결정 7-4 |
| 참여 조회 권한 | `participations_select_own`이 이미 필요한 권한을 준다 — **추가 정책 불필요** | ADR 0004 / 결정 5 |
| 계열 다중 선택 | 프로토타입은 배열(`state.interestTracks`, 최대 2개)이었으나 **단일 enum으로 확정.** "마이페이지 계열 선택 UI 스펙에서 다중이 필요하다고 판단되면" 재검토하라고 **이 스펙을 지목** | ADR 0003 "향후 변경" |

**이번에 개정되는 전제는 없다.** 다만 ADR 0005가 "다음 스펙 몫"으로 남긴 항목 4개(`point_transactions_select_own`, 전환 RPC, 계열 RPC, `reviews`)를 전부 회수한다.

### 현재 데이터 상태 — **지금 아카이브를 열면 비어 있다**

`participations` 2행, `point_transactions` **0행**. 즉:

- 아카이브 = 완료 활동 0건 → **빈 상태**
- 마이페이지 포인트 = `points_balance` 0 → **전환 버튼 비활성**
- 별점 = 평가할 완료 활동 0건 → **작성 경로 자체가 안 열림**

**가짜 데이터를 시드하지 않는다**(ADR 0005 확인 2번 케빈 확정, ADR 0004 "가짜 참여를 하드코딩하지 않는다"). 따라서 **빈 상태 설계가 이 스펙에서 장식이 아니라 기본 상태**이며, 인수 조건에서도 빈 상태를 먼저 검증한다.

### A. 왜 새 라우트를 만들지 않는가

- `StudentShell`의 하단 탭바/상단 나브가 **홈 · 프로그램 · 아카이브 · 마이** 4개로 이미 확정돼 있다. 아카이브 하위에 목록/상세를 또 만들면 탭 하나에 2단계가 생겨 모바일에서 뒤로가기 의미가 흐려진다.
- **관리자 아카이브가 2단계 라우트인 이유는 "학생 5명을 한 화면에 놓지 않기 위해서"**(admin-students 결정 A = 원칙 1 가드를 구조로 만든 것)였다. **학생 본인 화면에는 학생이 1명뿐이라 그 이유가 존재하지 않는다.**
- 활동 상세(참여 확인 일시 + 나의 평가)는 **모달**(`Modal.jsx` 재사용, 프로토타입 `openActivityDetail` 계열). 인쇄는 모달이 아니라 **페이지 본문**을 대상으로 하므로 admin-students 결정 A-3의 "모달은 PDF에 최악의 컨테이너" 문제가 발생하지 않는다.

| 게시중단 열화 | 데모에서 **거의 발생하지 않는다** (전 프로그램이 `created_by = ADM-0001`이라 관리자는 계속 읽는다 — 이슈 2) | **실제로 발생한다.** 학생은 미게시 행을 못 읽는다 | **다름 — 학생 쪽이 더 심각** |
| 서비스 파일 | `src/lib/archiveService.js` | **같은 파일에 학생용 함수 추가** | **공유** |
| 컴포넌트 | `AdminStudentArchivePage` | `StudentArchivePage` | 페이지는 다름, **요약·활동목록 자식 컴포넌트는 공유** |

**공유 규칙 (frontend 필수):**
- `admin-students.md`가 이미 예고했다 — *"이번에 만드는 요약·활동 목록 표현을 재사용할 수 있게 컴포넌트를 학생 id 비의존으로 짜두면 좋다"*. **이 스펙에서 그것이 의무가 된다.** 요약 블록과 활동 행은 `{ participation, program|null }` 배열만 받는 **표시 전용 컴포넌트**여야 하고, 누구의 기록인지 알지 못해야 한다.
- **차이는 prop으로 표현한다**(`showPoints` / `showReview` / `onActivityClick`). 컴포넌트를 복제하지 않는다.
- `print.css`는 **전역 1개**다. `.no-print` 규율, `break-inside: avoid`, `print-color-adjust: exact`, `document.title` 교체/복원까지 admin-students G절 그대로.

### C. 왜 막대 게이지를 기각하는가 (레이더는 M-2로 뒤집혔다 — M절 참고)

프로토타입 아카이브에는 **레이더 차트**(`renderRadar`, 1266~1281줄, "주력 분야 · IT 5회")가 있고 마이페이지에는 **분야별 획득 포인트 막대**(`.fieldpts`, 1312~1319줄)가 있다.

**막대 게이지(`.cc .bar` / `.fieldpts`)는 기각한다 — 이 판단은 유지된다.**

| 근거 | 설명 |
|---|---|
| 원칙 1 | ADR 0005 결정 5 가드가 성장 시각화에 **게이지·레벨·"N개 달성"을 금지**했다. `width: N%` 막대는 정확히 그 형태다 — **최대치 대비 비율**이 곧 달성률로 읽힌다 |
| 일관성 | `admin-students` 결정 C가 같은 정보를 **사실 기술 텍스트**로 확정했다 |

→ 유형 분포는 **사실 기술**: `총 참여 활동 5 · 교내 3 · 교외 2`, 그 아래 `방과후 2 · 동아리 1 · 봉사활동 2`. 프로그램 정보를 못 찾은 건은 **`분류 없음 1`**로 별도 집계(조용히 빼지 않는다).
→ **숫자 카운트업 금지.** 프로토타입 `animateNum`(1309줄)을 옮기지 않는다 — 원칙 1이 금지하는 성취 연출이다.
→ **레이더는 확정 M-2로 추가됐다.** 단 축이 다르다 — 이 절의 텍스트 요약은 **활동 유형(`CAT` 8종)**이고, 레이더는 **진로 계열(`TRACK` 5종)**이다. 둘은 겹치지 않으며 텍스트 요약은 그대로 유지된다(그래프가 유일한 정보원이 되지 않게).

### D. 만족도 평가를 어디서 어떻게 노출하는가

CLAUDE.md 6장 3번은 **"퇴장 인증 완료 시 포인트 자동 지급 + 만족도 평가 자동 노출"**을 요구한다. 훅 지점은 `QrCenterModal.jsx:289`에 이미 주석으로 예약돼 있다.

**1) 자동 노출 (요구사항)**
- 퇴장 완료 화면(`done` + `!isEntry`)에서 **"참여가 기록되었습니다" → +NNNP 적립 → 그 아래 만족도 평가 블록**이 이어서 나타난다.
- **별도 모달을 겹치지 않는다.** 이미 모달 안이므로 같은 `mbody`에서 뷰를 전환한다(프로토타입 `openSurvey`는 오버레이 교체였지만, 여기서는 QR 모달이 이미 떠 있다).
- 입장 인증(`isEntry`) 완료 화면에는 **노출하지 않는다.** 아직 활동이 끝나지 않았다.

**2) 건너뛰기 허용 (필수)**
- "건너뛰기" 버튼을 둔다(프로토타입 `skipSurvey`). **평가를 강제하면 QR 흐름의 마지막 단계가 막힌다** — 현장에서 학생이 모달을 못 닫는 상황은 QR 2회 인증(원칙 5)의 신뢰를 깎는다.
- 건너뛴 활동은 아카이브 목록에 **"평가 미작성 · 눌러서 남기기"**로 표시되고 언제든 작성할 수 있다.

**3) 입력 규칙 (프로토타입 그대로)**
- 별점 **1~5, 필수**. 별점 없이 제출 불가(인라인 안내: "별점을 먼저 선택해 주세요").
- 한줄평 **선택, 최대 60자**(프로토타입 `maxlength="60"`). placeholder: "한 줄 평을 남겨보세요 (선택) · 포트폴리오에 함께 기록됩니다".
- 별점 라벨 5종도 프로토타입 `RATE_TXT` 그대로("별로였어요"…"최고였어요!").
- **별 색은 amber**(프로토타입 `var(--amber)`). 원칙 4 위반이 아니다 — 별점은 포인트 표시가 아니고, CLAUDE.md 2장 1번이 명시적으로 허용한 요소다.

**4) 수정 허용**
- 이미 남긴 평가를 **다시 열어 수정할 수 있다**(별점 오입력은 실사용에서 반드시 발생한다). 삭제는 만들지 않는다.
- → **`reviews`에 update 정책이 필요하다.** 경계 요구사항은 아래 "데이터/백엔드 영향" 2번.

**5) 원칙 1 가드 (필수)**
- [ ] 프로그램의 **평균 별점·리뷰 수·"평점 4.8" 배지**를 어디에도 표시하지 않는다 (프로그램 선택 화면 포함)
- [ ] **다른 학생의 리뷰를 볼 수 있는 경로가 없다** — RLS로도 차단(결정 E)
- [ ] 평가를 남겼다고 **포인트·뱃지·보상을 주지 않는다** (원장에 `'적립'`이 늘지 않는다)
- [ ] "평가 완료율" 같은 진척도 표시 없음

### F. 전환 단위를 왜 이렇게 정하는가

| 항목 | 결정 | 근거 |
|---|---|---|
| 단위 | **10P** | 원칙 7(모든 포인트 값 끝자리 0) → 적립액이 항상 10의 배수 → **잔액도 항상 10의 배수**다. 10P 단위면 "전액 전환"이 언제나 정확히 떨어진다 |
| 최소 | **100P** | 1P 전환 같은 무의미한 원장 행 방지. 최소 적립액(150P)보다 낮아 **첫 활동 1건만으로도 전환을 시연할 수 있다** |
| 최대 | **현재 `points_balance`** | 잔액을 넘는 전환은 거부(음수 금지) |
| 프리셋 | `500 / 1,000 / 3,000` 중 **잔액 이하만** + **"전액 전환 · N P"** | 프로토타입은 `[1000,3000,5000,10000]`이었지만 **데모 잔액은 수백~수천P**라 칩이 하나도 안 뜬다(실제로 프로토타입도 `if(!chips.length)chips=[avail]` fallback을 탄다). 눈금을 데모 규모에 맞춘다 |
| 자유 입력 | **만들지 않는다** | 칩 + 전액이면 데모에 충분하고, 자유 입력은 프런트 검증(10P 단위·최소·최대)이 하나 더 는다 |

- **1P = 1원.** "받을 지역화폐 ₩ N" 표시(프로토타입 1233줄 그대로).
- **시뮬레이션 고지를 반드시 표시한다** — 프로토타입 1235줄 카피 그대로: *"※ 프로토타입에서는 실제 지역화폐 계좌로 연동되지 않으며, 전환 결과만 표시됩니다."* **이 문장은 절대 원칙 3을 화면이 스스로 말하는 자리라 삭제·축약 금지.**
- **되돌릴 수 없음을 확인 단계에서 고지한다**(결정 G): "전환한 포인트는 되돌릴 수 없습니다."

### I. `notifications`를 이 스펙에 넣을까 → **넣지 않는다** (판단 요청에 대한 답)

| 근거 | 설명 |
|---|---|
| **backend 4건이 5건이 된다** | 이미 정책 1 + 테이블 1 + RPC 2가 걸려 있다. 알림은 테이블·정책만으로 끝나지 않고 **"누가 알림 행을 만드는가"**가 따라온다 — 답은 `verify_participation_qr()`이고, 그건 **이미 검증이 끝난 QR 경로를 다시 여는 것**이다(ADR 0005 결정 3의 원자성·멱등 구조 전체가 회귀 대상이 된다). 이 스펙에 끼워 넣기에는 위험이 다른 층이다 |
| **화면 소속이 다르다** | CLAUDE.md 9장은 알림을 **"상단 공통"** 요소로 적었다. 아카이브·마이페이지의 기능이 아니라 `StudentShell`(나브)의 기능이다. 이 스펙의 두 화면을 다 만들어도 알림 없이 인수 조건이 전부 성립한다 |
| **읽음 처리가 학생 쓰기 경로를 하나 더 연다** | `is_read` 토글 = `notifications` update 정책. 지금 학생의 쓰기 경로는 `participations` insert 2컬럼뿐이고, 이 스펙이 이미 `reviews` 쓰기와 RPC 2개를 추가한다. **한 스펙에서 여는 쓰기 표면은 셋까지가 한계**라고 본다 |
| **원칙과 충돌하지 않는다** | 알림 자체는 원칙 위반이 아니다. 미루는 이유는 순수하게 범위·회귀 위험이다 |

→ **`docs/specs/student-notifications.md`(가칭)로 분리.** ADR 0005도 "입·퇴장 인증이 알림 이벤트의 첫 소스가 될 것"이라고만 예고해뒀다. 이 스펙이 끝난 뒤 QR 경로를 한 번에 손대는 편이 안전하다.

### J. 보존 대상 — QR 진입점과 로그아웃 (**삭제 금지**)

`StudentMyPage.jsx`의 현재 두 기능은 **placeholder의 부산물이 아니라 확정 사항**이다.

| 기능 | 왜 여기 있는가 | 이번 작업 |
|---|---|---|
| **QR 확인 · 입퇴장 인증** (`QrCenterModal`) | **확정 F-1**이 QR 진입점을 마이페이지에 심었다. 버튼 위치·카피·색(indigo)은 프로토타입 652줄 그대로 | **그대로 유지.** 프로필 카드 안, 계열 선택 칩 아래 |
| **로그아웃** | 홈이 실제 화면으로 바뀌면서 갈 곳이 없어진 경로. **케빈이 학생/관리자 계정을 오가며 시연하는 유일한 수단**이다. 나브에도 없다 | **그대로 유지.** 화면 최하단 |

- [ ] 리팩터링 중 이 두 버튼이 사라지면 **1인 시연이 불가능해진다.** frontend는 마이페이지를 새로 짜되 이 두 경로를 먼저 배치하고 나머지를 채운다.
- `PlaceholderScreen`은 더 이상 쓰지 않지만 **파일을 삭제하지 않는다**(`StudentArchivePage`가 함께 교체되면 참조가 0이 되지만, 다른 placeholder가 남아 있을 수 있다 — 확인 후 판단).

### 시나리오 1 — 퇴장 인증 직후 평가를 남긴다 (원칙 5 → 6장 3번 연결)
1. 관리자가 학생의 퇴장 QR을 스캔한다.
2. 학생 화면(QR 모달)이 폴링으로 감지 → **"참여가 기록되었습니다"** + `+700P 적립`.
3. **이어서 같은 모달 안에 만족도 평가가 나타난다**: "활동은 어떠셨나요?" + 별 5개 + 한줄평 입력(선택, 60자).
4. 별 4개를 누르니 라벨이 "좋았어요"로 바뀐다. 한줄평을 쓰고 "평가 제출하기".
5. 토스트: "평가가 저장되었어요 · 포트폴리오에 반영됩니다". 모달이 닫힌다.
6. 아카이브로 가면 그 활동 행에 **별 4개 미니 + "평가 완료"**가 붙어 있다.

### 시나리오 2 — 나중에 평가를 남기고 수정한다
1. 시나리오 1에서 "건너뛰기"를 눌렀다.
2. 아카이브 활동 행에 **"평가 미작성 · 눌러서 남기기"**가 회색으로 표시된다.
3. 행을 누르면 활동 상세 모달이 열린다 — 프로그램 정보 + 참여 확인 일시 + **"나의 만족도 · 한 줄 평"** 블록.
4. 거기서 평가를 남긴다. 다시 열어 별점을 5로 고치고 저장하면 **덮어쓰기된다**(행이 늘지 않는다).

### 시나리오 3 — 포인트를 지역화폐로 전환한다 (절대 원칙 3)
1. 마이 탭. **사용 가능한 포인트 `1,150 P`** (amber, `1P = 1원` 캡션). 그 아래 작게 `누적 획득 1,150P · 전환한 지역화폐 ₩0`.
2. "지역화폐로 전환"을 누른다 → 모달. `전환 가능 포인트 1,150 P` / 칩 `500P` `1,000P` / `전액 전환 · 1,150P`.
3. `1,000P`를 고르니 **받을 지역화폐 ₩ 1,000**. 하단에 시뮬레이션 고지와 **"전환한 포인트는 되돌릴 수 없습니다."**
4. "₩1,000 지역화폐로 전환하기" → 토스트 "₩1,000 지역화폐로 전환되었습니다".
5. 화면이 즉시 갱신된다: **사용 가능 `150 P` / 전환한 지역화폐 `₩1,000` / 누적 획득은 여전히 `1,150P`**(줄지 않는다).
6. 포인트 내역에 **`전환 −1,000P`** 행이 맨 위에 추가된다.
7. **새로고침해도 그대로다** — 로컬 상태가 아니라 DB가 바뀌었다.
8. 다시 전환을 누르면 잔액 150P라 칩이 하나도 안 뜨고 **"전액 전환 · 150P"만** 뜬다(최소 100P 이상이라 가능).

### 시나리오 4 — 잔액을 넘겨 전환을 시도한다 (거부 경로)
1. 두 탭을 열어두고 한쪽에서 전액 전환을 끝낸 뒤, 오래된 다른 탭에서 같은 전환을 누른다.
2. 서버가 거부한다 → **"포인트가 부족합니다. 잔액을 다시 확인해 주세요."** + 화면의 잔액이 최신 값으로 갱신된다.
3. **"권한 오류"가 아니라 사유가 구분된 문구**로 뜬다.
4. 개발자도구로 프런트를 우회해 잔액보다 큰 값을 보내도 **똑같이 거부되고**, DB의 `points_balance`가 **음수가 되지 않는다.**

### 시나리오 5 — 관심 계열을 바꾼다
1. 마이 탭 프로필 카드의 "관심 진로 계열" 칩 5개 중 `IT·소프트웨어`가 켜져 있다(시드 값).
2. `이공계·자연과학`을 누른다 → 선택이 옮겨간다. 토스트: "관심 계열을 저장했어요 · 홈 추천에 반영됩니다".
3. 홈으로 가면 **추천 프로그램 순서가 실제로 바뀌어 있다**(`career_track` 일치 항목이 앞으로).
4. 켜진 칩을 다시 누르면 **해제**(`null`)되고, 홈 추천은 최신순 fallback으로 돌아간다.
5. **새로고침해도 유지된다.**

### 시나리오 6 — PDF 포트폴리오
1. 아카이브 우측 상단 "PDF로 저장" → 브라우저 인쇄 미리보기.
2. 나브·하단 탭바·버튼·어두운 히어로(StackViz)가 사라지고, 상단에 **"Accumu 디지털 활동 포트폴리오 / 신지훈 · 10718 / 출력일 2026-07-30"** 머리글이 붙는다.
3. "PDF로 저장" → `Accumu_활동포트폴리오_신지훈_10718_2026-07-30.pdf`. **글자는 이미지가 아니라 텍스트**라 복사·검색된다.

### 시나리오 7 — 게시중단된 프로그램의 완료 기록 (**학생 쪽은 실제로 깨진다**)
1. 관리자가 학생이 완료한 프로그램을 "내리기" 한다.
2. 학생 아카이브를 다시 연다 → **그 활동 행이 사라지지 않는다.** 제목 자리에 **"게시가 중단된 프로그램"**, 날짜는 `exit_at` 기준 대체 표시, 유형 아이콘은 회색 fallback.
3. 요약에서는 **"분류 없음 1"**로 집계된다.
4. StackViz에서는 그 블록이 **그려지지 않는다**(월을 결정할 수 없다 — 기존 동작, 수정하지 않는다).
5. **포인트 내역에는 아무 영향이 없다** — `point_transactions.amount`는 원장에 남아 있다. 활동명만 대체 문구가 된다.
6. 콘솔에 에러가 던져지지 않는다.

6. **인쇄 전용 머리글** — 화면에서 숨김, 인쇄에서만: "Accumu 디지털 활동 포트폴리오" / 이름 · 학번 / 출력일(`todayISO()`) / "QR 입·퇴장 인증이 완료된 활동만 기록됩니다"
7. **표시하지 않는 것** — 막대 게이지(결정 C), 퍼센트·달성률·"N/5"·순위 정렬된 축(M절), 신청만 하고 안 간 활동(`applied`/`entered`는 QR 센터의 몫), 다른 학생과의 비교, 랭킹, 평가 완료율

### B. 마이페이지 (`/student/mypage`)

프로토타입 `.my-grid` 2열(좌: 프로필 / 우: 포인트). **모바일 1열에서 프로필 카드가 위**(원칙 4 — 아래 "절대 원칙 체크").

**B-1. 프로필 카드 (좌 / 위)**
1. `.pbanner` + 아바타(이름 첫 글자) + 이름 + `학생 · 진로 탐색 중`
2. 정보 행 — **학번(`code`)만.** 프로토타입의 학교·학년·가입일은 **표시하지 않는다**
   - 근거: `profiles`에 학교·학년 컬럼이 **없다**(ADR 0002). `created_at`은 있지만 그건 **시딩 시각**이지 가입일이 아니다. **없는 정보를 그럴듯하게 지어내지 않는다**
3. **관심 진로 계열 선택** — `TRACK` 5종 칩. 현재 값 강조, 누르면 저장, 다시 누르면 해제(`null`)
   - 안내: 선택됨 → "선택한 계열은 메인 화면 추천에 바로 반영돼요" / 없음 → "아직 설정하지 않았어요 · 설정하기"
   - **저장 중 칩 비활성**, 실패 시 이전 값으로 롤백 + 사유 표시
4. **"QR 확인 · 입퇴장 인증" 버튼 (보존 — 결정 J)** — indigo, 프로토타입 652줄 그대로
5. **아카이브 바로가기** — "내 활동 아카이브 보기 →" (brand blue, 텍스트 링크). 원칙 4의 동선 장치

**B-2. 포인트 카드 (우 / 아래)**
1. **사용 가능한 포인트** `1,150` + `P` (amber 큰 숫자) / 캡션 "사용 가능한 포인트 · 1P = 1원"
   - **카운트업 애니메이션 금지**(프로토타입 `animateNum` 미이식)
2. 보조 한 줄: `누적 획득 1,150P · 전환한 지역화폐 ₩1,000` (`points_total` / `currency_balance`)
3. **"지역화폐로 전환" 버튼** — 잔액 < 100P이면 비활성
4. **포인트 내역 (결정 H)** — `point_transactions` 원장, `created_at` 내림차순
   - 행: 유형 배지(`적립`/`전환`) + 활동명(적립 건만; 못 찾으면 "게시가 중단된 프로그램") + 날짜 + 금액(`+700P` / `−1,000P`)
   - **전환 행은 활동명이 없다**(`related_participation_id`가 NULL — DB CHECK로 보장). 대신 "지역화폐 전환"으로 표시
   - `.limit(50)` + "최근 50건" 캡션. 페이징 없음
   - 빈 상태: "아직 포인트 내역이 없습니다. 활동에 참여하고 QR 인증을 완료하면 이곳에 기록됩니다."
   - **분야별 획득 포인트 막대 없음**(결정 H)
5. **로그아웃 (보존 — 결정 J)** — 화면 최하단, 카드 밖

**B-3. 전환 모달**
- `전환 가능 포인트 N P` / 프리셋 칩 + 전액 전환 / `받을 지역화폐 ₩ N` / 실행 버튼
- **고지 2줄 (삭제 금지)**: 시뮬레이션 고지(프로토타입 1235줄) + "전환한 포인트는 되돌릴 수 없습니다."
- 실행 중 버튼 잠금(더블클릭 방어). 실패 시 **모달 유지 + 사유 표시**
- 잔액 0(또는 <100P)일 때: "전환할 포인트가 없어요 / 프로그램에 참여해 포인트를 모으면 지역화폐로 전환할 수 있어요." (프로토타입 1216~1217줄)

## 기능 요구사항 (체크리스트)

### 아카이브
- [ ] `/student/archive`가 placeholder를 대체하고 `StudentShell` 안에서 렌더된다
- [ ] `participations`를 조회한다 — **`student_id` 필터를 클라이언트에서 걸지 않는다**(RLS가 소유자)
- [ ] `programs`를 **클라이언트에서 결합**한다. **embed·뷰 금지**(정의자 권한 함정 — ADR 0003 6번 / 0004 5번 / 0005 결정 5)

- [ ] 요약에 **총/교내/교외 + 유형별 분포 + 활동 기간**이 뜬다. **막대·퍼센트 없음**
- [ ] **진로 계열 레이더가 요약 아래에 뜬다** — 축 5개 전부, 선언 순서, 건수만, 범례 없음 (확정 M-2)

- [ ] 완료 1건에서도 레이더가 **깨져 보이지 않는다**(면 채움 유지 + 0축 꼭짓점 표시)

- [ ] **숫자 카운트업 애니메이션이 없다**

## 데이터/백엔드 영향

> **이 스펙은 backend가 확실히 발생한다.** 아래 4건은 "무엇이 성립해야 하는가"만 적는다.
> **설계(정책 vs RPC, 함수 시그니처, 잠금 방식, 반환 형식)는 architect·backend의 몫이며 이 스펙이 정하지 않는다.**
> 다만 이 프로젝트가 이미 밟은 함정은 각 항목의 "함정" 소절에 적어둔다 — 선택지를 좁히려는 게 아니라 **같은 벽에 두 번 부딪히지 않기 위해서**다.

| # | 대상 | 필요 여부 | 판단 |
|---|---|---|---|
| **1** | `point_transactions_select_own` 정책 | **필요** | 포인트 내역이 이 스펙의 핵심 기능이고, ADR 0005가 **이 자리를 명시적으로 예약**했다 |
| **2** | `reviews` 테이블 + 정책 | **필요** | CLAUDE.md 5장에 필드만 있고 테이블이 없다. 6장 3번을 구현하는 유일한 방법 |
| **3** | 포인트 → 지역화폐 전환 경로 | **필요** | `profiles` update 정책 0개 + 결정 3-4가 "포인트를 늘리는 유일한 경로는 `verify_participation_qr()`"로 못박음 |
| **4** | `career_interest` 저장 경로 | **필요** | 같은 이유. 현재 앱에서 계열을 저장할 방법이 **존재하지 않는다**(ADR 0003이 시딩을 유일한 입력 경로로 둔 상태) |
| — | 새 시드 | **0건** | 빈 상태를 그대로 둔다(ADR 0005 확인 2번 확정) |
| — | 새 npm 의존성 | **0건** | PDF는 `window.print()`(admin-students 결정 G) |

### 1. `point_transactions_select_own` — 학생 본인 원장 읽기

**성립해야 하는 것:**
- 학생이 **자기 `student_id` 행만** 읽는다.
- **다른 학생의 원장은 0행**이어야 한다.
- **관리자에게는 이 테이블을 열지 않는다.** `admin-students.md` 결정 D가 "관리자 아카이브에 포인트를 표시하지 않는다"로 확정했고, 그 근거가 정확히 "원장 테이블을 관리자에게 처음 여는 결정을 하지 않는다"였다. **이 스펙이 그 문을 대신 열지 않는다.**
- **insert / update / delete 정책은 여전히 0개.** 적립은 `verify_participation_qr()`, 전환은 3번의 새 경로. 학생이 원장에 직접 쓸 수 있으면 **포인트를 스스로 찍어낼 수 있다.**

**함정:**
- `related_participation_id`로 활동명을 붙이려고 **embed·뷰를 쓰지 말 것**(정의자 권한 함정). 클라이언트 결합.
- 원장 조회 결과에 `amount`가 있다고 해서 **아카이브가 `programs.points`를 읽어도 된다는 뜻이 아니다.** 결정 3-6은 여전히 유효하다 — 표시할 포인트는 **원장의 `amount`**다.

### 2. `reviews` 테이블 — 신규

**필드 (CLAUDE.md 5장):** `id, participation_id, rating, comment` (+ 프로젝트 전례상 `created_at`).

**성립해야 하는 것:**

| 항목 | 요구사항 |
|---|---|
| 작성 경계 | **완료된 본인 참여에만** 작성 가능. `participation_id`가 가리키는 `participations` 행이 (a) `student_id = auth.uid()`이고 (b) `status = 'completed'`여야 한다 |
| 1참여 1리뷰 | `participation_id`에 **unique.** 같은 활동에 리뷰가 2행 생길 수 없다 |
| `rating` | **1~5 정수.** 범위 밖은 DB가 거부한다 |
| `comment` | nullable(선택), **길이 상한이 DB에도 있어야 한다**(프런트 60자는 우회 가능) |
| 읽기 | **본인 것만.** 관리자도, 다른 학생도 못 읽는다 (결정 E) |
| 수정 | **허용**(결정 D-4). 단 `participation_id`를 다른 참여로 **옮길 수 없어야 한다** |
| 삭제 | **정책 0개.** 삭제 경로를 만들지 않는다 |
| 부작용 | **없다.** 리뷰 저장이 포인트·상태·프로그램을 건드리지 않는다 |

**함정:**
1. **`participations`에 컬럼을 추가하지 말 것.** ADR 0005가 "`participations`에 컬럼이 추가되면 또 `participations_insert_own`을 재검토해야 한다"고 경고했다. **별도 테이블로 두면 그 재검토가 아예 발생하지 않는다.**
2. **컬럼 단위 insert grant 규율을 이어갈지 판단할 것.** `participations`는 `grant insert (student_id, program_id)`로 fail-closed다(결정 6-2). `reviews`도 같은 규율을 적용하면 나중에 컬럼이 늘어도 안전하다.
3. **update를 여는 순간 컬럼 경계가 문제가 된다.** RLS는 컬럼 단위가 아니므로 `using`/`with check` 양쪽에서 "그 참여가 여전히 본인 것"을 요구해야 `participation_id` 이동이 막힌다(admin-programs 이슈 1의 `with check` 규율과 같은 계열).
4. **`.update()`는 0행이어도 `error === null`이다**(admin-programs 이슈 1). `.select()`로 영향 행 수를 확인할 것.
5. **`status='completed'` 서브쿼리가 `participations`의 RLS를 탄다.** `participations_select_own`이 이미 있으므로 학생 경로는 성립하지만, 정책 간 결합이 늘어나는 지점이니 architect가 재귀·의존을 확인할 것(결정 6-3이 같은 벽에서 확인한 사항).

### 3. 포인트 → 지역화폐 전환 — **`profiles` 잔액을 줄이는 최초의 경로**

**성립해야 하는 것:**

| # | 요구사항 |
|---|---|
| 3-a | **원자성.** `points_balance` 차감 + `currency_balance` 증가 + `point_transactions(type='전환')` 1행이 **한 트랜잭션**이다. "포인트만 줄고 지역화폐가 안 늘어난" 상태가 존재할 수 없다 |
| 3-b | **음수 방지.** 어떤 경로로도 `points_balance < 0`이 될 수 없다. 프런트 조건문이 아니라 **DB가 판정한다** |
| 3-c | **잔액 부족은 도메인 실패다.** 권한 실패(`42501`)와 **구분 가능한 신호**여야 한다(결정 4의 규율: 권한 실패는 예외, 도메인 실패는 반환값) |
| 3-d | **금액 검증을 서버가 한다.** `amount > 0`, **10의 배수**, **최소 100**, `<= points_balance`. 프런트 검증은 우회 가능하다 |
| 3-e | **동시성.** 같은 잔액에 두 요청이 동시에 도착해도 **합계가 잔액을 넘지 않는다.** 순진한 "읽고 → 비교하고 → 쓴다"는 READ COMMITTED에서 둘 다 통과할 수 있다 |
| 3-f | **더블클릭 방어.** 같은 버튼을 두 번 눌러 두 행이 생기는 것은 **막지 않아도 정합은 깨지지 않는다**(각각 잔액을 검사하므로). 다만 프런트가 버튼을 잠근다. **QR과 달리 멱등이 요구되지 않는다** — 전환을 두 번 하면 두 번 차감되는 것이 정상 도메인이다 |
| 3-g | **`points_total`을 건드리지 않는다.** 결정 3-4가 "둘이 갈라지는 것은 전환이 생길 때"라고 명시했다. 누적은 영구 기록이다 |
| 3-h | **`related_participation_id`는 NULL이어야 한다.** DB CHECK가 이미 `(type='전환' and related_participation_id is null)`을 강제한다(결정 3-1). 이 CHECK를 **수정하지 말 것** |
| 3-i | **호출자는 학생 본인뿐.** 남의 잔액을 전환할 수 없다. 관리자 호출을 허용할 이유가 없다 |
| 3-j | **실제 결제·계좌·외부 API를 호출하지 않는다.** `currency_balance`는 **표시용 누적 숫자**다(절대 원칙 3) |

**함정 (이 프로젝트가 이미 밟은 것):**
1. **`profiles`에 update 정책을 열면 그 문은 "학생이 자기 `points_balance`를 고치는 문"과 같은 문이다.** RLS는 컬럼 단위가 아니고, 학생·관리자가 같은 DB 역할(`authenticated`)이라 컬럼 grant로도 좁힐 수 없다(결정 2-2 / 2-5-4). ADR 0005가 이 이유로 `profiles` update 정책을 0개로 유지했다.
2. **`security definer`를 만든다면 결정 2-5 체크리스트 전부 적용**: `set search_path = ''` / `revoke all from public` 후 `grant execute to authenticated` / **본문이 곧 권한 경계** / 권한 실패는 예외, 도메인 실패는 반환값.
3. **CAS 전례가 이미 있다.** 결정 3-3의 1차 방어가 `update ... where id = ? and status = '이전 상태'` 형태였다. 잔액 차감에도 같은 계열의 표현(`where id = auth.uid() and points_balance >= amt`)이 가능하고, **영향 행이 0이면 거부**로 다루면 3-b·3-e가 함께 성립한다.
4. **반환값에 갱신된 잔액을 담을지 판단할 것.** 담지 않으면 프런트가 `profiles`를 재조회해야 한다(왕복 1회 추가 + 그 사이 값이 어긋날 여지). 담으면 화면 갱신이 원자적이다 — **프런트 요구사항인 이슈 3과 직결된다.**
5. **`verify_participation_qr()`를 건드리지 말 것.** 전환은 완전히 별개 경로다. QR 함수에 손대는 순간 이미 검증이 끝난 원자성·멱등 구조 전체가 회귀 대상이 된다.

### 4. `career_interest` 저장 — **`profiles`를 학생이 바꾸는 최초의 경로**

**성립해야 하는 것:**

| # | 요구사항 |
|---|---|
| 4-a | **본인 행의 `career_interest`만 바뀐다.** `points_balance` / `points_total` / `currency_balance` / `role` / `code` / `name` / `id`가 **어떤 경로로도 함께 바뀌지 않는다** |
| 4-b | 값은 **`career_track` enum 5종 또는 NULL**(해제). 그 밖의 값은 거부 |
| 4-c | 남의 행을 바꿀 수 없다 |
| 4-d | 관리자가 학생의 계열을 바꾸는 경로를 **만들지 않는다**(관리자 기능 3종 밖) |

**함정:**
1. **ADR 0005가 이 항목에 명시적 경고를 남겼다** — *"절대 `for update using (id = auth.uid())`만 여는 것으로 끝내지 말 것(`points_*`가 함께 열린다)"*. `schema.sql` 167~170줄에도 같은 취지의 주석이 있다.
2. `career_interest`만 여는 컬럼 경계는 **RLS로 표현 불가능**하고 **컬럼 grant로도 역할 구분이 안 된다**(결정 2-5-4). ADR 0005는 **definer RPC가 될 가능성이 높다**고 예고했다.
3. **3번과 함수를 합치지 말 것.** 잔액을 만지는 함수와 계열을 만지는 함수는 권한 표면이 다르다. 합치면 계열 저장 호출이 잔액 로직을 지나간다.
4. **`career_interest`는 홈 추천의 매칭 축**이다(ADR 0003 결정 3). 저장이 조용히 실패하면 **홈 추천이 이유 없이 안 바뀐다** — 실패를 삼키지 말 것.

### 조회 설계

```js
// [공유] src/lib/archiveService.js — admin-students 가 만들 파일. 학생용 함수를 여기에 추가한다.
```

## 케빈 확인 필요 (3건) — **전부 확정됨**

> **셋 다 블로킹 아님.** 답이 없으면 **추천안(K-1 / L-1 / M-1)으로 구현**한다. "추천안대로"라고만 해도 확정된다.
>
> **[현재 상태]** K → **K-1 확정**, L → **L-1 확정**, M → **M-2 확정 (추천안 M-1이 케빈 요청으로 뒤집혔다 — 개정 이력 참고)**.

### K. 관심 계열을 **단일**로 둘까, **다중(최대 2개)**으로 열까 → **추천: K-1 (단일 유지)**

ADR 0003이 이 판단을 **이 스펙에 명시적으로 넘겼다** — *"마이페이지 계열 선택 UI 스펙에서 다중이 필요하다고 판단되면 `career_interest career_track` → `career_interests career_track[]`로 확장하고 매칭을 `= ANY`로 바꾼다."*

- **K-1 (추천, 현재 스펙 내용): 단일 유지.** 칩 1개만 켜지고, 다시 누르면 해제.
  - ADR 0003 결정 3이 **`programs.career_track`과 `profiles.career_interest`가 같은 enum 타입을 공유**하게 만들어 매칭 정합성을 타입 시스템에 맡겼다. 배열이 되면 그 관계가 `= ANY`로 느슨해진다.
  - CLAUDE.md 5장·기존 스펙 전부가 "단일 계열"로 적혀 있다.
  - **backend 변경 0건**(4번 RPC만 만들면 된다).
- K-2: 다중(최대 2개). 프로토타입 원형(`state.interestTracks`)에 충실하고 진로 탐색기 학생에게 현실적이다.
  - 비용: **`profiles` 컬럼 타입 변경 마이그레이션** + 홈 추천 매칭 로직(`ADR 0003` 결정 5) 개정 + `ProgramCard` 매칭 배지 개정. **이 스펙의 backend가 4건 → 5건이 되고 이미 구현된 홈 화면이 회귀 대상이 된다.**
  - 되돌리기 비용이 이 스펙에서 가장 크다. 그래서 질문으로 남긴다.

### L. 아카이브 활동 행에 **포인트를 표시할까** → **추천: L-1 (화면에는 표시, PDF에는 제외)**

**원칙 4의 정면 판단이다.** 프로토타입은 아카이브 활동 행 우측에 `+700P`를 표시했다(1263줄).

- **L-1 (추천, 현재 스펙 내용): 화면 활동 행에만 작은 amber로 표시. PDF·요약에는 없음.**
  - 값은 **`point_transactions.amount`**(지급 시점 스냅샷)를 읽는다 — 결정 3-6 준수. 이 스펙이 `point_transactions_select_own`을 여니 **올바른 값을 읽을 수 있다**(관리자 아카이브가 표시할 수 없었던 이유가 여기서는 사라진다).
  - 원칙 4는 **"시각적 우선순위"**를 요구하지 조항이 아니다. 요약 3칸은 활동 수이고 상단은 StackViz이므로 위계는 유지된다. `QrCenterModal`의 `+NNNP 적립`(작은 amber 보조)과 같은 계열.

- L-2: **아예 표시하지 않는다.** 원칙 4에 가장 강하고 `admin-students.md` 결정 D와 완전히 일치한다.
  - "포인트는 마이페이지가 전담한다"는 역할 분담이 깔끔해진다. 다만 프로토타입 카피와 어긋나고, 학생이 "이 활동으로 얼마 받았지"를 원장에서 역추적해야 한다.
- L-3: 아카이브 요약에 **누적 포인트 칸**까지 추가(프로토타입 `savePDF` 1336줄 형태). **비추천 — 원칙 4 정면 위반.** 요약 3칸이 활동 수라는 것이 위계의 핵심이다.

## 알려진 이슈 / 구현 시 주의

### 이슈 1 — `archiveService.js`와 `print.css`는 **두 스펙이 공유하는 파일인데 아직 둘 다 없다**

`admin-students.md`가 신규로 지정한 파일 2개(`src/lib/archiveService.js`, `src/styles/print.css`)가 **아직 구현되지 않았다.** 이 스펙도 같은 파일을 쓴다.

- **먼저 구현되는 쪽이 파일을 만들고, 나중 쪽이 확장한다.** 파일을 복제하면 두 아카이브의 인쇄 규칙과 결합 로직이 갈라진다.
- 이 스펙이 먼저 구현된다면: `archiveService.js`를 만들 때 **학생 id에 의존하지 않는 결합 함수**로 짜서 관리자 쪽이 그대로 쓸 수 있게 한다.
- `print.css`는 **전역 1개**다. 학생 전용 규칙과 관리자 전용 규칙을 한 파일에서 클래스로 구분한다.

### 이슈 2 — 학생 쪽 게시중단 열화는 **관리자 쪽보다 심각하다**

`admin-students.md` 이슈 2가 확인한 대로, 관리자는 자기가 만든 미게시 프로그램을 계속 읽을 수 있어(`programs_select_own_as_admin`) 열화가 거의 발생하지 않는다. **학생은 다르다** — `programs_select_published`뿐이라 **내려진 프로그램을 실제로 못 읽는다.**

- 즉 **이 화면에서는 방어적 렌더가 이론이 아니라 실제 경로다.** 관리자가 "내리기" 한 번만 눌러도 학생 아카이브에서 재현된다.
- 검증이 쉬운 만큼 **인수 조건 7번을 반드시 실행할 것**(관리자 쪽처럼 SQL로 `created_by`를 조작할 필요조차 없다).

### 이슈 3 — 전환·계열 저장 후 **`AuthContext`의 `profile`이 낡는다** (놓치기 쉬움)

`profile`은 로그인 시 한 번 조회되어 컨텍스트에 들어간다. 전환은 `points_balance`/`currency_balance`를, 계열 저장은 `career_interest`를 바꾸는데, **컨텍스트를 갱신하지 않으면:**

- 마이페이지 잔액이 예전 값으로 남는다(모달만 닫히고 숫자가 그대로 = 가장 나쁜 종류의 불일치).
- **홈 추천이 안 바뀐다** — `StudentHomePage`의 `useEffect`가 `[profile]`을 의존성으로 갖는데(72줄 계열), 컨텍스트가 그대로면 재조회가 일어나지 않는다. 계열을 바꾼 학생 입장에서는 **기능이 고장 난 것처럼 보인다.**

→ **`AuthContext`에 profile 갱신 경로가 필요하다**(RPC 반환값으로 갱신하거나 `profiles`를 재조회). 전역 새로고침(`window.location.reload()`)으로 때우지 말 것.
→ backend 요구 4-4와 연결: **RPC가 갱신된 값을 반환하면 왕복 1회를 아낄 수 있다**(architect 판단 사항).

### 이슈 4 — 아카이브가 **4개 조회에 의존한다** (실패 격리)

`participations` / `programs` / `reviews` / (L-1 채택 시) `point_transactions`. **하나가 실패해도 나머지가 떠야 한다.**

- 리뷰 조회 실패 → 활동 목록은 뜨고 평가 줄만 "평가 상태 확인 불가"
- 원장 조회 실패 → 활동 목록은 뜨고 포인트 칸만 비움
- **가장 나쁜 구현**: `Promise.all` 하나로 묶어 한 개만 실패해도 전체가 catch로 떨어지는 것. `Promise.allSettled` 또는 개별 try/catch.

### 이슈 5 — `point_transactions`와 `participations`를 잇는 축은 `related_participation_id`다

포인트 내역에 활동명을 붙이려면 `related_participation_id` → `participations.program_id` → `programs.title` **2단 결합**이 필요하다.

- **embed 금지**(정의자 권한 함정). 3쿼리 + 클라이언트 Map.
- **전환 행은 이 축이 NULL이다** — 결합 시 `undefined` 접근으로 죽지 않게 방어.
- 마이페이지가 이미 아카이브와 같은 데이터를 상당 부분 읽는다. **두 화면이 각자 조회하되 서비스 함수는 공유**한다(중복 호출은 데모 규모에서 문제가 아니다).

### 이슈 6 — `reviews`가 생기면 ADR 0005의 경고가 발동한다

ADR 0005 "향후 변경"이 적었다: *"`participations`에 컬럼이 추가되면 또 `participations_insert_own`을 재검토해야 한다."*

- **이 스펙은 `participations`에 컬럼을 추가하지 않는다**(별도 `reviews` 테이블). 따라서 그 재검토가 **발생하지 않는다** — 이것이 별도 테이블을 택하는 부수적 이득이다.
- 만약 architect가 `participations.rating`/`comment` 컬럼 방식을 검토한다면, **`participations_insert_own`의 9절 `with check` 재검토가 함께 따라온다는 점**을 비용에 넣을 것. 그 정책은 "한 절만 빠져도 관리자 무한 적립이 열린다"고 마이그레이션 주석이 명시한 자리다.
