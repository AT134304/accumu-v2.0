# 관리자 프로그램 관리 (올리기 / 내리기 / 수정)

## 영향 범위
**관리자 화면 주도 + 학생 화면 일부** (`/admin/programs` 신규, 학생 참여 신청 경로 1곳 개정).
※ **관리자 기능 3종 중 1번**(CLAUDE.md 2장 6번 / 10장). 범위 확장 아님.
※ **[초안 대비 변경] backend 작업이 있다.** 확정 F(정원 차단)로 `participations` 신청 경로에 **정원 검사가 추가**된다. 프로그램 관리 자체(올리기/내리기/수정)는 기존 RLS 정책 3개로 충분해 frontend만으로 성립하지만, **정원 차단은 DB 경계라 architect/backend를 거쳐야 한다**(아래 "F. 정원 차단" 절 전체).
※ 관리자가 등록/수정/게시중단한 결과는 **학생 화면에 즉시 반영된다**(프로그램 선택 화면·홈 추천이 `is_published = true`를 읽는다).

## 배경 / 왜 필요한가

ADR 0005 "추가 확정"이 구현을 2단계로 나눴고, **1단계(QR 발급 → 입장 → 퇴장 → 포인트 + 관리자 셸·홈·스캔)는 완료**됐다. `/admin/programs`는 지금 `AdminPlaceholderPage`("화면 준비 중")로 연결돼 있다(`src/App.jsx` 65~75줄).

즉 현재 관리자는 **자기가 올린 프로그램을 스캔할 수만 있고, 올릴 수는 없다.** 프로그램은 전부 `scripts/seed-programs.mjs`가 심은 20건뿐이고, 앱 안에서 프로그램이 태어나는 경로가 존재하지 않는다. 시연에서 "관리자가 프로그램을 올린다 → 학생 계정으로 로그인해 그 프로그램이 보인다 → 신청한다 → QR로 인증한다"라는 **가장 설득력 있는 한 바퀴가 여기서 끊긴다.**

이번 스펙이 채우는 것은 정확히 그 한 칸이다. 그리고 **이 화면은 앱 최초의 "관리자가 임의의 값을 직접 테이블에 넣는" 화면**이다 — 지금까지 관리자의 쓰기는 전부 `verify_participation_qr()` RPC 안에 있었다(토큰 문자열 하나만 넘기는 좁은 문). 그래서 값 검증(특히 `points`)과 에러 처리가 이 스펙의 실질적 무게중심이다.

### 프로토타입 레퍼런스가 없다 (중요)

`Accumu_prototype.html`은 **학생 화면 10개만** 담고 있다(`screen-` 10개, "admin" 문자열 0건). 관리자 프로그램 관리 화면의 시각 레퍼런스는 존재하지 않는다.
→ **시각 언어는 `AdminHomePage.jsx` + `src/styles/AdminShell.css`의 `.adm-list` / `.adm-row`를 확장해서 만든다.** 새 디자인 언어를 발명하지 않는다.

### D 함정 — `is_published`를 **명시적으로 `false`로 보내야 한다**

`public.programs.is_published`의 **DB default는 `true`다**(`20260716120000_add_programs_and_career_track.sql` 119줄).
→ insert payload에서 이 컬럼을 **생략하면 default가 먹어서 바로 게시된다.** 즉 확정 D(초안 저장)는 "아무것도 안 하면 되는 것"이 아니라 **한 줄을 명시적으로 써야 성립한다.**

```js
// createProgram — is_published: false 를 지우지 말 것.
// 이 줄이 없으면 DB default(true)가 먹어서 "초안 저장"이 조용히 "즉시 게시"가 된다.
// 화면·토스트·배지는 전부 초안이라고 말하는데 학생에게는 이미 보이는 상태가 된다 = 가장 나쁜 종류의 불일치.
.insert({ ...fields, created_by: adminId, is_published: false })
```

- **DB default를 `false`로 바꾸지 않는다.** 그건 새 마이그레이션이고, 시드(`is_published: true`를 명시하는 20건)와 학생 화면 전제를 함께 흔든다. **default는 방어가 아니다**(ADR 0004 주의 4) — 방어는 명시적 전송이다.
- **수정(update) 요청에는 `is_published`를 아예 넣지 않는다.** 넣으면 게시중인 프로그램을 수정 저장하는 순간 초안으로 되돌아가거나, 반대로 초안이 게시된다. 게시 상태를 바꾸는 유일한 경로는 목록의 올리기/내리기 토글이다.

### D — "초안"과 "미게시"는 **같은 상태다** (표현을 통일한다)

DB에는 초안을 구분하는 컬럼이 없다. `is_published = false` 하나뿐이고, **"아직 한 번도 안 올린 것"과 "올렸다가 내린 것"을 구분할 수단이 없다**(`created_at`으로 추측하지 않는다 — 추측은 틀린다).

→ **구분하지 않는다. 새 컬럼을 만들지 않는다.** 확정 B의 표현을 그대로 공유한다:

| 상태 | 배지 | 행 스타일 | 액션 버튼 |
|---|---|---|---|
| `is_published = true` | **"게시중"** (brand blue soft) | 기본 | `수정` / **`내리기`** |
| `is_published = false` | **"미게시"** (회색) | `opacity` 저하 | `수정` / **`올리기`** |

- 액션 문구는 **"올리기"로 통일**한다. "다시 올리기"라고 쓰면 처음 올리는 초안에 대해 거짓말이 된다.
- 등록 직후 흐름: 저장 → 모달 닫힘 → 목록에 **미게시 행으로 나타남** + 토스트 **"초안으로 저장했어요. '올리기'를 눌러야 학생에게 공개됩니다."**
- **[C 확정과의 상호작용 — 놓치면 시연이 답답해진다]** 목록이 날짜 축 정렬이라 새 초안은 **맨 위가 아니라 날짜 위치에 꽂힌다.** 그대로 두면 "저장했는데 어디 갔지?"가 된다.
  → **저장 직후 그 행으로 스크롤 + 짧은 하이라이트**(2초 내외, 담백하게)를 **필수 요구사항으로 둔다.** D 채택으로 이 장치의 중요도가 올라갔다.
- 등록 모달의 저장 버튼 문구 = **"초안으로 저장"**. 폼 하단 안내 한 줄: "저장하면 학생에게는 아직 보이지 않습니다. 목록에서 '올리기'를 눌러 공개하세요."
- 수정 모달의 저장 버튼 문구 = **"저장"**(게시 상태를 바꾸지 않는다).

## 사용자 시나리오

### 시나리오 1 — 올리기 (등록 → 초안 → 공개)
1. 관리자가 좌측 네비 "프로그램 관리"를 눌러 `/admin/programs`로 들어온다.
2. 우측 상단 "새 프로그램 올리기"를 누른다 → 모달.
3. 활동 유형(교내 방과후…), 제목, 주최, 설명, 날짜, 시간, 진로 계열, 지급 포인트를 채운다. 정원은 비워둘 수 있다.
4. 포인트 칸에 `175`를 넣자 **저장 버튼이 잠기고** "포인트는 150~3,000P 사이의 10원 단위여야 합니다"가 뜬다. `180`으로 고치니 풀린다.
5. "초안으로 저장" → 모달이 닫히고 목록의 날짜 위치로 스크롤되며 **"미게시" 배지가 붙은 흐린 행**이 잠깐 하이라이트된다. 토스트: "초안으로 저장했어요. '올리기'를 눌러야 학생에게 공개됩니다."
6. 학생 계정으로 확인하면 **아직 안 보인다.**
7. 관리자로 돌아와 그 행의 "올리기"를 누른다 → 배지가 "게시중"으로 바뀌고 흐림이 풀린다.
8. 학생 계정에서 프로그램 선택 화면에 그 프로그램이 실제로 보이고, 신청할 수 있다.

### 시나리오 2 — 내리기
1. 게시중인 프로그램의 "내리기"를 누르면 **확인 창**이 뜬다:
   > 학생에게 더 이상 보이지 않게 됩니다. **이미 신청한 학생의 참여 기록과 QR 인증은 그대로 유지**되지만, 학생 화면에서 이 프로그램의 제목·날짜가 "게시가 중단된 프로그램"으로 표시됩니다. 언제든 다시 올릴 수 있습니다.
2. 확인 → 행이 흐려지고 "미게시" 배지가 붙는다.
3. 그 프로그램에 이미 신청했던 학생은 **QR 발급 → 입장 → 퇴장 → 포인트 지급이 전부 그대로 동작한다**(결정 7-4).

### 시나리오 3 — 수정
1. 목록 행의 "수정"을 누르면 등록과 **같은 모달**이 기존 값으로 채워져 열린다.
2. 포인트 칸 아래에 항상 이 안내가 붙어 있다:
   > 포인트를 바꿔도 **이미 지급이 끝난 학생의 포인트는 변경되지 않습니다.** 이후 퇴장 인증부터 새 금액이 적용됩니다.
3. 시간을 `15:30–17:00` → `16:00–18:00`으로 고치고 저장 → 목록과 학생 화면에 즉시 반영된다. **게시 상태는 그대로다.**

### 시나리오 4 — 정원 (확정 F)
1. 관리자가 새 프로그램을 만들며 정원에 `1`을 넣는다. 정원 칸 아래 안내: "정원을 채우면 새 신청이 막힙니다. **정원을 줄여도 이미 신청한 학생은 취소되지 않습니다.**"
2. 올리기 → 학생 A가 신청 성공.
3. 학생 B가 같은 프로그램에 신청 → **DB가 거부**하고 학생 화면에 "정원이 모두 찼습니다"가 뜬다. 카드/팝업 버튼이 마감 상태로 바뀐다.
4. 학생 B가 개발자도구로 프런트 방어를 우회해 직접 insert를 쏴도 **똑같이 거부된다**(판정 소유자가 DB이므로).
5. 관리자 화면에는 **"1/1명" 같은 숫자가 어디에도 뜨지 않는다** — 관리자는 신청자 수를 알 권한이 없다(F-3).

### 시나리오 5 — 거부 경로
1. 관리자가 다른 탭에서 로그아웃한 뒤 저장을 누른다 → **"권한 오류"**로 분리 표시되고 로그인으로 유도된다(정상 사용에서는 발생하지 않는다 = 발생하면 버그).
2. 개발자도구로 프런트 검증을 우회해 `points: 175`를 보낸다 → DB CHECK(`programs_points_rule`)가 `23514`/400으로 거부하고, 화면은 조용히 넘어가지 않고 사유를 보여준다.

## 화면 구성 요소

### A. 목록 (`/admin/programs`)

1. **섹션 헤더** — eyebrow `Programs` / 제목 "프로그램 관리" / 서브 "내가 올린 프로그램을 관리합니다" + 우측 **"새 프로그램 올리기"** 버튼(`.adm-scanall` 계열, brand blue).
2. **행 = `.adm-row` 확장** — 카테고리 아이콘(soft 배경) + 제목 + 메타(`그룹 · 카테고리 · 주최 · 날짜 · 시간`) + **게시 배지** + **모집 상태 배지**(`STATUS[].cls`) + 포인트(amber, 작게) + 액션 2개(`수정` / `올리기`·`내리기`).
3. **게시 상태 표현 (확정 B)** — 위 "초안과 미게시는 같은 상태다" 표 그대로. 한 목록 안에서 배지 + 흐림.
4. **그룹 (확정 C)** — 날짜 축으로 2그룹:
   - **"오늘 · 예정"** — `date >= todayISO()`, 날짜 **오름차순**(가까운 것 먼저). 기본 펼침.
   - **"지난 프로그램"** — `date < todayISO()`, 날짜 **내림차순**. **기본 접힘**(`<details>` 또는 동등한 토글).
   - 날짜 판정은 `src/lib/date.js`의 `todayISO()`(로컬/KST). **`toISOString()` 금지.**
   - 미게시 행도 이 축 안에 섞인다(게시 상태로 그룹을 나누지 않는다 — 확정 B).
5. **저장 직후 하이라이트** — 위 "D — C 확정과의 상호작용" 참고. 등록·수정·토글 후 해당 행으로 스크롤 + 짧은 하이라이트.
6. **빈 상태** — "아직 올린 프로그램이 없습니다. 우측 상단에서 새 프로그램을 올려보세요."
7. **표시하지 않는 것 (원칙 가드)** — 참여자 수 / **정원 대비 신청 수(`N/20명`)** / 신청자 명단 / 출석률 / 랭킹 / `popularity`. 상세 근거는 F-3.

### B. 등록·수정 모달 (확정 A)

**등록과 수정은 같은 폼 컴포넌트**를 쓴다(모드만 다름). 다른 폼 2개를 만들면 검증 규칙이 갈라진다.

| 필드 | DB | 입력 | 필수 | 비고 |
|---|---|---|---|---|
| 활동 유형 | `category` (enum 8종) | 드롭다운 (`CAT` 맵) | **O** | 자유 입력 금지 — enum 위반은 `22P02` |
| 제목 | `title` text | 텍스트 | **O** | |
| 주최 | `org` text | 텍스트 | **O** | **NOT NULL이다.** 빠뜨리면 `23502` |
| 설명 | `description` text | textarea | **O** | **NOT NULL.** 학생 참여 팝업이 이 값을 표시한다 |
| 날짜 | `date` date | date input | **O** | 확정 H: 과거 날짜 **허용 + 경고**. `todayISO()` 기준 |
| 시간 | `time` **text** | 텍스트 | **O** | **time 타입이 아니다.** "방과후", "무박 2일" 같은 값이 들어간다 → **time picker 쓰지 말 것** |
| 진로 계열 | `career_track` (enum 5종) | 드롭다운 (`TRACK` 맵) | **O** | **NOT NULL.** 빠지면 학생 홈 추천의 매칭 축에서 누락된다 |
| 지급 포인트 | `points` integer | 숫자 (`step=10`) | **O** | 확정 G. **150~3000 / 끝자리 0** |
| 정원 | `capacity` integer | 숫자 (`min=1`) | X | **확정 F.** 빈칸 = 정원 미정(무제한). 아래 F 절 전체 |
| 모집 상태 | `status` (enum 5종) | 드롭다운 (`STATUS` 맵) | 기본 `open` | **확정 E** |
| 게시 여부 | `is_published` | **폼에 만들지 않는다** | 등록 시 `false` 명시 전송 | **확정 D.** 위 "D 함정" |
| 등록자 | `created_by` | **폼에 만들지 않는다** | 본인 id를 명시적으로 전송 | "default는 방어가 아니다"(ADR 0004 주의 4) |
| 인기도 | `popularity` | **폼에 만들지 않는다** | — | 원칙 1 가드. DB default 0 |

**폼에 절대 만들지 않는 것**: `popularity`(원칙 가드), `id`/`created_at`(DB 소유), **삭제 버튼**(delete 정책 0개 — 만들어도 동작하지 않는다).

#### 포인트 검증 (확정 G — 프런트 + DB 이중)

- 규칙: `150 <= points <= 3000` **and** `points % 10 === 0` (CLAUDE.md 7장 = DB `programs_points_rule`).
- **프런트 사전 검증**: 위반 시 저장 버튼 비활성 + 필드 아래 인라인 사유. 서버를 왕복시키지 않는다.
- **DB CHECK도 반드시 처리**: 프런트 검증은 개발자도구로 우회 가능하고, 우회하면 `23514`/HTTP 400이 온다. 이 코드를 "알 수 없는 오류"로 뭉개지 말고 **어느 필드가 왜 거부됐는지** 보여준다(`error.message`에 제약 이름이 들어온다: `programs_points_rule` / `programs_capacity_positive`).
- **[원칙 4]** 포인트 입력 칸을 폼 상단이나 강조 위치에 두지 않는다. **제목·유형·설명 아래**, amber는 값 표시에만.

#### 날짜 경고 (확정 H)

- `date < todayISO()`면 저장을 막지 않고 **필드 아래 경고**: "이미 지난 날짜입니다. 학생은 이 프로그램에 신청할 수 없습니다."
- 근거: 학생 쪽 지난 날짜 신청 차단은 확정 H-1로 이미 성립한다. 관리자 쪽에서 한 번 더 막으면 시드의 과거 행("수학 심화 탐구반")을 수정조차 할 수 없게 된다.

#### 정원 안내 (확정 F)

- 정원 필드 아래 **항상 표시**(값 유무·모드와 무관):
  > 비워두면 정원 제한이 없습니다. 정원을 채우면 새 신청이 막힙니다. **정원을 줄여도 이미 신청한 학생은 취소되지 않습니다.**
- 조건부 문구("현재 N명 신청")를 만들 수 **없다** — F-3.

#### 포인트 수정 안내 (확정 I)

- **수정 모드에서만**, 포인트 필드 아래 **항상 표시**(값을 바꿨는지와 무관):
  > 포인트를 바꿔도 이미 지급이 끝난 학생의 포인트는 변경되지 않습니다. 이후 퇴장 인증부터 새 금액이 적용됩니다.
- 근거: 그 프로그램에 참여자가 있는지 알 수 있는 권한이 없어(결정 7-2(d)) **조건부 표시가 구조적으로 불가능하다.**

### C. 내리기 확인 창 (확정 J)

`Modal.jsx` 재사용. **되돌릴 수 있는 동작이지만 학생 화면에 열화가 생기므로 고지가 필요하다**(결정 7-4).

- 고지 문구는 **참여자 유무와 무관하게 항상 같다.** "신청자가 3명 있습니다" 같은 조건부 문구는 **만들 수 없다**(F-3).
- "올리기"는 확인 창 없이 즉시 실행(위험이 없다).

## F. 정원 차단 (확정 F) — **backend 요구사항**

> **이 절은 backend-agent가 그대로 구현할 수 있도록 "무엇이 성립해야 하는가"만 적는다.**
> **설계(RLS with check 확장 / `before insert` 트리거 / `security definer` RPC / 잠금 방식 / 함수 시그니처)는 architect·backend의 몫이며 이 스펙이 정하지 않는다.**
> 다만 이 프로젝트가 이미 밟은 함정은 F-8에 적어둔다 — 선택지를 좁히려는 게 아니라 **같은 벽에 두 번 부딪히지 않기 위해서**다.

### F-1. 거부 판정의 소유자는 **DB**다

- 학생이 정원이 찬 프로그램에 신청하면 **거부된다.**
- **프런트 조건문으로만 막는 것은 요구사항 미충족이다.** 이 프로젝트의 기존 규율 그대로다:
  - 중복 신청 → `unique (student_id, program_id)` (ADR 0004)
  - 미게시 프로그램 신청 → `participations_insert_own`의 `is_published = true` 서브쿼리 (결정 6-3)
  - 이중 포인트 지급 → CAS + `unique (related_participation_id)` (결정 3-3)
  - 정원도 같은 층에 있어야 한다.
- **검증 방법**: 개발자도구/`curl`로 프런트를 우회해 `insert into participations`를 직접 쏴도 거부되어야 한다.

### F-2. "찼다"의 기준 — **status와 무관하게 그 프로그램의 참여 행 수**

```
정원이 찼다  ⇔  capacity IS NOT NULL  AND  count(participations where program_id = P) >= capacity
```

| 항목 | 확정 | 근거 |
|---|---|---|
| `applied`를 세는가 | **센다** | 신청 = 자리 예약이다. `applied`를 빼면 신청이 사실상 무제한이 되고 정원은 "입장 시점"에만 의미를 갖는데, 입장은 QR 스캔이라 **현장에 온 학생을 돌려보내는 지점**이 된다. 그건 정원 기능이 아니라 사고다 |
| `entered` / `completed`를 세는가 | **센다** | 상태 전이는 `applied → entered → completed` **단방향**이다(결정 1-4). 어느 상태든 "그 프로그램의 자리를 차지한 학생 1명"이다 |
| 결론 | **`status`를 조건에 넣지 않는다.** `count(*) where program_id = P` | 상태별 분기가 없으므로 규칙이 단순하고, 전이 도중 count가 흔들리지 않는다 |
| 취소로 인한 유령 자리 | **존재할 수 없다** | `participations`에 **delete 정책 0개 / update 정책 0개**(결정 2-1). 학생도 관리자도 행을 지우거나 되돌릴 수 없다 → **count는 단조 증가**한다. 시연 리셋(`service_role`)만 예외 |
| 중복이 count를 부풀리는가 | **아니다** | `unique (student_id, program_id)`가 이미 1인 1행을 보장한다(ADR 0004) |
| `capacity IS NULL` | **무제한.** 검사 자체를 하지 않는다 | 컬럼 주석의 "NULL = 정원 미정/무제한" 유지 |

**[회귀 위험이 낮다는 점을 명시]** 시드 20건은 **전부 `capacity IS NULL`**이다(`scripts/seed-programs.mjs`). 따라서 이 기능이 들어가도 **기존 시드 프로그램의 신청 동작은 한 건도 바뀌지 않는다.** 정원 차단은 "관리자가 이번 화면에서 정원을 입력한 프로그램"에만 발동한다.

**[남는 열화 — 수용]** 확정 C-1이 지적했던 "신청했지만 안 온 학생이 자리를 막는다"는 문제는 그대로 남는다. 취소 기능이 없기 때문이다(확정 G-1 유지). **수용한다.** 취소가 생기면 이 규칙을 재검토한다.

### F-3. 관리자 화면에 신청자 수를 표시하는가 → **표시하지 않는다** (PM 판단)

**차단(기능)과 숫자 노출(UI)은 별개 문제이고, 이 프로젝트에서는 분리된다.**

| 질문 | 답 |
|---|---|
| 차단은 하되 숫자는 안 보여주는 게 가능한가 | **가능하다.** 정원 검사는 **서버 안에서만** 일어난다. 서버는 count를 알지만 **그 값을 응답으로 내보내지 않는다.** 클라이언트에 필요한 것은 "성공/거부" 한 비트뿐이다 |

**표시하지 않는 이유 3가지:**

1. **원칙이 금지한다.** CLAUDE.md 2장 1번(게임화 배제) + ADR 0005 결정 7-5의 명시적 가드: "관리자 홈에 참여자 수·신청자 명단·출석률·학생 랭킹·학교 단위 통계를 표시하지 않는다." `N/20명`은 정확히 **참여자 수 표시**다.
2. **권한이 없어서 셀 수도 없다.** 결정 7-2(d)에 따라 관리자에게 열린 `participations`는 **담당 학생 5명의 `completed` 행뿐**이다. 지금 화면에서 count를 하면 **틀린 숫자**가 나온다(담당 학생이 아닌 신청자, `applied`/`entered` 상태가 전부 빠진다). **틀린 숫자를 보여주는 것은 안 보여주는 것보다 나쁘다.**
3. **정확한 숫자를 보여주려면 열지 않기로 한 권한을 열어야 한다.** 프로그램별 신청자 수 집계 권한(집계 함수든 정책이든)은 ADR 0005가 의도적으로 닫아둔 표면이고, 결정 7-2(d)는 이 닫힘이 **"원칙 1·6이 UI 규율이 아니라 RLS 구조로 성립"**하게 만드는 장치라고 못박았다. 정원 표시 하나 때문에 그 구조를 깨는 것은 비용이 훨씬 크다.

> **핵심 정리:** 정원 차단은 **서버가 아는 사실**이고, 신청자 수는 **관리자에게 보여주는 정보**다. 이번에 여는 것은 앞의 것뿐이다.

#### 그러면 관리자가 정원을 줄이려 할 때 어떤 경험이 되는가

**"현재 몇 명인지 모르는 채로 줄인다."** 이 불편을 없애려면 위 3번(권한 확장)이 필요하므로, **불편을 수용하고 대신 예측 가능하게 만든다:**

- 정원 필드 아래 **항상 표시되는 안내**(값·모드와 무관):
  > 비워두면 정원 제한이 없습니다. 정원을 채우면 새 신청이 막힙니다. **정원을 줄여도 이미 신청한 학생은 취소되지 않습니다.**
- **정원을 줄이는 update 자체는 막지 않는다.** 막으려면 서버가 "현재 신청 수 > 새 정원"을 판정해 관리자에게 알려야 하는데, 그 응답은 **신청자 수를 간접적으로 노출하는 오라클**이 된다("18은 되는데 17은 안 되네" → 정확히 17명). → **막지 않는 편이 정보 노출도 없고 규칙도 단순하다.**
- 결과적으로 관리자에게 정원은 **"이 이상은 안 받겠다"는 선언**이지, 현재 상태를 조회하는 계기판이 아니다. 데모 관리자는 케빈 1인이고 시연 시나리오를 본인이 알고 있으므로 실사용에 지장이 없다.

**[학생 화면 쪽 파생 — 사전 표시가 아니라 사후 거부다]**
같은 논리가 학생 화면에도 적용된다. 학생은 `participations_select_own`뿐이라 **남의 신청을 셀 수 없다.** 따라서 학생 화면은 "남은 자리 N석" 같은 사전 표시를 할 수 없고, **신청을 시도한 뒤 거부 사유로 마감을 알게 된다.**
- 완화 1: 거부 직후 그 카드/팝업을 **즉시 마감 상태로 로컬 갱신**한다(같은 세션에서 반복 시도하지 않게).
- 완화 2: 관리자가 `status`를 `full`(마감)로 바꾸면 학생 화면에 사전 표시된다 — 확정 E로 이 수단이 이미 열려 있다. 다만 이건 **관리자의 수동 운영**이지 자동 파생이 아니다(F-5).
- **이 열화를 없애려면 "정원이 찼는가"를 알려주는 boolean 노출 경로가 필요하다. 이번 스코프가 아니며, 원하면 별도 확정이 필요하다** → 아래 "추가 케빈 확인 필요 K".

### F-4. 정원을 나중에 **줄였을 때** — 이미 신청한 학생을 **쫓아내지 않는다**

| 항목 | 확정 |
|---|---|
| 초과 신청 학생의 `participations` 행 | **남는다** |
| 그 학생의 QR 발급 / 입장 / 퇴장 / 포인트 지급 | **전부 그대로 동작한다** |
| 신규 신청 | `count >= capacity`이므로 **계속 거부된다** |
| `capacity < 실제 신청 수` 상태 | **정합성 위반이 아니라 "정원 초과 상태"로 수용한다** |

**근거:**
1. **기술적으로 불가능하다.** 관리자는 `participations`를 지우거나(delete 정책 0개) 고칠(update 정책 0개) 권한이 없다. 이건 누락이 아니라 ADR 0005 결정 2-1의 **핵심 설계**다. 쫓아내는 기능을 만들려면 이번에 열지 않기로 한 update/delete 경로를 열어야 한다.
2. **철학이 이미 정해져 있다.** 결정 7-4(게시중단)가 같은 판단을 내렸다 — **"관리자의 사후 조작이 이미 신청한 학생의 인증 흐름을 끊지 않는다."** 정원 축소도 같은 계열의 사후 조작이므로 같은 답이어야 한다. 여기서 다른 답을 내면 학생 입장에서 "언제 내 신청이 사라질지 모르는 앱"이 된다.
3. **포인트 정합성.** 이미 `completed`인 학생을 되돌리면 `point_transactions`와 `profiles.points_*`를 함께 되돌려야 한다(결정 3-3의 멱등 구조가 역방향을 상정하지 않는다). 그건 별도 설계다.

→ **정원 검사는 "insert 시점의 게이트"일 뿐, 기존 행에 소급 적용되지 않는다.** 이 문장을 마이그레이션 주석에 남길 것.

### F-5. `status` 파생 전환은 **여전히 하지 않는다** (섞이기 쉬운 지점)

정원이 찼다고 해서 `programs.status`가 자동으로 `'full'`이 되지 **않는다.**

- `status`는 확정 E에 따라 **관리자가 수동 지정하는 정적 값**이다. 마이그레이션 주석("[ADR 0005] 관리자 프로그램 관리에서 이 값을 수동으로 지정한다 — 여전히 파생값이 아니다")이 그대로 유효하다.
- 파생시키려면 트리거가 `programs`를 쓰게 되고, "관리자가 손으로 정한 값을 서버가 덮어쓰는" 경로가 생긴다. 그러면 관리자가 `full`을 `open`으로 되돌려도 다음 신청 때 다시 `full`이 되는 등 **소유권이 모호해진다.**
- **정원 차단(DB 게이트)과 `status`(표시용 라벨)는 서로 독립이다.** 둘이 어긋난 상태(`status='open'`인데 정원이 참)가 존재할 수 있으며, **수용한다.** 그때 학생은 신청 시도 후 거부 사유로 알게 된다(F-3).

### F-6. 거부 신호는 **권한 오류와 구분 가능해야 한다** (강한 요구사항)

`participations` 신청 실패는 지금 이렇게 분류돼 있다:

| 사유 | 코드 | 프런트 처리 (`applyToProgram`) |
|---|---|---|
| 중복 신청 | `23505` | `'duplicate'` 반환 — 에러가 아니라 상태 동기화 신호 |
| RLS 거부(미게시/관리자 자기참여/컬럼 위조 등) | `42501` / 403 | throw → "권한 오류" |
| 네트워크 | — | throw |

**정원 마감이 `42501`로 뭉뚱그려져 오면 안 된다.** 그러면 학생 화면이 "정원이 찼습니다"와 "권한 오류(=버그 신호)"를 구분할 수 없다. 이건 ADR 0005 결정 4가 세운 규율 그대로다 — **권한 실패는 예외(42501), 도메인 실패는 구분 가능한 사유값.**

- **요구사항**: 정원 거부는 `42501`이 아닌 **식별 가능한 신호**로 와야 한다(전용 errcode, 제약 이름, 또는 RPC의 `{ok:false, reason:'full'}` — **어느 쪽인지는 backend가 정한다**).
- **프런트 영향**: `applyToProgram`의 반환값에 **`'full'`이 추가**된다(`'created' | 'duplicate' | 'full'`). 참여 팝업/카드가 이 값을 받아 "정원이 모두 찼습니다"를 표시하고 버튼을 마감 상태로 바꾼다.
- **[주의] 이 요구사항이 설계를 좁힌다.** `participations_insert_own`의 `with check`에 정원 절을 그냥 추가하면 위반이 `42501`로 나와 **미게시 신청·관리자 자기참여 거부와 구분되지 않는다.** 설계 시 반드시 고려할 것.

### F-7. 동시성 — 마지막 1자리를 두 명이 동시에 신청해도 **1명만 성공**

- 정원 1인 프로그램에 두 요청이 동시에 도착해도 **성공은 정확히 1건**이어야 한다.
- 이건 이 프로젝트에서 처음 생기는 요구가 아니다. 결정 3-3(이중 지급 방어)이 **CAS + unique 제약 2중**으로, 결정 1-4가 `select ... for update` 직렬화로 같은 성질을 이미 확보했다. **같은 수준의 방어를 정원에도 요구한다.**
- 순진한 `count(*) < capacity` 서브쿼리는 READ COMMITTED에서 **두 트랜잭션이 같은 count를 읽고 둘 다 통과**할 수 있다. 방법은 backend가 정하되, **"검사와 삽입 사이에 다른 트랜잭션이 끼어들 수 없음"**이 성립해야 한다.
- **검증 방법**: 정원 1인 프로그램에 두 계정으로 거의 동시에 신청 → 1건 성공 / 1건 정원 거부. `count`가 `capacity`를 넘긴 상태가 DB에 남지 않는다.

### F-8. 설계 시 반드시 검토할 함정 (선택지를 좁히려는 게 아니라 기록)

1. **정책 재귀.** `participations`의 정책 표현식 안에서 `participations`를 세면 Postgres가 정책 재귀를 감지해 에러를 낼 수 있다. ADR 0005 결정 7-2(a)가 `profiles`에서 정확히 같은 벽에 부딪혔고, `security definer` 헬퍼(`is_admin()`)로 풀었다. **같은 계열의 함정이다.**
2. **기존 `with check` 9절을 한 절도 지우지 말 것.** 특히 `not public.is_admin()`(결정 6-1(b): 관리자 무한 적립 폐루프 차단)과 `p.is_published = true`(결정 6-3). 마이그레이션 주석이 "이 두 절 중 하나만 빠져도 관리자 무한 적립이 열린다"고 명시했다.
3. **컬럼 단위 insert grant가 걸려 있다.** `participations`는 `grant insert (student_id, program_id)`뿐이다(결정 6-2). 정원 검사를 RPC로 옮긴다면 **학생용 insert 경로가 둘이 되지 않게** 정리해야 한다(경로가 둘이면 한쪽에만 정원 검사가 붙는 사고가 난다).
4. **`security definer`를 새로 만든다면** ADR 0005 결정 2-5의 체크리스트 전부 적용: `set search_path = ''` / `revoke all from public` 후 `grant execute to authenticated` / 본문이 곧 권한 경계 / 권한 실패는 예외, 도메인 실패는 반환값.
5. **`programs.capacity`를 읽는 방향에 새 권한이 필요한지 확인.** 학생은 게시된 `programs`를 select할 수 있으므로 `capacity` 값 자체는 이미 읽을 수 있다(RLS는 컬럼 단위가 아니다). **정원 상한은 비밀이 아니다 — 비밀인 것은 현재 신청 수다.**

### F-9. 확정 C-1 개정 요구 (문장 단위)

**ADR 수정은 architect/backend의 몫이지만, 근거와 범위는 이 스펙이 제공한다.**

**원문** — `docs/specs/student-programs.md` "확정된 결정":
> **C-1 정원 차단·`status` 파생 전환 둘 다 스코프 아님.** 시드 20건 전부 `capacity`가 NULL이라 정원 개념이 데모에 없고, 신청 가능 여부의 단일 소스는 정적 `status`(`STATUS[].join`)다. 파생 전환은 "참여 확정"(QR 입장)이 정의된 뒤 재결정.

**개정 1 — C-1이 묶어놓은 두 항목을 분리한다.**
C-1은 "정원 차단"과 "`status` 파생 전환"을 한 세트로 기각했다. **이번에 앞의 것만 뒤집히고 뒤의 것은 유지된다.** 따라서 개정의 첫 단계는 **두 항목을 분리해 각각 상태를 부여**하는 것이다.

| 항목 | 개정 후 상태 |
|---|---|
| 정원 차단 | **도입한다** (2026-07-30 확정 F) |
| `status` 파생 전환 | **여전히 하지 않는다** (C-1 유지. F-5) |

**개정 2 — "정원 개념이 데모에 없다"는 전제 문장을 갱신한다.**
- 삭제/개정 대상: "시드 20건 전부 `capacity`가 NULL이라 정원 개념이 데모에 없고"
- 대체 문장: **"시드 20건은 여전히 전부 `capacity`가 NULL이므로 기존 프로그램의 신청 동작은 바뀌지 않는다. 정원은 관리자 프로그램 관리 화면에서 입력한 프로그램에만 적용된다."**

**개정 3 — "신청 가능 여부의 단일 소스" 문장을 개정한다.**
- 삭제/개정 대상: "신청 가능 여부의 단일 소스는 정적 `status`(`STATUS[].join`)다"
- 대체 문장: **"신청 가능 여부는 두 층이다. (1) 화면 표시·버튼 활성 = 정적 `status`(`STATUS[].join`) + 날짜(확정 H-1). (2) 실제 거부 판정 = DB(중복·미게시·관리자 자기참여·정원). 표시는 프런트가, 경계는 DB가 소유한다."**

**개정 4 — `programs.capacity` 컬럼 주석을 갱신한다** (`20260723120000_...sql` 718~721줄).
- 뒤집히는 문장: "[ADR 0005] 관리자 프로그램 관리가 열려도 **정원 차단을 구현하지 않는다** — 시드 20건 전부 capacity가 NULL이라 정원 개념이 데모에 존재하지 않는다(확정 C-1 유지)."
- 새 주석에 담을 것: (a) NULL = 무제한(유지), (b) **정원 차단을 구현한다**(확정 F), (c) "찼다"의 기준 = `status` 무관 참여 행 수(F-2), (d) **기존 행에 소급 적용되지 않는다**(F-4), (e) **`status` 파생에는 여전히 사용하지 않는다**(F-5), (f) **신청자 수를 관리자/학생 화면에 노출하지 않는다**(F-3).

**개정 5 — `participations_insert_own`의 with check 주석을 갱신한다.**
정원 절이 정책에 들어가든 다른 장치로 가든, 해당 블록의 `[RLS 권한 경계]` 주석에 **"정원은 어디서 막히는가"**를 반드시 적는다. 지금 주석은 거부 사유를 7개 + unique로 열거하고 있고, **여기 없는 거부 사유가 생기면 다음 사람이 원인을 찾지 못한다.**

**개정하지 않는 것 (명시):**
- **ADR 0003 확정 D**(`status`·`popularity`는 정적 필드) — `status`를 파생시키지 않으므로 그대로.
- **확정 G-1**(신청 취소 스코프 아님) — 그대로. F-2가 "count 단조 증가"를 여기에 기대고 있다.
- **결정 7-2(d)**(관리자 참여 조회 = 담당 5명 completed) — **그대로.** F-3이 이 경계를 넓히지 않는다는 것이 이번 판단의 핵심이다.
- **결정 2-1**(`participations` update/delete 정책 0개) — **그대로.** F-4가 여기에 기대고 있다.

## 데이터/백엔드 영향

| 대상 | 이번 작업 |
|---|---|
| 프로그램 관리(올리기/내리기/수정) | **새 테이블·필드·정책·RPC·시드 0건.** 기존 RLS 정책 3개로 성립 (위 "전제") |
| **정원 차단 (확정 F)** | **새 마이그레이션 1건 필요.** architect(설계 판단) → backend(구현). 위 F 절 전체가 요구사항 |

### 이슈 1 — `update`가 0행이어도 에러가 아니다 (**이 스펙에서 가장 놓치기 쉬운 지점**)

RLS `using` 절에 걸린 update는 **에러가 아니라 "0행 영향"**으로 끝난다. `supabase-js`의 `.update()`는 이 경우 `error === null`을 돌려주므로, **권한 밖 행을 수정해놓고 성공 토스트를 띄우는 화면**이 만들어질 수 있다.

→ **모든 update에 `.select()`를 붙이고 반환 배열 길이가 1인지 확인한다.** 0이면 실패로 다룬다(문구: "이 프로그램을 수정할 권한이 없거나 목록이 오래됐습니다. 새로고침해 주세요").
※ `.select()`가 동작하는 근거: `programs_select_own_as_admin`이 본인 행 select를 이미 허용한다. 별도 권한 불필요.

### 이슈 2 — 관리자는 "이 프로그램에 신청자가 있는지" 알 수 없다 (경계이지 결함이 아니다)

결정 7-2(d)에 따라 관리자에게 열린 `participations`는 **담당 학생 5명의 `completed` 행뿐**이다. 따라서:
- "참여자 N명" / "N/20명" 표시 불가 → **원칙 1·6이 UI 규율이 아니라 RLS 구조로 성립한다** (상세: F-3)
- 내리기 확인 창의 문구를 참여자 유무로 분기할 수 없다 → **항상 같은 문구**
- 포인트 수정 경고(확정 I)·정원 축소 경고(확정 F)를 조건부로 띄울 수 없다 → **항상 표시**

이 제약을 우회하려고 집계 쿼리·뷰·RPC를 만들지 말 것. 그건 열지 않기로 한 권한을 여는 것이다.

### 이슈 3 — 새로 등록한 프로그램은 `popularity = 0`이다 (알려진 열화, 수용)

학생 프로그램 선택 화면의 기본 정렬이 **인기순**(확정 B-1)인데, 신규 등록 행은 `popularity = 0`이라 **모든 카테고리 행의 맨 뒤**에 붙는다.

- **`popularity`를 폼에 노출해 관리자가 조작하게 만들지 않는다** — 컬럼 주석이 명시적으로 금지한다.
- 완화: 시연 시 정렬을 **최신순**으로 바꾸면 맨 앞에 온다. **README/시연 메모에 한 줄 남긴다.**
- 이것을 이유로 정렬 기본값이나 `popularity` 설계를 바꾸지 않는다.

### 이슈 4 — `programs`에 `updated_at`이 없다

수정 시각을 기록할 컬럼이 없다. → **"수정됨" 표시나 수정 이력 UI를 만들지 않는다.**

### 조회/쿼리

```js
// 관리 목록은 수정 폼을 채워야 하므로 ADMIN_FIELDS(관리자 홈용)보다 넓다.
// popularity 는 가져오지 않는다: 화면에 쓰지 않는 값을 페이로드에 싣지 않는다(원칙 가드를 코드로 표현).
const ADMIN_MANAGE_FIELDS =
  'id, category, title, org, description, date, time, capacity, points, career_track, status, is_published, created_by, created_at';
```
- 단일 쿼리 + 클라이언트 필터/정렬. **뷰·PostgREST embed 금지**(정의자 권한 함정 — ADR 0003 6번 / ADR 0004 5번).
- `.limit(200)` 안전 상한 유지(기존 관례).

### 시드
- **추가 시드 불필요.** 미게시 fixture("교내 UCC 공모전")가 이미 있다(결정 8-3). **시드 20건의 `capacity`를 채우지 말 것** — NULL 유지가 F-2의 "회귀 없음" 근거다.
- 시연 리셋: 이번 화면이 만든 프로그램은 SQL로 지운다(**service_role/SQL 콘솔 전용** — 앱에 삭제 경로는 없다). 기존 리셋 절차(`participations` 삭제 + `points_*` 초기화)는 그대로.

## 스코프 아님 (Out of scope)

- **프로그램 삭제** — delete 정책 0개(결정 7-1). 게시중단으로 대체한다. 삭제는 `on delete cascade`로 학생의 `participations`·`point_transactions`까지 지우는데 `profiles.points_*`는 남아 **잔액과 원장이 어긋난다.** 시연 리셋(service_role) 전용.
- **참여자 수·정원 대비 신청 수·신청자 명단·출석률·랭킹·학교 통계** — 원칙 1·6. 데이터도 얻을 수 없다(F-3).
- **정원 초과 학생 강제 취소·대기열** — F-4. `participations` update/delete 정책 0개.
- **`status` 파생 전환** — F-5. 관리자 수동 지정 유지(확정 E).
- **`popularity` 편집·노출** — 이슈 3.
- **초안/미게시를 구분하는 별도 상태** — DB에 그 개념이 없다. 새 컬럼을 만들지 않는다(확정 D).
- **프로그램 복제 / 일괄 등록 / CSV 업로드 / 이미지 업로드** — 데모에 필요 없고 Storage 권한 표면이 새로 열린다.
- **수정 이력·감사 로그·`updated_at`** — 이슈 4.
- **다른 관리자의 프로그램 조회/수정** — 축 A(결정 7-0). 다중 관리자 관리 UI는 CLAUDE.md 2장 6번이 금지.
- **담당 학생 아카이브 + PDF** — 2단계의 나머지 절반. **별도 스펙.**
- **알림 연동("새 프로그램이 등록되었어요")** — `notifications` 테이블이 아직 없다. 알림 스펙 몫.
- **학생 화면의 사전 마감 표시("남은 자리 N석")** — F-3. 원하면 별도 확정 필요(아래 K).

## 추가 케빈 확인 필요 (F 채택으로 새로 생긴 것)

> **블로킹 아님.** K를 정하지 않아도 K-1(현재 스펙 내용)로 구현할 수 있다. 다만 시연 인상에 영향이 있어 남긴다.

### K. 학생 화면에 "정원 마감"을 **미리** 보여줄까 (사전 표시 vs 사후 거부)

F-3의 결론상 학생은 남의 신청을 셀 수 없어, 기본적으로 **신청을 눌러야 마감을 알게 된다.**

- **K-1 (PM 추천, 현재 스펙 내용): 사후 거부만.** 신청 → 거부 → "정원이 모두 찼습니다" + 버튼 즉시 마감 전환.
  - 추가 권한 0. 원칙 1·6과 완전히 무충돌. 관리자가 `status`를 `full`로 바꾸면 사전 표시도 된다(확정 E).
  - 단점: 정원이 찬 프로그램을 누른 학생 1명은 반드시 한 번 거부를 겪는다.
- **K-2: "찼는가" boolean만 노출.** 숫자가 아니라 참/거짓만 주는 경로를 만들어 카드에 미리 마감 표시.
  - 숫자를 안 주므로 **원칙 1을 직접 위반하지는 않는다.** 다만 `capacity`를 아는 상태에서 boolean이 뒤집히는 시점을 관찰하면 신청 수를 추론할 수 있고(오라클), **새 서버 표면(함수 또는 정책)이 하나 는다.**
  - ADR 0005가 닫아둔 방향과 맞닿아 있어 architect 판단이 한 번 더 필요하다.
- **K-3: 아무것도 안 한다.** 정원은 순수 서버 게이트로만 두고 학생 화면 문구도 손대지 않는다(일반 실패 메시지).
  - 가장 작지만 학생이 왜 실패했는지 모른다. **비추천.**

## 인수 조건 (Acceptance Criteria)

### 기능 동작 — 프로그램 관리
- [ ] `/admin/programs`가 "화면 준비 중" placeholder가 아니라 실제 목록을 보여준다
- [ ] 시드 20건이 전부 보인다(전부 `created_by = ADM-0001`)
- [ ] "교내 UCC 공모전"이 **"미게시" 배지 + 흐린 행**으로 보이고 액션이 **"올리기"**다
- [ ] "오늘·예정"과 "지난 프로그램"(기본 접힘) 2그룹으로 나뉘고, 날짜 정렬이 각각 오름/내림차순이다
- [ ] 새 프로그램을 저장하면 **"미게시" 행으로 나타나고**, 그 행으로 스크롤되며 잠깐 하이라이트된다
- [ ] **DB에서 확인: 방금 등록한 행의 `is_published`가 `false`다** (확정 D 함정 검증 — 여기가 `true`면 구현 실패)
- [ ] 등록한 프로그램의 `created_by`가 **로그인한 관리자 본인**이다 (DB에서 직접 확인)
- [ ] "올리기" → `is_published`가 `true`가 되고, "내리기"(확인 창 경유) → `false`로 돌아온다
- [ ] **게시중인 프로그램을 수정 저장해도 게시 상태가 유지된다** (수정이 `is_published`를 건드리지 않는다)
- [ ] 수정한 값(제목·시간·설명·모집 상태 등)이 목록과 DB에 실제로 반영된다
- [ ] **삭제 버튼이 화면 어디에도 없다**

### 기능 동작 — 정원 (확정 F)
- [ ] 정원 `1`인 프로그램을 만들어 올린 뒤, 학생 A 신청 성공 / **학생 B 신청 거부**
- [ ] 거부 문구가 **"정원이 모두 찼습니다"**이며 **"권한 오류"와 다른 문구**다 (F-6)
- [ ] **개발자도구로 프런트를 우회해 직접 insert를 쏴도 거부된다** (F-1 — 판정 소유자가 DB)
- [ ] 정원 1자리에 **두 계정이 동시에 신청 → 정확히 1건만 성공**하고, DB의 참여 행 수가 `capacity`를 넘지 않는다 (F-7)
- [ ] `capacity`가 NULL인 시드 프로그램은 **신청 동작이 이전과 완전히 동일하다** (F-2 회귀 확인)
- [ ] 학생 A/B가 신청한 뒤 관리자가 **정원을 1로 줄여도** 두 학생의 참여 행이 남아 있고, **QR 발급 → 입장 → 퇴장 → 포인트 지급이 전부 정상 동작한다** (F-4)
- [ ] 정원을 줄이는 update 자체가 막히지 않는다 (F-3)
- [ ] **정원이 차도 `programs.status`가 자동으로 바뀌지 않는다** (F-5)

### 학생 화면 연계 (계정을 오가며 확인)
- [ ] 초안(미게시) 상태에서는 학생 화면에 **보이지 않는다**
- [ ] "올리기" 후 학생 프로그램 선택 화면에 뜨고 **신청까지 된다**
- [ ] "내리기" 후 학생 목록·홈 추천에서 사라진다
- [ ] **이미 신청한 학생은 게시중단 후에도 QR 발급 → 입장 → 퇴장 → 포인트 지급이 전부 정상 동작한다** (결정 7-4 실증)
- [ ] 게시중단된 프로그램의 참여 건이 학생 QR 목록·stackviz·아카이브에서 **화면을 죽이지 않는다**(제목 자리에 대체 문구)

### 검증 / 거부 경로 (**전부 실제로 시도해볼 것**)
- [ ] `points = 175` 입력 → 저장 버튼이 잠기고 인라인 사유가 뜬다
- [ ] `points = 100` / `points = 5000` → 같은 방식으로 막힌다
- [ ] **개발자도구로 프런트 검증을 우회해 `points: 175`를 전송** → `23514`/400이 오고, 화면에 사유가 표시된다
- [ ] `capacity = 0` → `23514`(`programs_capacity_positive`)가 필드 오류로 표시된다
- [ ] 필수 필드를 비우면 저장되지 않는다
- [ ] 과거 날짜를 넣으면 **경고가 뜨지만 저장은 된다** (확정 H)
- [ ] 네트워크를 끊고 저장 → 모달이 닫히지 않고 입력값이 남아 있으며 재시도할 수 있다

### 권한 점검 (**anon 키 + 실제 계정으로 뚫어볼 것. service_role 금지**)
- [ ] **학생 계정으로 `insert into programs {created_by: 본인}`** → **403** (`programs_insert_own_as_admin`의 `is_admin()`)
- [ ] **학생 계정으로 `/admin/programs` 접근** → `ProtectedRoute(role="admin")`가 막는다
- [ ] **관리자가 `update programs set created_by = null`** → 0행 (`with check`)
- [ ] SQL로 어떤 프로그램의 `created_by`를 다른 uuid로 바꾼 뒤 → **그 행이 관리 목록에서 사라지고, 수정 시도는 0행**이 된다
- [ ] **관리자가 `delete from programs`** → 0행 (정책 0개)
- [ ] **관리자가 `insert into participations {student_id: 본인}`** → 403 (결정 6-1(b) 폐루프 차단이 정원 변경 후에도 유지)
- [ ] 관리자가 `select * from participations` → **여전히 담당 학생 5명의 `completed`만.** 프로그램 관리도, 정원 차단도 이 경계를 넓히지 않았다
- [ ] 학생이 `select count(*) from participations where program_id = ?` → **본인 행만 세진다** (남의 신청 수를 알 수 없다)

### 원칙 시각 점검
- [ ] 화면 어디에도 **참여자 수·`N/20명`·신청자 명단·출석률·랭킹**이 없다
- [ ] **"남은 자리 N석" / "마감 임박" 같은 희소성 연출이 없다**
- [ ] **`popularity` 숫자가 표시되지도, 편집되지도 않는다**
- [ ] 포인트가 목록에서 **작은 amber 한 칸**이고, 제목·카테고리(blue 계열)보다 시각적으로 앞서지 않는다
- [ ] 폼에서 포인트 칸이 상단·강조 위치에 있지 않다
- [ ] 수정 폼에 "이미 지급된 포인트는 변경되지 않습니다" 안내가 있다 (확정 I)
- [ ] 정원 필드에 "정원을 줄여도 이미 신청한 학생은 취소되지 않습니다" 안내가 있다 (확정 F)
- [ ] **이모지가 없다** — 새 아이콘 3종 전부 duotone SVG
- [ ] 초록 계열 색이 없다

### 반응형
- [ ] 980 / 768 / 600 / 430px에서 목록 행의 액션 버튼 2개와 배지 2종이 겹치거나 잘리지 않는다
- [ ] 모바일에서 모달이 하단 탭바에 가리지 않고, 필드 10개 폼이 스크롤된다
- [ ] 모바일에서 목록 행이 세로로 접히되 게시 배지가 계속 보인다
