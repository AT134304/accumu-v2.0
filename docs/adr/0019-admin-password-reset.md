# ADR 0019: 관리자의 담당 학생 비밀번호 초기화 (원칙 6 재개정 — 5번째 기능)

## 상태

확정 (2026-08-11, 케빈 요청 — 사용성 개선 라운드 14번 항목).

## 배경

케빈이 지목한 사용성 문제 14번: "비밀번호 찾기/재설정 기능이 없어 보임." 실제로 뜯어보니 단순한
누락이 아니라 이 앱의 로그인 설계 자체에서 비롯된 구조적 제약이었다.

- **학생(학교 계정)**: 학번 + 비밀번호. Auth 이메일은 `{학번}@accumu.local`.
- **관리자**: 관리자코드 + 비밀번호. Auth 이메일은 `{코드}@accumu.local`.
- **학생(개인 계정)**: 실제 이메일 + 비밀번호.
- **소셜 계정**: 비밀번호 자체가 없음(OAuth).

Supabase의 표준 비밀번호 재설정은 "이메일로 링크 발송"이다. 개인/소셜 계정은 문제가 없지만,
`@accumu.local`은 **받는 사람이 없는 가짜 도메인**이라 학생(학교 계정)·관리자에게는 애초에
작동할 수 없는 방법이었다. 이 구조를 만든 시점(ADR 0002)에는 재설정 자체가 스코프에 없어서
드러나지 않았던 문제다.

세 갈래 해법을 검토했다:

1. **본인확인 자서비스** — 학번+이름만으로 즉시 재설정. 구현은 가장 간단하지만, 학번·이름은 교실
   에서 공개적인 정보라 다른 학생이 재현할 수 있는 계정 탈취 경로가 된다. 기각.
2. **아무것도 만들지 않는다** — CLAUDE.md 1장의 "1인 시연용" 전제를 따르면 케빈이 Supabase
   대시보드에서 직접 바꿔주면 된다. 정직한 답이지만, 케빈이 명시적으로 다른 쪽을 골랐다.
3. **관리자 재설정 기능 추가** — 케빈이 최종 선택. 원칙 6을 다시 열어야 하지만(ADR 0015가 이미
   한 번 연 문을 한 번 더 여는 것), 담당 학생에 한해 관리자가 새 비밀번호를 발급해 줄 수 있게 한다.

케빈이 3번을 선택했다 — 이 ADR은 그 반영이다.

## 결정

### 결정 1 — "담당 학생 비밀번호 초기화"가 관리자 기능의 5번째가 된다

원칙 6을 "5가지 한정"으로 개정한다: 프로그램 관리, 담당 학생 아카이브 조회(포인트 열람 포함,
ADR 0015), QR 스캔, 담당 해제(ADR 0015), **비밀번호 초기화**(이 ADR).

- **관리자 본인의 비밀번호 문제는 이 기능으로 안 풀린다.** 관리자가 자기 비밀번호를 잊으면 여전히
  대상이 없다(관리자를 관리하는 관리자가 없다 — CLAUDE.md 1장 "1인 시연"). 케빈이 Supabase
  대시보드에서 직접 바꾼다. 아래 "알려진 사항" 참고.
- **관리자가 비밀번호 값을 직접 정하지 않는다.** 서버(Edge Function)가 무작위로 생성해 응답으로
  한 번만 돌려준다. 관리자가 타이핑하게 하면 약한 값("1234" 등)을 그대로 심을 위험이 생기고,
  그 값을 입력창에 남기면 화면에서 새는 경로가 하나 더 생긴다.
- **범위는 "담당 학생"으로 좁다.** 다른 관리자의 학생, 관리자 계정 자체는 대상이 아니다.

### 결정 2 — RPC가 아니라 Edge Function이다

비밀번호는 `auth.users`(Supabase Auth 내부 스키마) 소관이라 일반 SQL로 안전하게 못 건드린다.
이 앱의 계정 생성이 전부 Admin API를 거치는 것(`scripts/seed-accounts.mjs`, `naver-auth`/
`google-auth` — 셋 다 `admin.auth.admin.*`)과 같은 이유로, 비밀번호 변경도 Admin API
(`updateUserById`)를 호출하는 Edge Function(`admin-reset-student-password`) 하나로 좁힌다.

- **JWT 검증은 기본값(ON)이다.** `naver-auth`/`google-auth`는 로그인 *전* 호출이라
  `--no-verify-jwt`로 배포하지만, 이 함수는 로그인한 관리자만 불러야 하므로 기본값 그대로 둔다 —
  서명이 유효한 세션이 없으면 이 함수의 코드가 실행되기도 전에 플랫폼이 거부한다.
- **"로그인했다"와 "그 학생의 담당 관리자다"는 다른 검사다.** 후자는 호출자의 Authorization
  헤더를 그대로 실은 클라이언트로 `mentor_students`를 읽어서 확인한다 — service_role이 아니라
  호출자 권한 그대로이므로 기존 RLS(`mentor_students_select_own_as_admin`: `admin_id = auth.uid()`)
  가 자동으로 적용된다. 이 경계 로직을 함수 안에 새로 베끼지 않고 기존 정책을 그대로 재사용한
  이유는, 로직이 두 군데로 갈리면 나중에 RLS와 이 함수가 서로 다른 답을 낼 위험이 생기기 때문이다.
- **거부 사유를 세분화하지 않는다.** "관리자가 아님"과 "담당 학생이 아님"을 구분해 알려주지 않고
  둘 다 `not_your_student`로 뭉뚱그린다 — 구분해 주면 그 자체가 "이 학생이 실제로 존재하고
  다른 관리자 소속이다" 같은 정보를 캐낼 틈이 된다.

### 결정 3 — 임시 비밀번호는 1회만 보여주고 저장하지 않는다

Edge Function 응답의 `temp_password`는 그 요청 안에만 존재한다. 프런트도 React state에만 잠깐
담았다가 모달을 닫으면 버린다 — 로그에도, DB에도, localStorage에도 남기지 않는다. 관리자가
화면을 벗어나면 그 값은 다시 볼 방법이 없다(재초기화하면 새 값이 또 하나 생길 뿐이다).

## 절대 원칙 체크

- **원칙 1** (게임화 금지): 영향 없음. 비교·순위·진행률과 무관한 1회성 계정 관리 동작이다.
- **원칙 6** (관리자 기능 한정): 5가지로 개정했다. 학교 단위 대시보드·다중 관리자 관리는 여전히
  스코프 밖이고, 초대코드 생성·재발급 UI도 여전히 막혀 있다(이 기능과 별개 결정 — CLAUDE.md 4장).
- **다른 원칙**: 영향 없음.

## 알려진 사항

- **관리자 본인의 비밀번호 복구는 이 ADR의 범위가 아니다.** "1인 시연" 전제(CLAUDE.md 1장)를 따라
  Supabase 대시보드에서 직접 바꾼다 — 별도의 "관리자를 관리하는 관리자" 개념을 만들지 않는다.
- **학생이 로그인 후 스스로 비밀번호를 바꾸는 기능은 여전히 없다.** 임시 비밀번호를 받은 학생은
  계속 그 값을 써야 한다(재초기화를 관리자에게 다시 요청하는 것 외에는 바꿀 방법이 없다). 필요해
  지면 별도로 확인받을 것 — `supabase.auth.updateUser({ password })`는 로그인 세션만 있으면
  클라이언트에서 바로 호출 가능해 새 RPC 없이도 열 수 있는 자리다.
- **개인/소셜 계정의 비밀번호 재설정(실제 이메일 기반)도 이 ADR의 범위가 아니다.** 그쪽은 Supabase
  표준 `resetPasswordForEmail()`이 원래도 작동하는 경로이지만, 이번 요청은 학번/관리자코드 계정
  (가상 이메일)에 한정됐다.
- **임시 비밀번호 발급 이력이 남지 않는다.** 누가 언제 초기화했는지 감사 로그를 따로 남기지 않는다
  (데모 규모, ADR 0015의 담당 해제와 같은 수준의 생략).
