# ADR 0017: 초대코드 유출 완화 — 관리자 화면 마스킹 + 학생 화면 무차별 대입 방지

## 상태

확정 (2026-08-11, 케빈 요청).

## 배경

ADR 0016의 "알려진 사항"에 적어 둔 대로, 케빈은 신청 취소/대기열 작업을 마무리하며 "초대코드 유출을
막을 방법은 앞의 문제 해결하고 나서 생각해보자"라고 명시적으로 미뤄뒀다. 이번이 그 후속이다.

두 가지를 물었다: *"초대코드 유출을 막을 방법?"* → 논의 끝에 두 축으로 나뉘었다.

1. *"학교 코드 그러니까 초대코드는 평소에 '\*'로 표시되다 옆에 눈모양 아이콘 이용해서 숨기기 보이기
   설정하게 하는거 어때?"* — 관리자 화면의 **표시** 문제(화면 공유·옆에서 보임으로 새는 경로).
2. *"학생화면에서는 다시 초대코드 확인 못하게 수정하고"* — 되물어서 확정한 뜻은 **무차별 대입
   방지**다: `link_school_account()`는 로그인한 학생이면 누구나 무제한으로 다른 코드를 넣어 볼 수
   있는 "이 코드 존재해요/아니에요" oracle이었다.

두 문제는 성격이 다르다. 1번은 UI 열화(사람이 화면을 보는 문제)이고, 2번은 실제 권한 경계(서버가
막아야 하는 문제)다. 그래서 해법도 각각 UI 토글과 서버 rate limit로 갈렸다.

## 결정

### 결정 1 — 관리자 마이페이지 초대코드는 기본 마스킹 + 눈 아이콘 토글

`AdminMyPage.jsx`의 "내 학교 초대코드" 표시를 기본 `••••••••`(코드와 같은 길이)로 가리고, 옆의
눈 아이콘(`ic-eye`/`ic-eye-off`)을 눌러야 실제 값이 보인다. 기본 상태는 항상 가려짐(새로고침·재방문
시 매번 다시 가려진 채로 시작 — 브라우저에 "보기 상태"를 저장하지 않는다).

- **길이를 코드와 같게 유지한다.** 고정 길이 마스크(`••••`)를 쓰면 "이 관리자 코드는 짧다/길다"는
  것 자체가 새 나간다 — 지금은 전부 `SCH-XXXX`로 길이가 같아 실익이 적지만, 형식이 바뀔 가능성을
  남겨 둔다.
- **복사 버튼은 마스킹과 무관하게 항상 실제 값을 복사한다.** 가린 채로 복사가 안 되면 관리자가
  결국 "보기"를 눌러야 하고, 그 순간 다시 화면에 값이 뜬다 — 마스킹의 의미가 없어진다. 복사는
  "이미 값을 아는 사람이 스스로 쓰는 동작"이지 "보여주기"가 아니다.
- **이건 진짜 경계가 아니라 UI 열화다.** `invite_codes`의 진짜 권한 경계는 여전히 RLS
  (`invite_codes_select_own_as_admin` — 본인 school 코드 1행만)다. 마스킹은 "화면에 값이 떠 있는
  시간"을 줄일 뿐, DB 조회 권한 자체는 이 결정으로 바뀌지 않는다.

### 결정 2 — 학교 초대코드 연동은 5회 실패 시 15분 잠금

`link_school_account(p_invite text)`를 재정의해 `profiles`에 새 컬럼 두 개를 붙였다:
`school_link_fail_count`(연속 실패 횟수) / `school_link_locked_until`(잠금 해제 시각).

- **잠금 조건**: 연속 5회 `invalid_invite`면 15분 잠긴다. 성공하면(또는 이미 연동돼 있으면 그
  판정 자체가 실패가 아니므로) 카운터를 건드리지 않거나 0으로 리셋한다.
- **잠금 중엔 정답도 통과 안 시킨다.** 목적이 "이번 시도가 맞았는가"가 아니라 "짧은 시간에 몇 번
  시도했는가"를 늦추는 것이라서다 — 정답을 우연히 맞혀도 무제한 시도라는 사실 자체가 문제였다.
- **왜 이 정도 수치인가**: `SCH-XXXX`는 16^4 = 65,536가지다. 5회/15분 잠금이면 이론상 전수 조사에
  최소 32시간 이상 걸리고(65536 ÷ 5 × 15분), 그마저도 로그인된 학생 계정 하나로만 돌릴 수 있다 —
  병렬로 돌리려면 그만큼 학생 계정을 새로 여러 개 만들어야 하는데(학번+비밀번호 회원가입), 그건
  단순 API 반복 호출보다 비용이 훨씬 크다. 코드 자체를 길게 바꾸는 것(더 근본적인 해법)은 지금 이미
  공유된 실제 코드를 전부 무효화시키는 파급이 있어 이번 범위에 넣지 않았다 — 필요해지면 별도 ADR.
- **왜 RLS가 아니라 이 함수 안에서 처리하나**: 잠금은 "이 학생이 지금 몇 번 틀렸는가"라는 상태를
  같은 요청 안에서 읽고 갱신해야 하는 카운터 로직이라 RLS(정적 조건)로 표현할 수 없다. `for update`로
  프로필 행을 잠가 동시 요청의 레이스를 막는다(다른 RPC들과 같은 패턴).
- **범위를 학생 화면 하나로 좁혔다.** 회원가입 화면의 `check_signup_availability()`도 같은 종류의
  oracle(익명 호출, 학교/관리자 초대코드 유효성 검사)이지만 이번 ADR이 다루는 범위가 아니다 — 아래
  "알려진 사항" 참고.

## 절대 원칙 체크

- **원칙 1·4·6**: 영향 없음. 새 관리자 동작 0개(마스킹은 기존 "표시" 기능의 UI 상태일 뿐), 새 학생
  동작 0개(연동 폼 자체는 그대로, 실패 시 문구만 하나 늘었다).
- **CLAUDE.md 개정 불필요**: 이 ADR은 원칙 1~6을 하나도 바꾸지 않는다 — "초대코드는 표시만 한다"는
  기존 결정(4장)이 오히려 더 지켜지는 방향(마스킹)이고, rate limit는 이미 존재하던 RPC의 방어를
  강화한 것이다.

## 알려진 사항

- **`check_signup_availability()`는 이번에 손대지 않았다.** 회원가입 화면(로그인 전, `anon` 호출
  가능)에서 학교/관리자 초대코드 유효성을 미리 확인해 주는 함수라 같은 oracle 문제가 있다 — 특히
  관리자 초대코드(`ADMIN-2026`, 전체 앱에 딱 1개) 추측에 쓰일 수 있는 쪽이 더 심각하다. 다만 이 함수를
  거쳐 실제로 "성공"하려면 그때마다 새 계정을 만들어야 해서(학번/이메일+비밀번호) 단순 반복 호출보다
  비용이 크고, 이번 요청은 명시적으로 "학생화면"으로 범위를 좁혔다. 필요해지면 별도로 확인받을 것 —
  같은 방식(계정별 카운터)을 못 쓴다는 점(계정이 아직 없다)이 다르므로 IP/세션 기반 등 다른 설계가
  필요하다.
- **코드 자체의 키 공간(16^4)을 늘리지 않았다.** 잠금은 "얼마나 오래 걸리는가"를 늘릴 뿐 "불가능하게"
  만들지는 않는다. 이 프로젝트 규모(1인 시연, 관리자 1명)에서는 수용 가능한 트레이드오프로 판단했다.
- **관리자가 화면을 오래 열어 둔 채 "보기" 상태로 자리를 비우는 경우**는 막지 않는다(예: 일정 시간
  후 자동으로 다시 가리기). 데모 규모에서 과한 정교함이라 넣지 않았다 — 필요해지면 재검토.
