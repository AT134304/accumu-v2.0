# ADR 0013: 관리자 알림·캘린더와 자동 읽음 처리

## 상태

확정 (2026-08-08, 케빈 요청). `docs/specs/notifications-calendar.md` **결정 D(관리자 알림 없음)와
화면 A(자동 읽음 금지)를 대체한다.**

## 배경

`notifications-calendar.md`는 이틀 전 두 가지를 못박았다.

> **결정 D** — 관리자 알림: **없다.** `student_id` 축뿐. 알림함을 주면 관리자 기능이 4번째가 된다(원칙 6)
>
> **화면 A** — **자동 읽음 처리를 하지 않는다.** 열자마자 사라지는 표시는 "내가 뭘 놓쳤는지" 확인할 기회를 빼앗는다

케빈 요청으로 둘 다 뒤집는다. 뒤집는 근거와, 원래 근거를 어떻게 살렸는지를 여기 남긴다.

---

## 결정

### 결정 1 — 관리자 알림을 연다. **원칙 6은 "동작"으로 센다**

결정 D의 논리는 "알림함 = 4번째 기능"이었다. 이 등식을 다시 본다.

**관리자 기능 3종은 전부 동작이다** — 프로그램 올리기/내리기/수정, 담당 학생 아카이브 조회, QR 스캔.
아래 알림 3종은 **그 3종에 관한 사실**이고, 관리자가 새로 할 수 있게 되는 일이 하나도 없다.

| type | 사건 | 어느 기능에 관한 것인가 |
|---|---|---|
| `apply_admin` | 내가 올린 프로그램에 학생이 신청 | 프로그램 관리 |
| `mentee` | 학생이 내 초대코드로 연동 | 담당 학생 아카이브 |
| `stale` | 일정이 지났는데 아직 게시중 | 프로그램 관리 |

캘린더도 마찬가지다 — 관리자 홈의 "오늘 진행 프로그램"을 한 달 단위로 본 것이고, 새 테이블도 새 권한도
없다. 셸의 `MENU` 항목은 **4개 그대로**다.

>>> **규율: 알림 종류가 3종 기능 밖의 사실을 나르기 시작하면 그때가 원칙 6 위반이다.**
> 학교 전체 참여 통계, 다른 관리자의 활동, 학생 성취 요약, 랭킹 — 추가 금지.
>>> **캘린더/알림 팝업에 액션 버튼을 붙이지 말 것** (스캔 이동·내리기 등). 읽기 전용이 경계다.

### 결정 2 — `student_id` → `recipient_id`

컬럼이 관리자 행도 담는 순간 `student_id`라는 이름은 거짓말이 된다. `profiles`는 학생·관리자 공통
테이블이므로 FK는 그대로 두고 이름만 사실에 맞춘다. 테이블이 만들어진 지 이틀이라 지금이 가장 싼 시점이다.

- **수신자의 역할을 이 테이블이 저장하지 않는다.** `profiles.role`이 소유한다 — `is_admin_notice` 같은
  플래그를 더하면 같은 사실이 두 곳에 생긴다.
- **정책은 하나 그대로다.** `notifications_select_own (recipient_id = auth.uid())`.
  관리자용 별도 정책을 만들지 않는다 — "본인 수신분만"이라는 규칙이 두 역할에 똑같이 적용된다.
- `insert` / `update` / `delete` 정책은 **여전히 0개**다.

### 결정 3 — `apply_admin`에 **학생 이름을 넣지 않는다** (알려진 경계 넓힘)

ADR 0005 결정 7-2(d)는 "관리자는 담당 학생의 completed 참여 외에 `participations`를 읽을 수 없다"로
**신청자 명단·참여자 수를 닫아** 두었다. `AdminHomePage`의 주석도 "표시하지 않는 것: 참여자 수 / 신청자
명단 / 출석률 / 학생 랭킹"이다.

`apply_admin` 알림은 그 축을 **한 칸 연다.** 알림을 세면 신청 건수를 알 수 있다. 감수하되 최소로 연다:

- 문구는 **"새로운 참석 신청이 있어요" + 프로그램명 · 날짜**뿐이다.
- **누가 신청했는지는 여전히 알 수 없다** — 명단은 닫힌 채로 남는다.
- >>> 이 알림의 `detail`에 **학생 이름·학번·인원수를 추가하지 말 것.** 그 순간 명단이 열린다.

`mentee`는 다르다. 담당 학생은 관리자가 이미 아카이브에서 이름을 볼 수 있는 대상이므로(`admin_students`
정책) 이름을 담아도 새로 여는 정보가 없다.

### 결정 4 — `stale`은 트리거가 아니라 **지연 계산**

"일정이 지났다"는 **사건이 아니라 시간이 지나면 참이 되는 상태**다. 트리거는 행이 바뀔 때만 깨어나므로,
아무도 건드리지 않는 프로그램에서는 영원히 발화하지 않는다.

`sync_stale_program_notices()`를 관리자 셸이 마운트될 때 호출한다. **ADR 0012의
`settle_my_points()`와 같은 판단**이다 — 답이 날짜의 함수라 언제 계산해도 같으므로 `pg_cron`을 켜지 않는다.

- **멱등**: 부분 unique 인덱스 `notifications (recipient_id, program_id) where type = 'stale'`
  \+ `on conflict do nothing`. 조건문으로 "이미 있나"를 세지 않는다(동시 요청 두 건이 같은 검사를
  통과하는 창을 만들지 않는다).
- **알리기만 한다.** 이 함수가 `is_published`를 건드리지 않는다. 내리기는 관리자의 토글이 유일한 경로다
  (`admin-programs.md` 확정 D). 서버가 자동으로 내리면 그것이 4번째 관리자 기능(자동 운영)이다.
  >>> 이 함수 안에서 `programs`를 `update`하지 말 것.

### 결정 5 — `convert` 알림은 정산과 **같은 트랜잭션**

ADR 0012의 `settle_my_points()` 루프 안에서 `notify_user`를 1회 부른다. 알림만 따로 만들면
"전환은 됐는데 알림이 없는" 상태가 생긴다.

- 정산이 월당 1회이므로 알림도 자연히 월당 1회다 — 별도 멱등 장치가 필요 없다.
- **원칙 4**: 제목이 "지역화폐로 전환되었어요"이고 금액은 부가 줄이다(`exit` 알림과 같은 규율).

### 결정 6 — 자동 읽음. 원래 근거는 **다른 방법으로 살린다**

"모두 읽음" 버튼을 없애고 팝업을 여는 순간 `mark_notifications_read()`를 부른다.
화면 A의 근거("열자마자 사라지는 표시는 뭘 놓쳤는지 확인할 기회를 빼앗는다")는 여전히 옳다.
그래서 근거 자체를 버리지 않고 **표시 기준을 바꿔서** 지킨다:

- 팝업을 연 시점의 안 읽음 id 집합(`unreadIds`)을 붙잡아 두고, **이 팝업 안에서는 계속 강조해 보여준다.**
- 즉시 사라지는 것은 **종 아이콘의 배지뿐**이다. 목록은 그대로다.
- **순서가 중요하다**: 조회에 성공해 목록을 그린 **뒤에만** 읽음 처리한다.
  반대로 하면(먼저 읽음 → 조회 실패) 사용자는 보지도 못한 알림을 잃는다.
- 읽음 처리 실패는 화면을 막지 않는다. 목록은 이미 보이고, 다음에 열 때 다시 시도된다.

서버 규칙은 **그대로다**: `update` 정책 0개, RPC만이 유일한 쓰기 경로, 인자 0개(`auth.uid()`만 본다).

## 절대 원칙 체크

- **원칙 1 (게임화 배제)**: 관리자 캘린더가 운영 건수·참여율·달성률을 세지 않는다. 점은 계열 색이고
  배지는 예정/오늘/종료 3종 사실 표시다. 알림에도 카운터·연속 기록이 없다.
- **원칙 4 (포트폴리오 우선)**: `convert` 알림의 제목이 "지역화폐로 전환되었어요"이고 금액은 부가 줄이다.
- **원칙 6 (관리자 3종)**: 관리자가 새로 할 수 있게 된 **동작이 0개**다. `MENU` 항목 4개 그대로,
  두 팝업 모두 읽기 전용, `stale`은 알리기만 하고 내리지 않는다.
- **원칙 5 (QR 2회 인증)**: 손대지 않았다. `enter`/`exit` 알림이 각각 그대로다.

## 스코프 아님

- **개별 알림 읽음/삭제** — 여는 순간 전부 읽음이라 개별 조작의 자리가 없어졌다.
- **알림 필터/탭(학생·관리자 구분)** — 한 사람은 한 역할이다. 섞여 보이는 상황이 없다.
- **실시간 구독** — 팝업을 열 때 조회한다(`notifications-calendar.md` 그대로).
- **푸시 알림** — CLAUDE.md 11장.

## 알려진 열화

- **`apply_admin` 알림 개수 = 신청 건수**다. 결정 3 참고. 이름은 막았지만 개수는 새어 나간다.
- **`stale` 알림은 프로그램당 1회뿐**이다. 관리자가 읽고 넘긴 뒤 계속 게시해 두어도 다시 알리지 않는다
  (부분 unique 인덱스가 그렇게 만든다). 반복 잔소리를 만들지 않으려는 의도적 선택이다.
- **`mentee` 알림에는 `program_id`가 없다.** 프로그램과 무관한 사건이라 그 칸이 비어 있다 —
  화면이 `program_id`로 분기하지 않도록 주의할 것.

### `mentee` 알림을 두 경로로 나눈다 (같은 날 보강)

`mentor_students` 행이 생기는 앱 경로는 정확히 둘이고 **둘 다 같은 트리거를 지난다:**

| 경로 | 만드는 곳 | 문구 |
|---|---|---|
| 학교 계정 **가입** | `handle_new_user()` — `profiles` + `mentor_students`를 함께 만든다 | "새 학생이 학교 계정으로 가입했어요" |
| 마이페이지 **연동** | `link_school_account()` — 기존 학생에 매핑만 더한다 | "담당 학생이 추가되었어요" |

**구분 방법은 어림짐작이 아니다.** `now()`는 트랜잭션 시작 시각이라 한 트랜잭션 안에서 고정이다.
가입 경로에서는 `profiles.created_at`과 `mentor_students.created_at`이 같은 트랜잭션의 `default now()`라
**정확히 같은 값**이 되고, 연동 경로에서는 프로필이 이전 트랜잭션 소속이라 절대 같을 수 없다.
>>> 이 등식을 "몇 초 이내" 같은 시간 범위 비교로 바꾸지 말 것.

**★ 이 트리거는 예외를 삼킨다 — 이 저장소에서 거의 유일한 자리다.** 가입 경로에서 트리거가
`auth.users` insert와 같은 트랜잭션에 있어, 여기서 예외가 나면 **회원가입 전체가 롤백된다.**
알림 한 건 때문에 가입이 실패하는 것은 명백히 잘못된 우선순위다.
>>> 권한/정합성 검사를 그 `begin ... exception` 블록 안으로 옮기지 말 것.

### 새 알림 4종이 전부 지연 계산인 이유

`stale`·`upcoming`·`upcoming_admin`·`exit_due`는 **사건이 아니라 시간이 지나면 참이 되는 상태**다
(결정 4와 같은 논리). `sync_my_notices()` 하나가 역할로 갈라져 넷을 모두 처리하고,
학생 셸·관리자 셸이 **같은 함수를 부른다** — 프런트가 `role`을 보고 함수를 고르면 그것도 클라이언트
판정이고, 두 셸이 서로 다른 호출을 갖게 되어 한쪽만 조용히 낡는다.

멱등은 `notifications (recipient_id, program_id, type) where type in (…)` 부분 unique 인덱스 +
`on conflict do nothing`이 맡는다. 사건형 알림(`new`/`apply`/`enter`/`exit`/`convert`/`mentee`)은
이 인덱스에 걸리지 않는다 — 그것들은 사건마다 1행이 정상이다.

**★ `sync_my_notices()`는 `security definer`라 RLS를 우회한다.** 4개 `insert` 전부
`created_by = auth.uid()` 또는 `student_id = auth.uid()`로 묶여 있다.
>>> 그 조건을 지우면 그 순간 "전교생 알림 생성기"가 된다.

### 알려진 열화 (지연 계산의 대가)

**`upcoming`은 그 하루 동안 앱을 한 번이라도 열어야 생긴다.** 전날 앱을 안 열면 그 알림은 영영
만들어지지 않는다(다음 날에는 `date = 내일` 조건이 이미 거짓이다). 푸시 알림이 스코프 밖이라
(CLAUDE.md 11장) 구조적 한계이고 감수한다.
>>> 이걸 메우려고 `pg_cron`을 켜지 말 것 — 시연에서 확인할 수 없는 실패 지점이 는다.

## 구현 시 주의 — enum 확장은 **반드시 단독 마이그레이션**

Postgres는 같은 트랜잭션에서 추가한 enum 값을 그 트랜잭션 안에서 **쓰는 것**을 금지한다(`55P04`).
Supabase SQL Editor는 붙여넣은 스크립트 전체를 한 트랜잭션으로 실행하므로,
`alter type ... add value`와 그 값을 쓰는 문장이 같은 파일에 있으면 **반드시 실패한다.**

실제로 걸린 곳은 부분 인덱스의 술어였다(2026-08-08):

```
create unique index ... where type = 'stale';
ERROR: 55P04 unsafe use of new value "stale" of enum type notification_type
```

- **함수 본문(plpgsql)은 걸리지 않는다** — 문자열이 런타임에 해석된다.
  위험한 것은 **인덱스 술어 · CHECK · DML**이다.
- **"실패하면 한 번 더 실행" 은 통하지 않는다.** 오류가 트랜잭션을 통째로 되돌리면서
  `alter type`까지 함께 취소되기 때문이다(그래서 다음 스크립트에서는 `22P02 invalid input value`가 난다).

>>> **규율: `notification_type`에 값을 더할 일이 생기면 `20260808100000_extend_notification_type.sql`에
> 한 줄 추가하고 그 파일만 단독 실행할 것.** 다른 마이그레이션 안에 `alter type`을 섞지 말 것.

**실행 순서**: `20260808100000` → `20260808120000` → `20260808140000`
