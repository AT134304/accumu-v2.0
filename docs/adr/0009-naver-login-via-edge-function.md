# ADR 0009 — 네이버 로그인: Edge Function 으로 직접 잇는다

## 상태
확정 (2026-07-31). **케빈 결정: 구글·카카오·페이스북을 전부 걷어내고 네이버만 구현한다.**
스펙: `docs/specs/auth-signup.md`(결정 F 개정).

## 배경

ADR 0008 은 소셜 로그인을 Supabase 의 `signInWithOAuth` 로 붙였고, **네이버는 "만들지 않는다"로 두었다.** 근거는 그대로 유효하다:

- 네이버는 Supabase 의 제공자 목록에 **없다**.
- 네이버 로그인은 OAuth 2.0 이고 **OIDC `id_token` 을 발급하지 않는다** → `signInWithIdToken` 도 쓸 수 없다.

즉 Supabase 가 제공하는 두 경로가 모두 막혀 있어, 붙이려면 **`code → token → 프로필 → 계정 → 세션`을 직접 이어야 한다.** 그 중 "계정 생성"과 "세션 발급"은 `service_role` 을 요구한다.

**이 ADR 은 그 비용을 알고도 지불하기로 한 결정의 기록이다.** 국내 사용자에게 가장 익숙한 로그인 수단이라는 것이 유일한 근거이며, 아래 결정 3의 가드가 그 대가를 감당 가능한 크기로 묶는다.

### 함께 개정되는 것
- **구글 · 카카오 · 페이스북 제거.** `SOCIAL_PROVIDERS` / `signInWithProvider` / `SocialButtons` 삭제.
- ADR 0008 "결정 2"의 role 판정은 **그대로다.** 오히려 네이버 경로에서 더 좁아진다(결정 3).
- `handle_new_user()` 의 소셜 분기(`provider != 'email'`)는 **삭제하지 않는다.** 지금은 타는 경로가 없지만, 나중에 Supabase 제공자를 켜면 그대로 동작하는 방어 코드다. 마이그레이션을 되돌리는 비용이 남겨두는 비용보다 크다.

## 결정 1 — 교환은 Edge Function 이 한다 (프런트에서 하지 않는다)

| 안 | 판단 |
|---|---|
| 1-1 (기각) 프런트가 네이버 토큰 API 를 직접 호출 | **client_secret 이 번들에 들어간다.** 그 순간 누구나 우리 앱을 사칭해 토큰을 받을 수 있다. 게다가 네이버 토큰 엔드포인트는 CORS 를 허용하지 않아 브라우저에서 호출되지도 않는다 |
| **1-2 (채택) Edge Function `naver-auth`** | 시크릿과 `service_role` 이 서버에만 존재한다. 프런트는 `code/state` 두 개만 보내고 `token_hash` 하나만 받는다 |

- 함수는 `--no-verify-jwt` 로 배포한다. **로그인 이전에 호출되므로 사용자 JWT 가 존재하지 않는다.**
- 그래서 이 함수는 **인증 없이 누구나 호출할 수 있다.** 그 사실을 전제로 결정 3의 가드를 건다.

## 결정 2 — 세션은 매직링크 토큰으로 만든다

Admin API 로는 `access_token` 을 직접 발급할 수 없다. 두 가지 우회가 있다.

| 안 | 판단 |
|---|---|
| 2-1 (기각) 임의 비밀번호를 심고 `signInWithPassword` | **기존 비밀번호를 덮어쓴다**(이메일 가입자가 네이버로 한 번 들어오면 원래 비밀번호를 잃는다). 서버가 사용자의 비밀번호를 알게 되는 구조도 피해야 한다 |
| **2-2 (채택) `admin.generateLink({type:'magiclink'})` → 프런트가 `verifyOtp`** | 토큰이 1회용이고 짧게 만료된다. 기존 계정 상태를 건드리지 않는다 |

- 반환값은 **`hashed_token` 하나뿐**이다. 함수가 세션(`access_token`/`refresh_token`)을 만들어 돌려주지 않으므로, 응답이 새더라도 교환 시점의 1회용 토큰 이상은 얻을 수 없다.

## 결정 3 — **이 함수가 role 을 넓히지 않는다는 것이 이 ADR 의 핵심**

`naver-auth` 는 인증 없이 호출 가능하고 `service_role` 을 들고 있다. 그래서 다음을 **구조적으로** 보장한다.

| 가드 | 구현 |
|---|---|
| 입력이 두 개뿐이다 | 본문에서 읽는 값은 `code`, `state` 뿐이다. 이메일·이름·role·초대코드를 **받지 않는다** — 받지 않으면 신뢰 여부를 판단할 일도 없다 |
| 신원의 근거는 네이버뿐 | 계정 식별에 쓰는 값은 `openapi.naver.com/v1/nid/me` 응답의 `id`/`email` 이다. 유효한 네이버 `code` 없이는 어떤 계정에도 도달할 수 없다 |
| **role 을 넘길 자리가 없다** | `createUser` 의 `user_metadata` 는 `{ name }` 하나다. `code`/`role`/`invite` 가 비어 있으므로 `handle_new_user()` 의 **"(c) 개인 이메일 가입" 분기**를 타고 **언제나 `student` / `personal`** 로 만들어진다 |
| 관리자 승격 불가 | 관리자는 `invite_codes(kind='admin')` 를 입력하는 이메일 가입 경로에서만 만들어진다. 네이버 경로에는 그 입력이 존재하지 않는다 |
| 담당 배정 불가 | `mentor_students` 를 건드리지 않는다. 네이버 가입자는 개인 계정이며, 학교 연동은 로그인 후 학생 본인이 `link_school_account()` 로만 한다 |
| 포인트 불가 | `profiles.points_*` 를 SET 하지 않는다. 가입 보너스가 없다(원칙 1) |

**규율**: 이 함수에 인자를 추가하려는 변경은 전부 이 표를 다시 검토해야 한다. 특히 `role`·`code`·`invite`·`student_id` 를 본문에서 읽기 시작하는 순간 위 보장이 전부 깨진다.

## 결정 4 — CSRF 대조(`state`)는 프런트가 한다

- 함수는 브라우저 세션을 알지 못하므로 `state` 의 진위를 판단할 수 없다(네이버 규격상 토큰 교환에 함께 실어 보낼 뿐이다).
- 그래서 **발급과 대조를 프런트가 `sessionStorage` 로** 한다: `startNaverLogin()` 이 `crypto.randomUUID()` 로 만들어 저장하고, 콜백 화면이 대조에 실패하면 **교환 자체를 하지 않는다.**
- `code` 는 1회용이라 콜백 화면은 **StrictMode 이중 실행을 ref 로 막는다.** 안 막으면 개발 모드에서만 항상 실패하는 형태가 된다.

## 결정 5 — 이메일이 없을 수 있다

네이버의 이메일 제공은 검수 대상이라, 검수 전에는 프로필에 `email` 이 없을 수 있다.

- 없으면 **`naver_{네이버id}@accumu.local`** 를 쓴다. 같은 사람이 다시 로그인해도 같은 값이라 계정이 하나로 유지된다.
- 그 계정은 이메일/비밀번호로는 로그인할 수 없다(네이버로만 들어온다). **이것을 결함이 아니라 상태로 다룬다** — 화면은 마이페이지에서 그 주소를 그대로 보여준다.

## 권한 영향

### 새로 생기는 것
| 표면 | 내용 |
|---|---|
| Edge Function `naver-auth` | 인증 없이 호출 가능. `service_role` 보유. 반환은 1회용 `token_hash` 하나 |
| 프런트 환경변수 `VITE_NAVER_CLIENT_ID` | **공개값이다.** 클라이언트 ID 는 인증 URL 에 실려 어차피 노출된다. `client_secret` 은 절대 프런트에 두지 않는다 |

### 그대로 유지되는 것 (확인 완료)
- `profiles` / `mentor_students` / `invite_codes` 의 insert·update·delete 정책 **전부 0개**
- role 판정의 소유자는 여전히 `handle_new_user()` 트리거
- QR 발급·검증, 정원 게이트, 포인트 지급 경로 **수정 0줄**
- 마이그레이션 **0건** — 네이버 경로는 기존 트리거 분기를 그대로 재사용한다

### 알려진 제약 (숨기지 않는다)
- **폰 시연에서 네이버는 안 될 가능성이 크다.** 네이버는 Callback URL 로 **앱 주소**를 등록해야 하는데(구글·카카오는 Supabase 콜백 하나면 됐다), 사설 IP(`192.168.x.x`)는 등록이 거부될 수 있다. → **네이버는 PC 시연 전용**으로 잡는다. 폰에서는 이메일 가입/로그인을 쓴다.
- 함수가 배포되지 않았거나 시크릿이 비어 있으면 버튼은 **비활성**으로 뜬다(`VITE_NAVER_CLIENT_ID` 부재 시). 눌리는데 실패하는 버튼을 두지 않는다.
- `listUsers()` 로 이메일을 찾는다. 데모 규모(수십 명)에서는 충분하지만, 규모가 커지면 `naver_id → user_id` 매핑 테이블이 필요하다.

## qa-agent 가 볼 것
1. **`naver-auth` 에 임의 본문(role/code/invite 포함)을 실어 호출해도 관리자·학교 계정이 만들어지지 않는가.**
2. `state` 를 조작하거나 비운 채 콜백에 진입하면 교환이 일어나지 않는가.
3. 같은 네이버 계정으로 두 번 로그인했을 때 `profiles` 행이 하나로 유지되는가.
