# ADR 0022: 프로그램 대표 사진 (관리자 업로드 → 카드 썸네일)

## 상태

확정 (2026-08-13, 케빈 요청).

## 배경

케빈: *"관리자가 프로그램 올릴 때 사진 넣을 수 있게 추가해줘. 그러면 프로그램 화면에서 원래
아이콘으로만 보이던 위치에 사진 들어가게."*

지금까지 카드·팝업의 썸네일 자리(`ProgramCard`의 `.thumb`, `JoinModal`의 `.mthumb`)는 category
색 그라데이션 + duotone 아이콘이었다. 유형 4종에 아이콘도 4개라 **한 유형의 프로그램끼리는 카드가
전부 똑같이 생겼다** — "봉사활동" 카드 6장이 같은 하트 아이콘으로 나란히 서 있다. 사진은 그 자리를
구분 가능하게 만드는 가장 직접적인 수단이고, 시연에서 "실제 서비스처럼 보이는가"에 가장 크게
기여하는 변경이기도 하다.

---

## 결정

### 결정 1 — 사진은 1장, 컬럼은 `programs.image_url text` 하나

`participations`나 별도 `program_images` 테이블을 만들지 않는다. 카드 썸네일 **한 자리**에 들어갈
값이므로 스칼라 한 개면 충분하다.

- **배열/갤러리를 만들지 않는다.** 여러 장이 되는 순간 순서 정하기 UI, 대표 이미지 고르기, 팝업
  캐러셀이 따라붙는다. 그건 "프로그램 올리기" 폼 하나가 아니라 별도 화면이고, 그 순간 관리자
  기능이 6번째로 늘어난다(CLAUDE.md 원칙 6).
- **NULL 이 정상 상태다.** 기존 20여 행과 튜토리얼 행(ADR 0021)은 전부 사진이 없다. 그래서 사진은
  **선택 입력**이고, 필수로 만들지 않는다 — 필수가 되면 사진을 구하지 못한 활동은 아예 올릴 수 없다.
- DB 체크 `programs_image_url_shape`: `image_url is null or (image_url ~ '^https://' and length <= 500)`.
  이 값은 `<img src>` 로 그대로 나가므로 스킴 강제는 DB 가 한다(폼이 파일 업로드만 허용한다는
  사실은 방어가 아니다 — ADR 0004 주의 4와 같은 태도).

### 결정 2 — 아이콘은 폐기가 아니라 **fallback** 이다

케빈의 문장은 "아이콘 자리에 사진이 들어가게"이지 "아이콘을 없애라"가 아니다. 실제로도 없앨 수
없다 — 사진 없는 행이 다수다.

| 상태 | 카드/팝업 표시 |
|---|---|
| `image_url` 있음 | 사진 (`object-fit: cover`, 썸네일 칸을 꽉 채움) |
| `image_url` NULL | **지금까지와 완전히 동일** (category 그라데이션 + duotone 아이콘) |
| `image_url` 있는데 로드 실패 | 아이콘으로 되돌린다 (`onError` → 상태 플래그) |

세 번째 줄이 중요하다. DB 행과 스토리지 오브젝트는 수명이 분리돼 있다(앱은 오브젝트를 지우지
않지만 Supabase 대시보드에서는 지울 수 있다). fallback 이 없으면 그 순간 카드마다 깨진 이미지가
뜬다 — `alt=""` 인 장식 이미지라 대체 텍스트조차 안 나온다.

- **예외 — 관리자 목록(`AdminProgramsPage`)에는 fallback 을 두지 않는다.** 학생에게 깨진 사진을
  숨기는 것은 맞지만, 관리자에게 "사진이 깨졌다"는 **고쳐야 할 사실**이다. 숨기면 다시 올릴 이유를
  영영 못 본다.

### 결정 3 — 저장소는 Supabase Storage 공개 버킷, 경계는 `{auth.uid()}/` 폴더

버킷 `program-images` (public read, 3MB, `image/jpeg|png|webp`).

- **public 버킷인 이유.** 서명 URL 로 하면 카드 20장마다 만료·갱신 로직이 붙는다. 사진 자체는
  숨길 값이 아니다(프로그램 홍보물이다). 화면 접근 통제는 계속 RLS 가 한다.
- **정책은 `insert` 하나뿐이다** — `is_admin() and (storage.foldername(name))[1] = auth.uid()::text`.
  programs 의 행 경계가 `created_by = auth.uid()` 인 것(ADR 0005 결정 7-0 축 A)과 같은 축을 오브젝트
  경로에 그대로 옮긴 것 — 관리자 A 가 관리자 B 의 폴더에 파일을 넣을 수 없다.
  >>> **`select` 정책을 만들지 말 것** (20260813140000 이 처음 만든 것을 다시 지웠다).
  >>> 공개 버킷의 이미지 읽기는 `/object/public/` 경로가 처리하고 그건 RLS 를 타지 않아 정책이
  >>> 필요 없다. 반면 `to public` SELECT 정책이 있으면 anon 키로 `list('')` 가 통과해
  >>> **미게시 초안 사진 · 버려진 사진 · 관리자 uid(=폴더명) · 업로드 메타데이터**가 전부 열거된다.
  >>> 아래 "파일명이 uuid 라 추측 불가"라는 전제가 열거 앞에서는 무의미해진다.
- **경로는 `{adminId}/{uuid}.{ext}`.** 원본 파일명을 쓰지 않는다 — 한글·공백·중복 파일명이 그대로
  URL 이 되는 문제와 "같은 이름 업로드가 남의 사진을 덮어쓰는" 사고가 한꺼번에 사라진다.
- **`file_size_limit`/`allowed_mime_types` 는 버킷에 건다.** 폼의 검증은 사용자에게 먼저 알려주는
  역할이고, 개발자도구로 우회 가능하다. 진짜 상한은 버킷이다.
  >>> `programService.js` 의 `PROGRAM_IMAGE_*` 상수와 마이그레이션의 버킷 설정은 **같은 값 2벌**이다.
  >>> 한쪽만 고치면 "폼은 통과했는데 업로드만 실패"가 된다.

### 결정 4 — **스토리지 오브젝트를 지우는 코드를 만들지 않는다** (delete 정책 0개)

`programs` 에 delete 정책이 0개인 것(ADR 0005)과 같은 태도이자, 더 실질적인 이유가 하나 더 있다:

> 폼에서 사진을 교체하고 **저장하지 않고 취소**하면 DB 는 여전히 옛 URL 을 가리킨다.
> 교체 시점에 옛 파일을 지우는 코드가 있으면 **그 순간 저장된 행의 이미지가 깨진다.**

"안 쓰이는 파일이 버킷에 남는 것"과 "저장된 프로그램의 사진이 깨지는 것" 중 후자가 훨씬 나쁘다.
시연 스코프에서 전자는 해가 없다(정리가 필요하면 대시보드에서 사람이 지운다). 폼의 "지우기"
버튼도 **폼 값만 비운다** — 오브젝트는 그대로 둔다.

### 결정 5 — 업로드는 저장과 별개의 왕복이다 (파일을 고르는 즉시 올라간다)

폼 상태가 들고 있는 값은 `File` 객체가 아니라 **업로드 결과 URL 문자열 하나**다.

- `File` 을 들고 있다가 저장 시점에 올리면, "저장" 한 번에 업로드 + insert 두 왕복이 묶여
  **한참 뒤에 사진 때문에 저장이 실패**한다. 사용자는 무엇이 실패했는지 모른다.
- 대신 업로드 중에는 저장·취소·모달 닫기를 모두 잠근다(`uploading` 플래그). 이미 있던 `saving`
  플래그와 같은 방식이다.
- 업로드 실패는 `ProgramImageError` 로 좁혀서 사진 칸 아래에만 표시한다. 버킷이 없을 때(404 —
  마이그레이션 미실행)는 "다시 시도"로 절대 안 풀리는 상황이라 문구를 따로 준다.

### 결정 6 — 자르기는 **업로드 시점에 실제로** 한다 (2026-08-13 추가)

케빈: *"사진이 원래 아이콘이 들어가있고 색이 된 위치에 맞게 자르는 과정을 추가해서 그렇게 잘린
사진을 놓는 거로 수정해줘."*

`programService.renderCropToBlob(img, rect)` 가 캔버스로 **카드 썸네일 비율(236/108)에 맞춰
가로 960px 로 구운 webp**(미지원 브라우저는 jpeg)를 만들어 그것을 업로드한다. 원본은 올라가지
않는다. (처음에는 가운데 고정이었고 함수 이름도 `cropToCardRatio(file)` 였다 — 아래 결정 6-1 에서
영역을 관리자가 고르게 되며 시그니처와 이름이 바뀌었다.)

- **화면 CSS(`object-fit`)에만 맡기지 않는 이유.** 보이는 것만 자르면 원본이 그대로 올라가
  학생 카드 20장마다 3000px 짜리를 내려받게 되고(모바일에서 특히 나쁘다), 관리자가 폼에서 본
  모양과 학생 카드의 모양이 미묘하게 달라진다. 실제로 잘라 두면 저장된 파일 자체가 카드
  모양이라 둘이 정확히 같아지고 파일도 100~200KB 로 줄어든다.
- **입력 상한이 3MB → 15MB 로 올라갔다.** 올라가는 것이 원본이 아니라 결과물이라 버킷의 3MB
  제한에 걸릴 일이 없다. 이제 이 값은 "버킷 제한의 복사본"이 아니라 **디코딩 방어선**이다 —
  폰 사진은 5~10MB 가 흔해서 원본 크기로 막으면 정작 쓰고 싶은 사진이 전부 거부됐다.
  (버킷 설정은 바꾸지 않았다. 마이그레이션 재실행 불필요.)
- 관리자 폼의 미리보기 상자도 같은 비율로 맞췄다. **미리보기에 보이는 그림 = 학생 카드에 나올
  그림**이다. 참여 팝업(`.mthumb.has-photo`)도 사진일 때는 같은 비율을 쓴다 — 처음에는 팝업이
  460×120(3.83:1) 고정이라 고른 영역의 **세로 43%가 다시 잘려나갔다**(QA 지적으로 수정).
  다만 목록의 정사각 칸(`.arc-row .ic` 42×42, `.adm-row .ic` 40×40)은 1:1 이라 가로가 크게
  잘린다 — 거긴 "사진이 있다"는 식별 표시라 의도된 열화다.

### 결정 6-1 — 자를 영역은 관리자가 고른다 (같은 날 후속)

처음에는 가운데 기준 자동이었는데 케빈이 *"어느 부분을 살릴지 내가 고르고 싶어"* 로 확정했다.
`ImageCropper` 신규 — 파일을 고르면 업로드 전에 자르기 패널이 뜨고, **드래그로 위치 · 슬라이더로
확대**를 맞춘 뒤 "이 영역으로 자르기"를 눌러야 업로드된다.

- **Modal 이 아니라 폼 안의 패널이다.** `ProgramFormModal` 자체가 이미 `Modal` 이라 여기서 `Modal` 을
  또 열면 Esc 리스너와 포커스 트랩이 두 벌 겹친다 — Esc 한 번에 자르기 창과 폼이 같이 닫힌다.
  사진 칸 자리에서 미리보기를 대체하는 패널이면 그 문제가 아예 없고, 모바일에서도 폼 모달이
  거의 화면 폭이라 크기가 아쉽지 않다.
- **손대지 않으면 결과가 이전과 같다.** 초기 상태가 "뷰포트를 꼭 덮는 최소 배율 + 가운데 정렬"
  이라 그냥 확정하면 가운데 자르기와 동일한 그림이 나온다. 고르는 것은 선택이지 의무가 아니다.
- **Esc·바깥 클릭은 폼이 아니라 자르기만 취소한다.** 사진 하나 잘못 골랐다고 입력하던 폼 전체가
  날아가면 안 된다.
- **업로드 실패 시 패널을 닫지 않는다.** 고른 영역 그대로 다시 시도할 수 있어야 한다
  (`setCropFile(null)` 이 성공 경로에만 있다).
- 포인터 이벤트 하나로 마우스·터치·펜을 다 받고, 뷰포트에 `touch-action: none` 을 준다 — 없으면
  모바일에서 사진은 안 움직이고 폼만 스크롤된다. 마우스를 못 쓰는 경우를 위해 방향키 이동도 있다.

### 결정 6 이전에 있던 버그 — 사진이 카드 전체를 덮었다

같은 요청에서 함께 고쳤다. 원인은 자르기가 아니라 **CSS 레이아웃**이었다.

`.thumb` 는 `display:grid; place-items:center` 이고 행 크기가 `auto` 다. auto 행을 재는 시점에는
행 높이가 아직 없으므로 자식의 `height:100%` 가 `auto` 로 해석되고, 행이 **이미지 원본
높이**(폰 사진이면 3000px)로 잡힌다. 컨테이너의 108px 를 넘긴 채 남아 이미지가 카드 본문 위를
통째로 덮었다(`place-items:center` 라 stretch 도 안 걸려 스스로 줄지 않는다).

→ 사진을 `position:absolute; inset:0` 으로 흐름에서 빼서 행 크기 계산에 참여하지 않게 했다.
아이콘 경로(사진 없음)는 흐름 안에 그대로 남아 영향이 없다.
>>> `.thumb-photo` 의 `position:absolute` 를 지우지 말 것. 지우는 순간 이 버그가 그대로 돌아온다.

## 원칙 체크 (CLAUDE.md 2장)

| 원칙 | 판정 |
|---|---|
| 1. 게임적/사행적 요소 배제 | **위반 없음.** 사진은 꾸밈이다. 조회수·좋아요·"사진 있는 프로그램 먼저" 정렬 없음 |
| 2. 진로·커리어 집중 | 해당 없음 |
| 3. 포인트 전환 시뮬레이션 | 해당 없음 |
| 4. 포트폴리오 > 포인트 | **강화된다.** 카드에서 가장 큰 면적이 활동 사진이 된다. 폼에서도 사진 칸이 포인트 칸보다 위다. amber 는 이 변경 어디에도 없다 |
| 5. QR 2회 인증 | 손대지 않음 |
| 6. 관리자 기능 5종 | **위반 없음.** "프로그램 올리기/수정" 폼 안의 입력칸 1개다. 새 메뉴 0개, 새 화면 0개, 담당 학생·QR·아카이브 쪽 변경 0줄 |

## 재검토 시점

- 관리자가 "사진을 여러 장 올리고 싶다"고 하면 → 결정 1 을 다시 본다. 그때 필요한 건 컬럼 하나가
  아니라 별도 관리 화면이므로 **원칙 6 재검토가 먼저**다.
- 버킷에 안 쓰는 파일이 눈에 띄게 쌓이면 → 결정 4 를 다시 본다. 다만 해법은 "교체 시 삭제"가
  아니라 "저장 성공 후 옛 URL 정리" 같은, 저장된 행을 절대 깨뜨리지 않는 방향이어야 한다.
