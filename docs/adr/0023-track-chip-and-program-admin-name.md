# ADR 0023: 카드에 진로 계열 · 팝업에 담당 관리자 이름

## 상태

확정 (2026-08-14, 케빈 요청).

## 배경

케빈: *"프로그램 화면에서 프로그램 관리자가 누구인지 딱 안 보이고 진로 계열도 뭔지 바로 표시가
안 되거든? 그래서 그거 보이게 수정해줘. 관리자는 카드 열어서 나온 팝업에서 이름 뜨게, 그러고
계열은 그냥 화면에서 뜨게."*

두 값 모두 데이터에는 이미 있는데 화면에 없었다 — 성격은 정반대다.

| | 지금까지 | 왜 안 보였나 |
|---|---|---|
| `programs.career_track` | 정렬·필터의 **입력으로만** 쓰였다(프로그램 선택 화면의 계열 칩 필터) | 순수 표시 누락. 카드가 그리는 값에서 빠져 있었을 뿐 |
| 담당 관리자 이름 | 어디에도 없었다 | **RLS 때문에 읽는 경로 자체가 없다** (아래 결정 2) |

계열은 특히 아쉬운 자리였다. ADR 0014가 "`category`(무엇을 하는가)와 `career_track`(어느 계열인가)은
완전히 별개 축"이라고 못박아 놓고, 정작 카드는 category 하나만 찍고 있었다. 계열로 활동을 고르는
학생은 카드를 하나씩 열어 봐야 했다.

---

## 결정

### 결정 1 — 계열은 카드 썸네일 **왼쪽 아래**에, 흰 알약 + 계열색 점으로

`.pcard .thumb` 위쪽 줄은 이미 다 찼다 — 왼쪽에 유형 칩(`.tag`), 오른쪽에 매칭 배지(`.matchbadge`).
236px 카드에 셋을 한 줄로 넣으면 서로 겹친다. 그래서 **왼쪽 아래 구석**을 쓴다.

모양은 유형 칩과 **일부러 다르게** 한다:

- **유형 칩** = 유형색(CAT[].deep) 배경 + 흰 글씨 (2026-08-13에 정한 것)
- **계열 칩** = 흰 알약 + 진한 글씨 + **계열색 점**

두 개의 진한 알약이 나란히 있으면 어느 쪽이 무슨 축인지 오히려 흐려진다. 그리고 실용적인 이유가
하나 더 있다 — TRACK 색 중에는 흰 글씨 대비가 모자란 값이 있다(`sci #0EA5E9`). 흰 배경은 사진
위에서도 항상 읽히고, 색은 글자가 아니라 점이 나른다.

- 팝업(`JoinModal`)에서는 `infogrid` 칸으로 넣고 **글자에 계열색**을 준다 — 흰 패널 위라 대비가
  확보되고, 그 칸은 "값"이 주인공인 자리라 점보다 글자가 낫다.
- `TRACK`에 없는 키(데이터 이상)면 칩·칸을 **렌더하지 않는다.** "미분류" 칸을 만들지 않는다
  (ADR 0014 "기타 칸을 만들지 말 것"과 같은 태도).
- >>> **계열 칩에 개수·순위·매칭률을 붙이지 말 것.** 이건 분류 표시 하나다(원칙 1).

### 결정 2 — 관리자 이름은 **RLS 정책이 아니라 서버 함수**로 연다

이게 이 ADR의 핵심 판단이다.

`public.profiles`의 select 정책은 두 개뿐이다:

```
profiles_select_own                        (본인 행)
profiles_select_mentored_students_as_admin (관리자 -> 자기 담당 학생)
```

**학생이 관리자 프로필을 읽는 경로는 없다.** `programs`에 embed 조인을 걸면 에러가 아니라 조용히
`null`이 와서 "이름 칸이 늘 비어 있는 화면"이 된다.

그래서 정책을 하나 여는 게 자연스러워 보이지만 — **RLS는 행 단위다.** "학생이 관리자 프로필을
select 할 수 있다"고 열면 그 행의 **모든 컬럼**이 함께 열린다. `profiles.code`가 거기 있고,
관리자의 code(`ADM-0001`)는 곧 **로그인 아이디**다(CLAUDE.md 4장 — `{코드}@accumu.local`).
이름을 보여주려다 전교생에게 관리자 계정 아이디를 뿌리는 셈이 된다. `points_balance`·
`career_interest`도 같이 딸려 나온다.

`20260814140000`이 컬럼을 고를 수 있는 `security definer` 함수로 연다:

```sql
program_admin_names() returns table(program_id uuid, admin_name text)
  -- is_published = true 인 프로그램만. created_by 가 NULL 이면 결과에 없다(inner join).
```

나가는 값은 **(program_id, 이름) 둘뿐**이다 — 관리자의 uuid·code·잔액은 이 경로로 나가지 않는다.
`program_applicant_counts()`가 "숫자만 내보내고 명단은 안 내보낸" 것과 같은 모양이다(ADR 0016).

- >>> **이 함수에 컬럼을 추가하지 말 것.** 특히 `code`·포인트 계열은 절대 금지다.
- >>> 반대 방향(관리자가 신청자 명단을 보는 것)은 ADR 0005 결정 7-2(d)로 **계속 닫혀 있다.**
  이 ADR이 연 것은 "관리자 -> 학생"이 아니라 "학생 -> 관리자 이름" 한 방향뿐이다.

### 결정 3 — 이름이 없으면 칸을 **통째로 숨긴다** ('-'로 채우지 않는다)

프런트는 두 경우를 구분할 수 없다:

1. `created_by`가 NULL인 프로그램 (함수 결과에 아예 없음)
2. RPC 조회 실패 (빈 Map으로 열화 — `fetchApplicantCounts()`와 같은 태도)

둘 다 **"담당자가 없다"는 사실이 아니다.** `-`나 `미정`으로 채우면 모르는 것을 안다고 말하는 것이
된다. 그래서 `adminName`이 없으면 `infogrid` 칸 자체를 렌더하지 않는다 — 카드의 신청자 수를
`null`일 때 숨기는 규칙(ADR 0016)과 같다.

### 결정 4 — 관리자 이름은 신청/취소 후 **다시 읽지 않는다**

`StudentProgramsPage`는 신청·취소마다 참여 상태·신청자 수·대기 순번 세 Map을 다시 읽는다.
관리자 이름은 그 목록에 넣지 않는다 — **내 행동으로 바뀌는 값이 아니다.** 프로그램을 올린 사람은
내가 신청한다고 달라지지 않는다. 첫 로드 때 한 번만 읽는다(왕복 1회 추가로 끝).

### 결정 5 — 주최(`org`)와 담당 관리자를 **한 줄로 합치지 않는다**

팝업 statusline에 이미 `주최 <b>{org}</b>`가 있다. 거기 이어 붙이고 싶어지지만 둘은 다른 정보다 —
**주최는 기관이고 담당은 사람이다.** 합치면 "서울시립도서관 김선생"처럼 읽혀 어디까지가 기관
이름인지 흐려진다. `infogrid`의 별도 칸으로 둔다.

## 원칙 체크 (CLAUDE.md 2장)

| 원칙 | 판정 |
|---|---|
| 1. 게임화·사행성 배제 | **영향 없음.** 계열 칩은 분류 표시, 관리자 이름은 사실 한 줄이다. 개수·순위·비율 0개 |
| 2. 진로·커리어 중심 | **강화.** 계열이 카드에서 바로 읽히면 진로 축으로 활동을 고를 수 있다 |
| 3. 포인트 시뮬레이션 | **영향 없음** |
| 4. 포트폴리오 > 포인트 | **유지.** 새로 추가한 표시에 amber가 0개다. 계열 칩은 카드에서 포인트 배지보다 위(썸네일)에 온다 |
| 5. QR 2회 인증 | **영향 없음** |
| 6. 관리자 기능 5종 | **영향 없음 — 관리자가 새로 할 수 있게 된 일 0개.** 학생 화면의 표시만 늘었다. 관리자 화면·메뉴·정책 변경 없음 |

## 배포 순서

1. `20260814140000_add_program_admin_names.sql` 실행
2. 프런트 배포

**순서를 지켜야 하는 이유는 약하다** — 함수가 없으면 `fetchProgramAdminNames()`가 빈 Map으로
열화하므로 담당 관리자 칸만 안 보이고 나머지는 그대로 동작한다. 계열 칩은 마이그레이션과 무관하다
(`career_track`은 이미 `CARD_FIELDS`에 있었다).

## 재검토 시점

- 관리자 이름 외의 값(연락처·소속 등)을 보여달라는 요구가 오면 → **결정 2를 다시 읽을 것.**
  함수에 컬럼을 붙이는 순간 "이름만 나간다"는 보장이 사라진다.
- 카드 썸네일에 표시를 하나 더 붙이고 싶어지면 → 네 구석이 다 찼다는 뜻이다. 추가가 아니라
  무엇을 뺄지부터 정할 것.
