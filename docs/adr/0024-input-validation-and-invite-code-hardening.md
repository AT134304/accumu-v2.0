# ADR 0024: 입력 검증을 DB로 내리고, 초대코드를 계산 불가능하게 만든다

## 상태

확정 (2026-08-20, 케빈 요청 — *"보안이나 프로그램을 올린다거나 하는 부분에서 검증이 너무 대충인 것
같아서 해결 방안 알려줘"*).

## 배경

기능이 대부분 완성된 시점에서 **검증과 경계**만 따로 점검했다. 네 건이 나왔고, 성격이 둘로 갈린다.

### A. 프로그램 등록의 검증이 클라이언트에만 있었다

| 필드 | 폼(`ProgramFormModal`) | DB |
|---|---|---|
| `title` | `maxLength 80` | (없음) |
| `org` | `maxLength 60` | (없음) |
| `description` | `maxLength 400` | (없음) |
| `time` | `maxLength 40` | (없음) |
| `points` | 150~3000, 끝자리 0 | CHECK ✅ |
| `capacity` | `>= 1` | `> 0` (상한 없음) |
| `date` | (경고만) | (없음) |

`not null`은 빈 문자열 `''`을 막지 못한다. 그래서 개발자도구나 `curl`로 폼을 우회하면 **제목이 빈
카드**, **설명 1MB짜리 프로그램**, **정원 20억**, **2999년 프로그램**이 전부 저장되고 모든 학생의
목록에 그대로 렌더됐다.

ADR 0005가 `points` CHECK에 대해 써 둔 원칙 — *"프런트도 같은 규칙으로 미리 검증하되, 경계의
소유자는 이 CHECK다"* — 이 나머지 필드에는 적용되지 않은 상태였다. 같은 규율이 다른 곳엔 이미
있었다: `profiles.school`은 20260814160000에서 `btrim(school) <> '' and length(school) <= 60`을
받았다. `programs`만 빠져 있었다.

### B. ★ 학교 초대코드가 추측이 아니라 **계산**으로 나왔다

코드 규칙이 `'SCH-' || upper(substr(md5(관리자 uuid), 1, 4))`였다. 입력이 관리자 uuid 하나뿐인
md5라서, **uuid를 아는 사람은 무차별 대입 없이 한 줄로 코드를 만들어낼 수 있다.**

그리고 그 uuid는 공개돼 있었다. ADR 0022가 대표 사진을 붙이면서 공개 URL이 이렇게 생겼기 때문이다.

```
https://<ref>.supabase.co/storage/v1/object/public/program-images/<관리자 uuid>/<파일>.webp
                                                                  ^^^^^^^^^^^^^^
```

`image_url`은 학생 화면 카드가 실제로 읽는 필드(`CARD_FIELDS`)다. 즉 **사진이 붙은 프로그램을
하나라도 본 학생은 그 관리자의 학교 초대코드를 즉시 계산할 수 있었다.**

ADR 0017이 `link_school_account()`에 붙인 5회 실패 → 15분 잠금은 이 경로를 **전혀 막지 못한다** —
첫 시도가 맞기 때문이다. 그 방어는 "무차별 대입"을 상정했는데 실제 위협은 무차별 대입이 아니었다.

> 이건 ADR 0022(사진)와 ADR 0008(초대코드)이 **각각은 옳은데 겹치는 순간 구멍이 되는** 사례다.
> 두 결정 사이에 "관리자 uuid는 비밀인가"를 물어본 문서가 없었다.

### C. 관리자 승격 코드가 추측 가능한 리터럴이었다

`ADMIN-2026`. 그 값이 마이그레이션·ADR 0017·`SignupPage` placeholder 세 곳에 그대로 적혀 있었다.
이 코드 하나가 뚫리면 `role=admin` 계정이 생기고, 그 순간 포인트 지급 RPC(`verify_participation_qr`)가
열린다 — 이 앱에서 가장 비싼 사고다.

### D. `check_signup_availability()`가 익명·무제한 oracle이었다

anon이 호출 가능하고 rate limit이 없는데 **관리자 초대코드의 정오답까지 알려줬다.**
ADR 0017이 이 함수를 유예한 근거는 *"계정 생성 없이는 재시도가 안 된다"*였는데, 이 함수는 애초에
계정 없이 호출된다 — **그 근거가 이 함수에는 맞지 않았다.**

## 결정

### 결정 1 — 텍스트·숫자·날짜 제약을 `programs`에 건다 (20260820140000)

```sql
programs_title_shape        btrim(title) <> ''       and length(title) <= 80
programs_org_shape          btrim(org) <> ''         and length(org) <= 60
programs_description_shape  btrim(description) <> '' and length(description) <= 400
programs_time_shape         btrim("time") <> ''      and length("time") <= 40
programs_capacity_range     capacity is null or capacity between 1 and 1000
programs_date_range         date between '2020-01-01' and '2035-12-31'
programs_end_date_range     end_date is null or (같은 범위)
```

- **`btrim`을 함께 보는 이유**: 길이만 재면 `'   '`(공백 3칸)이 통과한다. 그러면 카드의 제목 자리가
  비어 보이는데 DB는 "값이 있다"고 답한다 — 화면과 데이터가 갈리는 상태다.
- **숫자를 폼의 `maxLength`와 정확히 같게 맞춘다.** 어긋나면 "폼에서는 되는데 저장이 안 되는" 칸이
  생기고, 어느 쪽이 진짜 규칙인지 아무도 모르게 된다.
  >>> 한쪽을 바꾸면 반드시 다른 쪽도 바꿀 것.
- **`capacity` 상한 1000의 근거**: 상한이 없으면 20억 같은 값이 저장돼 "정원 있음"이 사실상
  "정원 없음"과 같아진다. 그건 이미 `NULL`이 표현하는 상태다 — 두 표현이 겹친다.
- **지난 날짜는 계속 허용한다.** 확정 H("막지 않고 경고만")를 뒤집지 않는다. 여기서 막는 것은
  **연도 오타 수준의 값**이다.
- `programs_capacity_positive`는 `programs_capacity_range`로 **대체**한다. 규칙 하나에 제약 두 개를
  두지 않는다.

### 결정 2 — 초대코드를 난수로 바꾸고, 규칙의 소유자를 함수 하나로 (20260820120000)

`public.new_school_invite_code()` → `SCH-` + 난수 8자리(16⁸ ≈ 43억). `generate_personal_code()`와
같은 패턴(충돌 시 재시도, fail-closed)이다.

- **salt를 섞는 방법은 기각했다.** salt가 이 파일(=git)에 남으면 같은 문제가 그대로 돌아온다.
  입력이 공개값 하나뿐인 해시는 "비밀"이 아니라 **인코딩**이다.
- **결정론적 재실행 안전성을 잃는 대가를 받아들인다.** 기존 백필은 `not exists` 가드가 있어
  재실행해도 새 코드를 뽑지 않는다.
- **기존 코드는 전부 교체한다.** 옛 규칙으로 만들어진 값은 이미 유출된 것으로 간주한다.
- 관리자 승격 코드도 `ADMIN-` + 난수 12자리로 교체한다. **새 값은 마이그레이션 파일에 적지
  않는다** — 적으면 git에 남는다. 적용 후 `select`로 읽는다(파일 하단에 쿼리를 적어 뒀다).
- ADR 0017의 잠금은 **그대로 유지한다.** 방어선을 줄이지 않는다.

> **함수로 뽑아낸 이유가 따로 있다.** 이 규칙은 마이그레이션 4개에 리터럴로 복사돼 있었다
> (20260731120000 / 20260731140000 / 20260814160000 / 20260814180000). 규칙이 여러 벌이면 다음에
> 트리거를 재정의하는 사람이 옛 규칙을 그대로 옮겨 적는다 — 실제로 4번 그렇게 됐다.
> >>> 앞으로 `handle_new_user()`를 다시 정의할 때 **리터럴을 쓰지 말고 이 함수를 호출할 것.**

### 결정 3 — `check_signup_availability()`에서 관리자 분기를 제거한다

남는 것: 학번/코드 중복(`code_taken`) + **학교** 초대코드 유효성.
사라지는 것: 관리자 초대코드 검사.

- **기능 회귀가 없다.** 틀린 관리자 코드로 가입을 시도하면 `handle_new_user()`가 같은 문구로
  거부하고 가입 자체가 롤백된다. `authService.js`가 그 문구를 `invalid_admin_invite`로 이미
  매핑하고 있다(`/초대코드/` 정규식) — 프런트는 **한 줄도 바꾸지 않았다.**
- **비용 구조가 달라진다.** 판정 1회에 `signUp` POST 1회가 들고 Supabase Auth의 기본 요청 제한을
  탄다. 값싼 oracle이 아니게 된다.
- 학교 코드 검사는 남긴다 — 43억 공간의 난수라 정오답을 알려줘도 전수 조사가 성립하지 않고,
  "코드를 잘못 적었다"를 즉시 말해주는 가입 UX 가치가 그대로 크다.
- 인자 시그니처는 유지한다(`p_invite`를 계속 받되 admin일 때 보지 않는다) — 바꾸면 호출부가 깨진다.

  >>> **여기에 admin 분기를 되살리지 말 것.** 되살리는 순간 같은 oracle이 돌아온다.

### 결정 4 — `image_url`이 **자기 폴더**를 가리키는지 정책에서 검사한다

```sql
and (image_url is null or position('/program-images/' || auth.uid()::text || '/' in image_url) > 0)
```

20260814120000이 `image_url`을 "우리 버킷 공개 URL"까지 좁혔지만 경로 안의 폴더는 보지 않았다.
스토리지 insert 정책은 `(storage.foldername(name))[1] = auth.uid()::text`로 **올리는 쪽**을 이미
막고 있었는데 **참조하는 쪽**이 비어 있었다. 두 정책이 같은 축(폴더 = 소유자)을 말하도록 맞춘다.

- **CHECK가 아니라 정책인 이유**: `auth.uid()`는 IMMUTABLE이 아니라 CHECK 제약에 쓸 수 없다.
  행 경계를 판정하는 자리는 어차피 정책이다.
- 정상 경로에는 영향이 없다. `uploadProgramImage()`가 만드는 경로가 언제나 `${adminId}/...`다.

### 결정 5 — CORS를 오리진 허용목록으로 좁힌다 (Edge Function 3개)

`'Access-Control-Allow-Origin': '*'` → 환경변수 `ALLOWED_ORIGINS` + `localhost` + `*.vercel.app`.

- **요청 자체를 403으로 막지는 않는다.** CORS는 브라우저의 규칙이고, 서버측 경계는 각 함수의
  JWT 검증/OAuth code 대조가 따로 갖고 있다. 여기서 403을 내면 두 경계가 겹쳐 원인 파악만 어려워진다.
- `*.vercel.app`은 느슨한 규칙이다. 배포 주소가 정해지면 `ALLOWED_ORIGINS`에 넣고 지우는 것이 맞다.
  지금은 **시연이 조용히 깨지는 쪽이 더 비싸서** 남겨둔다.

### 결정 6 — RLS 회귀 테스트를 만든다 (`scripts/test-rls.mjs`)

이 프로젝트의 권한 경계는 전부 DB 안에 있는데, 그것이 실제로 막히는지는 지금까지 **문서와 손
확인**으로만 검증됐다. 정책은 한 줄만 어긋나도 조용히 열리고, **조용히 열린 것은 화면을 보는
것으로는 절대 발견되지 않는다** — 화면은 원래 그 데이터를 안 그리기 때문이다.

- anon / 학생 2명 / 관리자 2명의 **anon 키 세션**으로 금지된 요청 약 50건을 실제로 쏜다.
  통과가 아니라 **거부**를 기대하는 테스트가 대부분이다.
- `service_role`은 테스트 계정 생성·정리에만 쓴다. 그 키로 검증하면 RLS를 우회해 **모든 테스트가
  통과하고 아무것도 검증하지 않는다.**
- 만드는 데이터에 전부 마커(`[RLS-TEST]`, `RLSTEST-`)를 붙이고 `finally`에서 지운다.
  중간에 죽어도 `--cleanup`으로 같은 조건으로 지운다.
- 결정 2의 회귀를 직접 검사하는 테스트가 있다: 저장된 school 코드가 `md5(admin_id)[0:4]`와
  **같지 않은지** 확인한다. 마이그레이션을 안 돌린 환경에서 즉시 빨간불이 뜬다.

## 대안으로 고려했던 것

| 안 | 기각 이유 |
|---|---|
| 폼의 `maxLength`만 믿는다 | 개발자도구·`curl`로 우회된다. 화면에서 막는 것은 UX이지 경계가 아니다(ADR 0005 반복) |
| 초대코드에 salt를 섞는다 | salt가 git에 남으면 같은 문제가 돌아온다 |
| `check_signup_availability()`에 rate limit을 건다 | anon 호출이라 계정 단위 카운터를 걸 자리가 없다. IP는 Postgres가 모른다. **표적을 없애는 쪽**이 싸고 확실하다 |
| `status`를 파생값으로 바꾼다 | 옳은 방향이지만 ADR 0003의 "정적 필드" 결정을 뒤집는 별개의 작업이다 — 아래 "다음"에 남긴다 |
| 게시 전환에 게이트 RPC를 둔다 | 같은 이유로 분리한다 (이번 변경은 "검증"이고, 그건 "승인 절차"다) |
| pgTAP으로 테스트한다 | DB 확장 설치가 필요하고 CI가 없다. **실제 HTTP 경로**로 쏘는 편이 이 앱의 위협 모델(브라우저에서 anon 키로 오는 요청)에 더 가깝다 |

## 원칙 체크

- **원칙 1(게임화 배제)**: 무관. 새 화면·새 표시값 0개.
- **원칙 4(포트폴리오 우선)**: 무관.
- **원칙 6(관리자 기능 5종)**: 늘어난 관리자 동작 0개. 기존 동작에 **거부 조건**만 붙었다.
- **ADR 0008 "초대코드는 표시만"**: 그대로. 생성·재발급·회수 UI를 만들지 않았다 — 값이 바뀐 것은
  마이그레이션이고, 관리자 마이페이지는 여전히 읽어서 보여줄 뿐이다.
- **ADR 0009/0011 소셜 가드**: 두 Edge Function의 인자가 그대로다(`code`/`state`). CORS 헤더만 바뀌었다.

## 알려진 사항 (이번에 닫지 않은 것)

1. **`find_student_code_by_name()`은 여전히 무제한이다.** 이름으로 학번을 얻을 수 있다. ADR 0020이
   수용한 판단 그대로다 — 다만 이제는 그 학번으로 할 수 있는 다음 단계(초대코드 계산)가 막혔다.
2. **`status`가 여전히 관리자의 자유 입력이다.** 지난 날짜인데 `open`, 정원이 찼는데 `open`이
   가능하다. 실제 신청 가능 여부는 트리거+RLS가 정하는데 화면 라벨은 이 값이 정한다 — **사본이
   둘이고 어긋나도 아무도 막지 않는다.** 파생값으로 바꾸는 것이 맞다.
3. ~~**게시(`is_published=true`) 전환에 게이트가 0개다.**~~ → **ADR 0026 결정 1에서 해소** (미리보기 + 체크리스트 + 서버 검사 + `programs_publish_gate` 트리거).
   원래 적어 뒀던 내용: 초안이 완성됐는지, 날짜가 지났는지 아무도
   보지 않는다. 실제 유사 시스템(꿈길의 학교운영자 승인, 청소년수련활동 인증제)은 전부 이 자리에
   **승인 절차**를 둔다. 1인 시연이라 승인자를 둘 수 없으니 **승인 조건을 서버 함수에 박는** 것이
   그 자리를 대신할 수 있다.
4. ~~**관리자 행위 감사 로그가 없다.**~~ → **ADR 0025 결정 3-2에서 해소** (`admin_audit` — 남기되 읽는 화면은 0개).

## 재검토 시점

- 배포 주소가 확정되면 → `ALLOWED_ORIGINS`에 넣고 `*.vercel.app` 규칙을 지운다(결정 5).
- `status`를 파생값으로 바꿀 때 → 위 "알려진 사항 2". ADR 0003의 재검토 시점이 온 것이다.
- 학교가 여러 개가 될 때 → 초대코드가 학교 단위로 갈라지는지 다시 본다.
- 테스트가 CI에서 돌아야 할 때 → `.env.seed`를 시크릿으로 넣고 `npm run test:rls`를 그대로 쓴다.
