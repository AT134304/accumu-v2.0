# ADR 0020: 본인 비밀번호 변경 + 아이디/비밀번호 찾기

## 상태

확정 (2026-08-11, 케빈 요청).

## 배경

ADR 0019(관리자의 담당 학생 비밀번호 초기화)를 실제로 써 본 케빈의 피드백: *"초기화는 잘 작동하는데
초기화된 비번을 다시 바꿀 방법이 없어."* 이어서 *"로그인 화면에 '비밀번호를 잊어버리셨습니까?',
'아이디를 잊어버리셨습니까?' 이거 기능도 추가해줘."*

`docs/specs/auth-login.md`(2026-07-16 작성)는 "비밀번호 찾기/재설정 화면"을 명시적으로 스코프
밖에 뒀었다 — 그 시점엔 회원가입도, 소셜 로그인도 없던 최초 스펙이다. 그 뒤로 회원가입(ADR 0008),
소셜 로그인(ADR 0009~0011)이 이미 그 스펙을 사실상 넘어섰고, 이번 요청으로 비밀번호 관리도 같은
길을 걷는다. (오래된 스펙 파일 자체는 고치지 않는다 — 이 프로젝트의 관례대로 ADR이 현재 상태의
기록이고 스펙은 그 시점의 동결된 기록이다.)

세 가지를 만들었고, 계정 종류(학교/개인/관리자)마다 실제로 가능한 일이 다르다는 전제는
ADR 0019에서 이미 확립된 것을 그대로 물려받는다 — 학번/관리자코드 계정은 가상 이메일이라
이메일 기반 자동화가 안 통한다.

---

## 결정

### 결정 1 — 로그인 상태에서는 누구나 스스로 비밀번호를 바꿀 수 있다

`authService.updateMyPassword(newPassword)` 신규 — `supabase.auth.updateUser({ password })` 한
줄이다. 현재 비밀번호를 다시 묻지 않는다 — 이미 유효한 세션이 본인 확인을 대신한다(Supabase Auth의
기존 신뢰 모델을 그대로 따른다).

`PasswordChangeForm` 컴포넌트 하나를 학생/관리자 마이페이지가 공유한다. 소셜 계정에도 숨기지
않는다 — 소셜 계정에 비밀번호를 새로 얹는 것도 Supabase가 허용하는 정상 동작이고("이후 이메일/
비밀번호로도 로그인 가능해진다"는 부가 옵션), 계정 종류로 화면을 나누면 분기만 늘고 얻는 게 없다.

이것으로 ADR 0019의 "알려진 사항"에 남아 있던 gap이 닫힌다 — 관리자가 초기화해 준 임시 비밀번호를
학생이 로그인 후 원하는 값으로 바꿀 수 있다.

### 결정 1-1 — **위 결정 1을 뒤집는다: 현재 비밀번호를 묻는다** (2026-08-14, 케빈 요청)

> 케빈: *"그 비밀번호 변경이 너무 아무 인증없이 쉽게 되는데 보통 다른 사이트도 그래?"* → 아니다.
> 현재 비밀번호를 묻는 것이 표준이고(OWASP ASVS가 명시적으로 요구한다), 이 앱은 오히려 더 필요한
> 조건을 갖고 있었다.

**결정 1의 논리는 틀리지 않았다 — 막으려는 위협을 잘못 골랐다.** "유효한 세션 = 본인 확인"은
*계정 주인인지*를 묻는 질문에는 맞는 답이다. 그런데 이 확인이 실제로 막는 것은 그게 아니라
**로그인된 화면을 잠깐 만진 사람이 계정을 영구히 가져가는 것**이다:

| 상황 | 현재 비번을 안 물으면 | 물으면 |
|---|---|---|
| 학교 공용 PC에 로그아웃 안 하고 자리를 뜸 | 다음 사람이 비번을 바꿔 **계정 탈취** | 못 바꾼다 |
| 폰을 잠깐 빌려줌 / 분실 | 같음 | 못 바꾼다 |
| 토큰 탈취 | 영구 장악 | 추가 장벽 |

이 앱은 **학번이 곧 로그인 아이디**라(CLAUDE.md 4장) 아이디 쪽이 이미 반쯤 공개돼 있고, 학교
공용 PC 사용이 전제된 환경이다. 게다가 탈취당하면 원래 주인이 스스로 되찾을 방법이 없다 —
관리자 초기화(ADR 0019)를 거쳐야 한다.

- `changeMyPasswordWithCurrent(current, next)` 신규. **`updateMyPassword()`는 그대로 남는다** —
  쓰는 곳이 `/auth/reset-password`(결정 2)와 관리자 초기화(ADR 0019)이고, 둘 다 **옛 비밀번호를
  모르는 사람을 위한 경로**라 물으면 경로 자체가 성립하지 않는다.
  >>> 마이페이지를 `updateMyPassword()`로 되돌리지 말 것.
- **검증은 같은 이메일로 다시 `signInWithPassword`.** Supabase의 `reauthenticate()`는 확인 코드를
  **메일로 보내는** 방식이라 `@accumu.local` 가상 주소 계정(학번·관리자코드)에서 쓸 수 없다.
  세션의 이메일을 쓰므로 학번·관리자코드·실제 이메일이 전부 같은 코드 경로를 탄다.
  실패해도 기존 세션은 유지되고, 성공하면 같은 사용자의 세션으로 교체된다(AuthContext의
  `profileIdRef` 가드 덕에 프로필 재조회도 일어나지 않는다).
- 429(시도 과다)는 "비밀번호가 틀렸다"와 **다른 문구**로 말한다. 뭉개면 맞는 비밀번호를 넣고도
  계속 틀렸다는 말을 듣는다.
- 입력이 3칸이 되면서 인라인 펼침 → **모달**로 옮겼다.

### 결정 1-2 — **소셜 계정에는 변경 칸을 만들지 않는다** (결정 1의 반대, 같은 날)

결정 1은 "소셜 계정에도 비밀번호를 얹는 부가 옵션"으로 폼을 열어 뒀다. 결정 1-1로 현재 비밀번호가
필수가 된 이상 그 전제가 무너진다 — **소셜 계정에는 입력할 현재 비밀번호가 없어 반드시 실패하는
칸이 된다.** 빈 화면으로 두지도 않는다(빠진 기능처럼 보인다). "○○ 계정으로 로그인 중이에요 ·
비밀번호는 ○○에서 관리합니다" 한 줄로 대체한다.

**구분 방법이 문제였다.** 두 Edge Function이 `admin.createUser`로 계정을 만들기 때문에 Supabase가
보는 provider는 `'email'`이고, 제공자가 준 **실제 이메일**을 그대로 쓰므로(naver-auth 96줄 /
google-auth 117줄) 이메일 모양으로도 개인 계정과 구분되지 않는다. 그래서 두 함수가
`user_metadata.auth_provider`를 직접 심는다(`socialProviderOf()`가 읽는다).

- >>> **이건 ADR 0009 결정 3 / ADR 0011 결정 4의 "인자를 추가하지 말 것" 가드에 걸리지 않는다.**
  그 가드의 취지는 *클라이언트가 보낸 값으로 권한을 정하지 않는다*이다. `auth_provider`는 요청
  본문에서 오지 않고 **함수가 자기 자신이 누구인지로** 정한다. `role`/`code`/`invite`는 여전히 금지다.
- 표식이 생기기 전에 만들어진 소셜 계정은 다음 로그인 때 `updateUserById`로 소급 기록된다.
  그전까지는 변경 칸이 보이지만 현재 비밀번호를 모르니 바꾸지는 못한다(안전한 쪽으로 실패한다).
- >>> **두 Edge Function을 재배포해야 적용된다** (`supabase functions deploy naver-auth google-auth`).

### 결정 2 — "비밀번호를 잊으셨나요?"는 계정 종류마다 다르게 답한다

로그인 화면에 링크를 추가했다. 실제 동작은 둘로 갈린다:

| 계정 종류 | 동작 |
|---|---|
| 개인 계정(실제 이메일) | **진짜로 작동한다.** `authService.requestPasswordReset(email)` → Supabase가 재설정 링크를 실제로 발송 → `/auth/reset-password`(신규 라우트)에서 완료 |
| 학교 계정(학번) | 안내 문구만. "담당 선생님(관리자)에게 문의해 초기화를 요청하세요" — ADR 0019의 경로를 가리킨다 |
| 관리자 | 안내 문구만. "운영자에게 문의하세요" — ADR 0019가 이미 "관리자 본인 복구는 범위 밖"으로 정한 것과 같다 |

**존재 여부를 노출하지 않는다.** `requestPasswordReset`은 그 이메일이 실제 가입 계정인지와 무관하게
항상 같은 결과를 낸다(Supabase 기본 동작) — 화면 문구도 "보냈어요"로 통일하고 성공/실패로 계정
존재를 유추할 수 있는 문구를 만들지 않는다.

`/auth/reset-password`(`ResetPasswordPage`, 신규 공개 라우트)는 이메일 링크의 recovery 토큰을
Supabase 클라이언트가 자동으로 세션으로 바꾼 뒤, 그 세션에서 결정 1과 같은 `updateMyPassword()`를
불러 새 비밀번호를 반영한다 — "메일로 온 링크로 들어와 새 비밀번호를 설정한다"와 "로그인한 채
비밀번호를 바꾼다"는 이 앱에서 같은 동작이라 함수를 나누지 않았다.

### 결정 3 — "아이디를 잊으셨나요?"는 학교 계정만 실제 조회가 있다

| 계정 종류 | 동작 |
|---|---|
| 학교 계정(학번) | **진짜로 작동한다.** 이름을 넣으면 `find_student_code_by_name()` RPC가 학번을 찾아 준다 |
| 개인 계정 | 안내 문구만. "아이디는 가입 시 사용한 이메일이에요" — 이메일 자체가 아이디라 조회할 "다른 무언가"가 없다 |
| 관리자 | 안내 문구만. "운영자에게 문의하세요" |

**학번 노출을 수용하는 근거는 새로 만든 것이 아니라 ADR 0008 결정 4의 연장이다.** 회원가입 화면의
`check_signup_availability()`가 이미 "학번은 교실에서 공개적으로 쓰이는 식별자이고 비밀번호 없이는
아무것도 되지 않는다"는 판단으로 `code_taken`(학번 존재 여부)을 `anon`에게 노출해 왔다. 이번 함수는
"존재하는가"를 "그 이름의 학번이 무엇인가"로 한 단계 넓힌 것뿐 — 같은 위험 등급, 같은 판단이다.

- **정확히 일치하는 이름 1명일 때만** 학번을 돌려준다. 0명이면 `not_found`, 2명 이상이면
  `ambiguous`(추측해서 알려주지 않는다) — 틀린 학번을 알려주는 것보다 "모른다"가 안전하다.
- **rate limit을 걸지 않았다.** `check_signup_availability`도 원래 무제한이라 같은 위험 등급에
  이 함수만 특별히 막을 근거가 약하다. ADR 0017의 `link_school_account` rate limit은 "로그인한
  계정 하나로 수만 번을 값싸게 반복"할 수 있다는 다른 종류의 위험이었다(매 시도가 요청 하나로
  끝나는 이 함수와는 비용 구조가 다르다). 필요해지면 그때 같은 패턴(실패 카운터+쿨다운)을 추가한다.

## 절대 원칙 체크

- **원칙 1·4·6**: 영향 없음. 관리자 기능 개수도, 포인트 시각 위계도 건드리지 않는다 —
  이번 기능은 전부 학생·개인·관리자 "본인" 계정 관리이지 관리자가 남에게 하는 동작이 아니다
  (ADR 0019와 다른 지점 — 그건 원칙 6을 다시 열었지만 이번 ADR은 열 필요가 없었다).
- **CLAUDE.md 개정 불필요**: 절대 원칙을 하나도 바꾸지 않는다.

## 알려진 사항

- **관리자 본인의 비밀번호 복구는 여전히 자동화돼 있지 않다.** ADR 0019가 이미 "1인 시연" 전제로
  범위 밖에 뒀고, 이번 ADR도 같은 판단을 유지한다 — Supabase 대시보드에서 직접 바꾼다.
- **학번 찾기는 이름 완전 일치만 지원한다.** 부분 검색·유사 이름 추천은 만들지 않았다 —
  검색 범위가 넓어질수록 "이름 목록을 훑어 학번을 캐내는" 시나리오에 가까워진다.
- **비밀번호 재설정 이메일은 개인 계정에만 실제로 발송된다.** 학교/관리자 계정 이메일
  (`{학번}@accumu.local`)에 이 함수를 호출해도 API 자체는 성공을 반환하지만 실제로 받는 사람이
  없다 — 그래서 UI가 애초에 그 경로로 안내하지 않는다(결정 2 표).
- **`/auth/reset-password`는 "이미 로그인된 다른 세션"과 구분하지 않는다.** recovery 링크로 온
  것인지, 이미 로그인된 사용자가 URL을 직접 입력한 것인지 구분하지 않고 "세션이 있으면 비밀번호
  변경 폼을 보여준다" — 어느 경우든 본인 계정의 비밀번호를 바꾸는 것이라 실질적 위험 차이가 없고,
  이미 마이페이지에서 할 수 있는 일(결정 1)과 같은 동작이라 새로 여는 권한이 아니다.
